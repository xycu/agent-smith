# agent-smith reference

Full behavior of `/agent-smith:10x-pipeline`: routing, run isolation, review routing, rigor, archive, pre-plan steps, budget, executors, manual verification, scoring, reports, comparison, provenance, opt-in features and limits. The OpenSpec chain, `/agent-smith:openspec-pipeline`, has its own section at the end; everything it does not name works as in the 10x chain. For install and a first run, see the [README](../README.md). Decisions and their reasons are in [`docs/ADR/`](ADR/).

For both the 10x and OpenSpec chains, `init` accepts change ids or names of 1–100 characters using lowercase letters, digits and hyphens, starting with a letter or digit. An otherwise valid id longer than 100 characters halts with exit 1 before project filesystem reads or writes, including when resuming an existing run with `init`. Existing longer-id runs remain accessible through `next`, `status`, `status --report`, `risk`, `usage`, `verify-archive` and `compare`, subject to each command’s state requirements.

## Codex and provider dispatch

Both chain skills share the router and a standalone `scripts/run-codex.mjs` execution boundary (ADR-024). Claude Code hosts Claude or mixed ladders. Codex hosts OpenAI-only ladders. `init --host claude|codex` stores the host permanently for a run. Omitted host/provider fields in old state read as Claude. A conflicting resume or incompatible mutable policy halts before dispatch.

Each ladder rung can declare `provider` as `claude` or `openai`. Absence means Claude. OpenAI actions and pending entries also carry nullable `profile`, selected by optional policy `codex.profile`. Null or absent configuration uses existing Codex settings and omits `-p`. A named configuration must already exist. The copyable `codex-policy.json` overlay replaces the ladder with eight OpenAI rungs while retaining tier indexes and effort positions. Merge it into existing project overrides explicitly. Model names remain arbitrary nonempty identifiers. The preset is an initial capability ordering with no measured equivalence claim.

Upgrade note: the GPT overlay now uses `gpt-6.2-sol` and `gpt-6.2-astra`, with Luna, all eight tiers and every effort unchanged. Installing the plugin does not rewrite copied overrides. To adopt it, explicitly re-merge the entire preset ladder into `context/foundation/agent-smith-policy.json`, preserving unrelated keys and reconciling any custom ladder; prefer adoption between runs. Recorded attempts and pending/neutral retries retain their stored targets, while newly selected targets use the effective ladder. When a run has recorded provenance and tracks the `ladder` section, a regular `next` call adds `ladder` to `provenance.drift` if the effective ladder differs from the recorded ladder. `compare` reports recorded drift separately. Between runs, `ladder` is an allowed difference in default pinned comparison mode. To roll back, restore the prior seven model values in both repository policies with the matching assertion and upgrade guidance through a preserving forward edit or revert; downstream users can re-merge their prior ladder while preserving other keys. Older-model availability remains a prerequisite. Rollback affects later dispatches and can itself record drift; never rewrite recorded targets or logs. This update does not requalify historical execution or establish live access to the new models.

The verified CLI contract is Codex 0.169.0 with Node 24+. Authenticated model access, explicit project trust and child-visible upstream toolkit skills are installation prerequisites. The compatibility manifest declares `./skills/` for both shared workflows. Claude uses `${CLAUDE_SKILL_DIR}`. Codex resolves scripts relative to the absolute loaded SKILL.md path. OpenSpec resolves the sibling 10x scripts directory. A parent session's skill catalog alone cannot prove fresh-child discovery. Clean import, toolkit discovery and paid execution remain live acceptance checks.

The runner accepts the entire action JSON on stdin with `node <absolute scripts path>/run-codex.mjs <id> [--chain 10x|openspec]` from the run root. It validates root, change, chain, host and exact pending dispatch. Inline actions must match the stored full prompt and have no `promptFile`. File actions must match the stored short prompt and canonical relative path, with a regular task file containing exactly the stored task bytes; these checks run before and after the permission probe. Archive actions reject file handoff fields. Neutral retries keep stored provider/model/effort/profile/prompt despite policy changes. Archive validation checks the ended archive state and router-selected destination. The runner never writes router state or result files and never advances the router.

Execution uses a fresh `codex exec`, exact prompt stdin, absolute `-C`, model `-m`, reasoning-effort configuration, JSONL output, retained native CLI session metadata and a unique final-message file outside the worktree. Optional `-p` is supplied only for an explicit profile. Native children are enabled with `-c agents.enabled=true --disable multi_agent_v2`, as observed on CLI 0.169.0. The separate exec is the step root. The shared child contract permits one leaf layer; current documented Codex settings supply no depth cap, so this bound is an instruction, not a verified runtime limit. Existing configuration, managed requirements, outer restrictions, execpolicy and hooks remain in control. The runner grants no trust or permissions. Child-owned typed code commits and archive commits remain required before RESULT.

Before launching, a model-free native sandbox probe checks the actual resolved Git metadata, shared objects and refs, then commits in a disposable linked-worktree fixture. It uses the same configuration selection and process working directory. The sandbox's `-C` and `--include-managed-config` flags require an explicit permissions profile `-P`, so the runner supplies neither. Managed requirements are included by default. Legacy `sandbox_mode` can be forced read-only by native sandbox, preventing parity verification even when `exec` would differ. An unverifiable probe stops before model launch. This filesystem proof does not exercise shell-tool execpolicy or model-command hooks. Live approval behavior remains pending. [Phase 2 evidence](../context/archive/2026-11-13-openai-codex-support/evidence/phase2-permissions.md)

The runner returns `launched`, `completed`, normalized `result`, measured `usage` and a bounded failure `reason` when needed. Completed transport requires exit zero, a final successful completed turn, final-file equality with the final assistant event and a valid last RESULT in that message. An invalid last RESULT cannot reuse an earlier success. A child-authored `orchestrator-error` becomes `unknown`. Only a confirmed `launched: false` permits the host to declare its own orchestration fault. Successful transport preserves child failure statuses. The host writes the normalized result to the selected result file and calls `next` after the runner closes. Archive replies return without recreating the moved folder.

The shared run lock covers execution, `init`, `next`, `usage` and `status --report`. Plain `status` stays readable. Cancellation forwards to the child process group, waits for close and cleans owned temporary files. After model launch, it retains the native execution lock for authorized reconciliation and router-owned recovery. Hosts retain a running terminal handle and wait through completion. A foreground observation timeout never authorizes a duplicate launch.

Before every native-capable model launch, including historical flat-prompt retries, the existing lock records native ownership with a null child PID, then its PID and root thread identity. That ownership can settle for a successful result or an ordinary failure of a pending `run` action. An ordinary failure is a numeric nonzero exit, exit zero with a final root `turn.failed`, or exit zero with root `turn.completed` and a matching final file and assistant event that lack a valid last RESULT. A numeric nonzero exit or a final failed turn can be reconciled without a usable reply. Eligibility requires process close, a trusted recorded root and intact execution JSONL without launch or stream faults, cancellation, an exit signal or an explicit root interruption. Archive settlement still requires the successful result protocol.

The model-free app-server must prove a latest `completed` turn for every descendant and for the root of a successful result. For an eligible failed result the root may also have a latest `failed` turn. A proven turn has a positive safe-integer completion timestamp and a consistent start timestamp when present. Release also requires recursive descendant enumeration across every source kind, archived and unarchived threads, complete pagination, stable membership on re-enumeration and closure of the recorded process group. The runner omits `--ephemeral` so Codex retains its own CLI session records. The runner stores no transcript in run state or locks.

After an ordinary failure settles, the runner exits 1 with `launched: true`, `completed: false`, a null result, the original failure reason and measured exec duration. It skips optional usage metadata reads. The host writes `unknown` with the reason and duration and calls `next` after the runner closes. The router records a failed attempt and can retry within the existing budget.

Uncertain closure retains native exclusion even after the process group disappears. `Execution suspended:` names the exact lock path and the recorded thread or `unknown`. Both orchestrators STOP before result writes, `next`, late usage, archive follow-up and publication. Read-only status stays available. Keep the enabling revision and same TMPDIR. Await an active runner through its existing handle. After it exits, the authorized owner must inspect the recorded thread and its descendants, prove settlement and arrange router-owned recovery before mutation, relaunch or publication. Automatic recovery for a retained native lock is unavailable. Never delete a production lock or change TMPDIR to bypass it. Legacy numeric/flat locks retain their original dead-PID/group recovery semantics, and model-free preflight keeps its existing lifecycle. Saved dispatches, lock records, results and run schemas remain compatible.

Token accounting runs after successful native settlement, separately from execution correctness. The runner replaces step-authored accounting with observed usage and optional version-1 `usageEvidence`: verified `step-tree` coverage, or unavailable with a bounded reason. Flat steps use the same contract as delegated steps. Codex 0.169.0 accounting joins actual thread IDs and the causal root session/turn, deduplicates response IDs, reconciles each context against its own final snapshot and sums disjoint contexts, including archived descendants. App-server metadata session IDs identify each thread itself; persisted rollout session IDs identify the causal root. It adds input plus output; cached input and reasoning output are subsets. The exec stream corroborates its root snapshot and is never added again. Proven copied legacy and paginated-child boundaries are supported; unknown resumed/forked/root history is unavailable. A collaboration marker does not itself prove coverage. Child messages and explicitly foreign terminal events never supply enclosing completion. Independently measured elapsed duration covers the enclosing exec, including child waits; no tool count is invented.

Both skills use the shared [observed-usage contract](#observed-token-accounting) for on-time, late and archive accounting. Claude native collection is optional and requires already-authorized matching local sources. Identity matching alone proves no completeness. A missing source, unsupported version, default zero without records, partial capture or ambiguity leaves tokens absent, with a reason. Accounting failure cannot turn settled execution into an execution fault. Archive usage stays in the final message and never enters numbered totals. Deterministic fixtures cover these contracts; final-candidate interactive/headless host qualification remains pending.

Status and reports expose enclosing provider/model/tier groups. The pinned baseline remains Claude/Sonnet/high; GPT or custom baselines use `--unpinned`. Cross-provider token comparisons remain raw counts with different tokenizer and billing semantics. Blended prices are routing-rate approximations whenever verified subtree usage is present; they cannot establish actual child-model spend.

OpenAI manual verification selects `manual-verify-openai` after provider selection unless the user explicitly selected `--chrome false`. Browser rows require covering test, command or script evidence and a truthful browser-unavailable reason, or remain pending. The evidence-kind check rejects browser-prefixed claims from OpenAI steps. Native restricted Claude agents and matching advisor opt-ins refuse OpenAI dispatch. The archive gate uses the host's available native question capability and fails closed when no affirmative answer exists.

## Step safety and pre-publication acceptance

Every newly assembled task carries the shared safety rules in `skills/10x-pipeline/rules/top.md`, including both archive paths, overridden templates and file-handoff bodies. They cover actions through any tool or API. Working-copy and staged-only versions need preservation in a commit or ref before discard. The rules forbid force-push, rewriting pushed history, bypassing Git hooks, deleting uniquely reachable commits or protected GitHub data, repository settings or branch protection changes and step-owned publication. The router owns run snapshots, rollback and state. Authorized local implementation and archive commits follow their scoped instructions.

The `plan` step rules cover `plan`, `plan-revise`, `plan-replan` and `plan-rejected`. Automated acceptance runs locally before publication, including deterministic tests with fake Git/GitHub clients. Checks requiring a pushed branch, open PR, PR CI or an external PR comment belong in Manual acceptance. Initial and confirmation plan reviews inspect phase Success Criteria and canonical Progress, move an actionable pending row intact to Manual and synchronize its Success Criteria and brief. They preserve row ids, titles and tick state. A ticked or immutable contradiction follows existing pending-finding and `signals.needsHuman` handling. OpenSpec `os-propose` records post-publication follow-up in proposal/design Manual acceptance, outside executable apply tasks.

New Claude run actions select `agent-smith:step` unless an enabled restricted mapping supplies a usable type. Both Claude archive actions select the fixed guarded type, following their existing treatment of restricted mappings. Its `agents/step.md` definition inherits session tools and uses router-selected execution parameters. OpenAI actions use the existing Codex runner and host permission controls. An unresolved Claude agent follows existing failed-attempt handling. Exact historical neutral retries replay their stored prompt and optional agent field, including an absent field. New safety text and identity take effect at the next newly assembled dispatch, so upgrades need a fresh session loading the plugin agent and hooks.

The plugin-level `hooks/hooks.json` registers a synchronous `PreToolUse` Bash hook. Exec form invokes Node with the plugin-root script path as one argument, including paths with spaces. `step-guard.mjs` scopes events to the exact top-level `agent_type: agent-smith:step` with a present `agent_id`. The 64 KiB input cap applies to those events, including an invalid ID. Oversized non-step events pass through with neutral output when the complete JSON object validates within 64 simultaneously open containers, including the root, and the five-second hook timeout. Malformed scoped commands at or below 64 KiB deny. Invalid JSON, non-object input, exceeding the oversized nesting limit, startup failure and timeout fail closed.

The direct-command subset forbids push, `gh`, hook bypass, hard reset, checkout, restore including staged-only restore, non-dry-run clean, stash drop/clear, destructive branch/tag/ref/worktree deletion and router snapshot ref writes. The stateless guard conservatively denies checkout and restore because it cannot prove preservation. It forbids recursive shell deletion and find deletion, plus direct execution of `open-pr.mjs` and `pr-comment.mjs`. Literal quotes, escapes, leading `cd` and separators `&&`, `||`, pipes, semicolons and newlines are covered by payload tests. Read-only Git, typed/archive commits, dry-run clean, inspected single-file unlink and empty-directory removal are covered positive cases. The guard performs only stdin reading and decision output.

The hook accepts literal heredoc data for simple `cat` or `tee` commands and pipelines composed of those commands with literal file destinations. Delimiters are simple words made of ASCII letters, digits, underscores, periods or hyphens, or wholly single- or double-quoted words. The `<<-` form permits tab-indented closing delimiters. A quoted heredoc captured by `cat` is also supported as the entire separate `-m` operand of literal `git commit`. The hook denies active expansions in unquoted bodies and ambiguous routes such as interpreter input, computed destinations, descriptor changes, special Bash descriptor and socket paths, and compound routing. Quote the delimiter to keep text literal or use the Write tool. Unsupported delimiters and missing terminators fail closed with guidance.

Runtime coverage is bounded to those direct forms. Aliases, dynamic shell construction, wrappers and helper internals, unrecognized syntax or executables, interpreter deletion, filesystem tools and MCP/API actions rely on the semantic rules and host controls. Custom mapped agents and OpenAI children use their existing host controls. Disabled hooks, unsupported identity schemas and managed settings suppressing plugin hooks provide no runtime guarantee. The plugin baseline is Claude Code 2.1.292+, while fail-closed handling requires 2.1.295+. Enforcement on older supported hosts is unverified. Fresh-host identity and blocking on both chains, plus live planning/review adherence, remain Manual acceptance checks. Payload tests and plugin validation establish their respective contracts. [Hooks](https://code.claude.com/docs/en/hooks) · [Subagents](https://code.claude.com/docs/en/sub-agents) · [Plugin hook discovery](https://code.claude.com/docs/en/plugins-reference)

The orchestrator owns terminal publication through `open-pr.mjs` and the authorized `pr-comment.mjs` call. Step agents cannot publish indirectly through those scripts. Human review and merge follow publication, including PR CI acceptance.

## State publication and log recovery

The shared state layer publishes `run.jsonl`, `meta.json` and `report.md` through an exclusively created same-directory `<state-basename>.<positive-decimal-pid>.tmp` file. It completes and closes the temp, then renames it over the target. Readers see complete previous or replacement bytes during process termination and ordinary filesystem failures. Existing regular-file permission bits carry into the replacement, and fresh files use the process umask.

Result intake publishes the verified completion to `run.jsonl` before unlinking `last-result.json`. On `next` and `init` resume, the latest executed entry owns cleanup, with skipped rows ignored. An already persisted result is authoritative. Intake removes any surviving result file without parsing it or re-verifying the completed entry. A missing file (ENOENT) is tolerated. Every other unlink error halts before handoff cleanup, step commits, rollback snapshots, terminal publication, pre-archive commits or a later dispatch. Fix the filesystem problem and retry `next`.

A pending latest entry consumes its own supplied result once. With no executed entry, intake leaves the result file untouched. The sequential producer writes one result for the dispatched pending entry and waits for `next` before producing another. Cleanup uses this persisted dispatch order. Late `usage` updates an explicitly numbered completed entry and preserves any later pending result file, including on identical or refused usage calls.

Each file has its own publication boundary. An interruption between publications can leave complete files from different command stages. Command recovery, rollback refs and the late-usage commit lifecycle govern that state. Power-loss durability depends on the underlying storage guarantees.

After taking the shared run lock, eligible `init`, `next`, `usage` and `status --report` commands inspect the full log and finish their command-specific guards. They then inspect and individually unlink abandoned immediate regular temps for exactly `run.jsonl`, `meta.json` and `report.md` before publication or Git staging. Matching symlinks, directories, nested entries and unrelated names retain their contents. Inspection or deletion errors halt the command. The Codex runner validates through reads while holding the same lock.

Writing commands and Codex action validation reject a damaged log before consuming a result, cleaning temps, updating state or launching execution. A strict refusal names the absolute file and first damaged physical line and gives recovery guidance. The run-folder bytes, pending result, index and refs retain their prior state. `usage` also validates before its equal-figure response.

Plain `status`, `risk`, `compare` and `verify-archive` inspect logs tolerantly and expose usable entries in source order. Problems appear as `logProblems` records with `{ file, line, reason }`. File paths are absolute, physical line numbers start at one, and file-read failures use `line: null`. Reasons identify invalid JSON, a non-object JSON value or a read failure while keeping raw log content private. Clean output omits `logProblems`. Empty physical lines and CRLF remain accepted. Missing and zero-byte logs retain their historical empty-log behavior. Object entries retain unknown fields. Whitespace-only nonempty lines require recovery. On both chains, any comparison-side diagnostic makes the pair ineligible while preserving partial totals and diagnostics for inspection, including with `--unpinned`.

Preserve the damaged copy and inspect a usable committed log before restoring content.

1. Keep a byte-for-byte backup of the damaged file at a chosen backup path.
2. Inspect the last usable step commit on the run branch with `git show <sha>:./<project-relative-log-path>` from the project root. The `:./` revision path supports projects below the Git root.
3. Compare the backup with the committed log and restore the affected content after inspection.
4. Retry the refused command and inspect `status` for a clean log.

The same procedure and publication contract apply under `context/changes/<id>/agent-smith/` and `openspec/changes/<id>/agent-smith/`.

## `/agent-smith:10x-pipeline <change-id> [goal] [--archive] [--chrome false] [--rigor <level>] [--pr-comment]`

Runs a 10xDevs change end to end: plan, plan review, implement, implementation review, fix. With `--archive` it also commits the change folder and archives the change when the run is done (see "Archive (opt-in)").

Requirements in the target project:

- The 10x toolkit skills: `10x-plan`, `10x-plan-review`, `10x-goal-implement`, `10x-impl-review`.
- A change folder made with `/10x-new <change-id>`.
- Node.js 24 or later (ADR-006). Claude Code does not guarantee a `node` on PATH (a native install is a single binary), so install it yourself. Churn risk also reads `git` history; without it the router flags no hot path. `--archive` needs a git work tree and the `10x-archive` skill.
- The `10x-research` and `10x-frame` skills are used when a pre-plan gate opens or when a `thorough` run loops (see "Pre-plan steps"). A step whose skill is missing fails three times and halts the run. A run that stays at `standard` or `lean` runs no such step and needs neither skill.
- The `score` step at `standard` and `thorough` needs no toolkit skill: its rules are in `skills/10x-pipeline/prompts/score.md` (see "Complexity score").

How routing works:

- `skills/10x-pipeline/policy.json` defines a ladder of model/effort tiers, a base tier per step, and escalation rules. Compatible Claude hosts can append two rungs with the [opt-in fable ladder](#opt-in-fable-ladder).
- `skills/10x-pipeline/scripts/route.mjs` reads `plan.md` (`## Progress`) and `reviews/*.md` (verdict, finding counts) after every step and returns the next step, model, effort and prompt. It stays a script: it makes no model or network call (ADR-006). The complexity score comes from a step it schedules (ADR-007).
- The tier goes up for large plans, `RETHINK`/`REVISE`/`REJECTED` verdicts (a `REVISE` or `NEEDS ATTENTION` counts when findings are still open) and failed attempts. It goes down after a clean review and for a simple change (a small plan or a short goal). A hard keyword in the goal, such as `refactor` or `security`, keeps the first plan at the plan step's base tier.
- In a run with its own worktree (see "Run isolation") the first attempt of an implement step (`implement`, `implement-segment`, `implement-tdd`, `implement-e2e`) runs one tier lower (`escalation.firstAttempt`), because a failed attempt is rolled back and retried. No drop applies when that step already failed in the run or the simple-change discount applies, and the clamp and the effort floor still bound it: a tdd or e2e step on the floor keeps its tier and `tierWhy` reads `-1 first attempt not applied (clamp or floor)`. An execution-sum score up shift cancels it the same way (`-1 first attempt not applied (cancelled by the score shift)`), and the step runs on the tier it would have without both. The entry carries `cheap: true` only when the drop survived the score shift, the clamp and the floor. Its failure raises no rigor and uses no step budget, but it counts as a failed attempt for the retry tier, `maxAttemptsPerStep` and the code re-plan, so the retry runs two tiers above it. The drop counts as a discount for the score down shift, so the two never stack. A failed cheap attempt is neutral only for rigor and the step budget, on purpose: the implementation review after it still runs one tier up, and for the rest of the run the simple-change discount is withheld and the score down shift is blocked, as after any failed step. `drop: 0` turns it off.
- The ladder has an `opus/medium` rung between `sonnet/high` and `opus/high`. A move up from `sonnet/high` reaches `opus/medium` first for a non-interactive step, such as implement or fix.
- Plan size adds one tier for every `complexity.phaseThresholds` entry reached by the phase count in `## Progress`, on steps named by `complexity.appliesTo`.
- A simple plan has at most `complexity.simple.maxPhases` (1) phase and `complexity.simple.maxRows` (6) Progress rows. Its discount is one tier on plan review, implement and implementation review. A step's `minTier` can absorb it. Any failed step withholds it, so the first retry of a discounted step rises two tiers, combining lost discount and failure escalation.
- Before implementation starts, a plan review `RETHINK` re-plans at +2, and a header-count `REVISE` with criticals or warnings above tolerance re-plans at +1. A noisy review (3 or more warnings) raises implement by one tier, and a clean `SOUND` lowers it by one. Decision-bearing reviews follow the open-findings rules below.
- Implementation review after retries or fixes runs one tier higher. `REJECTED` before a fix can re-plan once at the plan tier +1 when rigor and the extra-step pool allow. Otherwise it runs fix at the last code tier +1. `NEEDS ATTENTION` uses the last code tier, subject to the open-findings and header-count rules below.
- The first plan reads the goal text. A brief goal (at most 25 words, no hard keyword) lowers the plan tier by 2 and earns the simple-change discount. Any other goal lowers it by 2, and a goal with a hard keyword lowers it by nothing. The word limit and the keyword list sit under `complexity.firstPlan` in `policy.json` and can be overridden per project.
- Effort floor: plan, plan review and implementation review ask questions, so they never run below the floor in `rigor.minEffort` for the run's rigor level. The floor beats the simple-change discount, and the report marks a step as simple only when the discount survived. The floor also skips a rung whose own effort is below it, because the ladder is not ordered by effort: at `standard` and `thorough` such a step moves from `opus/medium` up to `opus/high`. A failed attempt of an interactive step moves it one rung up counting only the rungs that clear its floor, so a step that starts on `sonnet/high` runs `opus/high` on its second attempt and `opus/xhigh` on its third.
- Shared result intake persists completion before unlinking the result file. Recovery cleans a completed latest executed entry's surviving file before Git effects or routing. A pending latest entry keeps its own result ownership. See "State publication and log recovery".
- A step counts as failed when the subagent does not report `done` or the expected file did not change. Verification requires `plan.md` with `## Progress`, a freshly written review with a recognized verdict, or new checked Automated rows, with the code-commit check below for tdd/e2e. A result with the status `orchestrator-error` is the exception: it is no step result, and the router returns the same step again with no failed attempt (see "Neutral rerun after an orchestrator fault").
- On the 10x chain, `init`, `next` and `status --report` halt with `No change folder. Run /10x-new <id> first.` and write nothing (no `agent-smith/` folder, no start commit, no `report.md`) when `context/changes/<id>/change.md` is missing. `status` without `--report`, `risk`, `usage`, `verify-archive` and `compare` write nothing there either.
- Both reviews apply their own fixes (`prompts/plan-review-apply.md`, `prompts/impl-review-apply.md`): a finding with a clear fix is applied to `plan.md` (plan review) or to the code, tested and committed (implementation review) before the step ends, and marked `Decision: APPLIED` in the review file. Findings that need an owner decision stay `PENDING`. The `Verdict` and `Findings` header counts stay as measured before the edits, and the router now routes a `REVISE` or `NEEDS ATTENTION` on the findings that are still open (see "Review routing on open findings"). A review without `### F<n>` blocks that carry a `Decision` line is routed on the header counts, as before.
- The archive step is not moved by any of these rules: the policy pins its tier.
- From `standard` up the router runs one `score` step before the first plan, on a tier the policy pins. A subagent scores the change on six factors and writes `complexity.json`. The cognitive sum can move the first plan up one tier. The execution sum can move an implement step up or down one tier; a down shift needs measured churn risk with no hot path and a few more guards. A failed scorer is skipped after its attempts and never halts the run. See "Complexity score".
- At rigor `thorough` the router can run `research`, `domain-brief` and `frame` before the first plan. Before implementation starts, a plan review `RETHINK` or a repeated `REVISE` re-plan can send the run back to `frame` or `research` once before the re-plan. Both features are off below `thorough` by default. See "Pre-plan steps".
- From `standard` up the router can swap the plain implement step for a phase executor (`implement-e2e`, `implement-tdd`, `implement-segment`), and re-plan after code ran (`plan-replan` after two implement failures in a row, `plan-rejected` after a first `REJECTED` review). A tdd or e2e step also needs a code commit to count as done, and a step that ends `blocked` falls back with no failure counted. See "Phase executors".
- At every rigor level the router runs `manual-verify` before the first implementation review when a Manual row is pending: a subagent proves every pending Manual row it can, with evidence, and gives a reason for each row it cannot. It runs on `sonnet/medium` first and once more on `sonnet/high` when rows stay pending, outside the extra-step pool, and the run goes on whatever it leaves. See "Manual verification".
- The run halts for a human after repeated failures, too many plan revisions or fix loops, a review that leaves an open finding (see "Review routing on open findings"), or when the step budget is spent.
- `init --goal` takes the next argument as the goal whatever it starts with (`--goal "--verbose flag"` stores that text). `init` halts, and writes nothing, on words that belong to no flag, such as an unquoted goal: `Unexpected argument(s) after the flags: <words>. Quote the goal: --goal "<text>". Nothing was written.` A bare or empty `--goal` keeps the stored goal. Every flag of every command also reads `--key=value`, split at the first `=`: `--goal="fix the bug"`, `--rigor=standard`, `--chain=openspec`; `--goal=` is an empty goal. `init` halts, and writes nothing, on a flag it does not read (a typo such as `--gaol`, which would otherwise take the next word and start the run without a goal): `Unknown flag(s) for init: <flags>. init reads: --goal, --rigor, --archive, --chrome, --chain, --host, --pr-comment. Nothing was written.` An argument with no flag name (`--`, `--_`, `--=x`) is a leftover word and takes no value, so the halt names every word no flag claimed. The other commands still skip leftover words and unknown flags.

Run isolation:

- Each run works in its own linked Git worktree. Fresh setup concatenates `isolation.branchPrefix` and the change id for its branch, defaulting to `agent-smith/<change-id>`. `isolation.require` in `policy.json` ships `true`.
- Setup and publication share the router-compatible isolation projection, merging the shipped 10x policy, OpenSpec fragment and project override in that order. A missing prefix inherits the shipped default. With isolation active, an explicit prefix must be a non-blank string, and generated and recorded branch names must pass literal Git ref validation with option-like names rejected. A trailing slash is optional, so `runs-` is valid. Strict boolean opt-out precedes prefix validation.
- `init` halts, and writes nothing, when the project is not a git work tree, is the main checkout instead of a linked worktree, has a detached HEAD, is on a default branch (`isolation.defaultBranches`, plus the branch `origin/HEAD` points to) or on a branch that does not start with `isolation.branchPrefix` (default `agent-smith/`), or when git ignores a router file of the change. The halts for no git work tree and for the main checkout name the opt-out.
- The first `init` of a run stores `isolated: true` and `branch` in `meta.json`. The recorded branch remains authoritative, including before any executed entry. Setup and continuation validate the selected run against its id, chain, HEAD and active policy, with an absent saved chain interpreted as `10x`. A conflicting prefix refuses setup, init/resume, cleanup and publication with the recorded branch and guidance to restore `isolation.branchPrefix` and resume its worktree. A run that already has executed steps and was not started isolated halts at `init` and names the opt-out.
- Both skills run the shared standalone `skills/10x-pipeline/scripts/prepare-run.mjs <id> [--chain 10x|openspec]` from the original project root before `init`. It creates the worktree at `<project root>/.claude/worktrees/agent-smith-<change-id>`. The run root is that directory plus the project root's path below the repository top level, if any. Fresh creation validates the source directory before adding an exclude or creating a branch or worktree, then adds an anchored, prefix-aware local exclude when needed and reports uncommitted paths outside the selected change folder.
- Only when it creates the run branch does it copy the change folder into the worktree, preserving regular-file timestamps, modes and symlink targets through Node filesystem copying. A resume reuses the worktree, or adds one for the existing branch, and copies nothing, so edit the run's files in the worktree. An in-flight run in the main checkout stays there and halts at `init` until the project opts out. Both skills check the selected run root for change inputs after setup, allowing reuse and attachment when the original source folder is absent. Missing inputs use archive verification and new-change guidance from the selected root, with original-root fallback when setup cannot select one.
- Setup retains the ordered opt-out, already-in-run, in-flight main-checkout, fresh-creation, registered-reuse and existing-branch-attachment cases. Setup inside a linked run under the effective prefix preserves its actual branch. Resume paths preserve destination files. A shared exclusive lock for the resolved full branch in the Git common directory covers discovery through the complete fresh copy. An interrupted setup can leave a lock requiring inspection before manual removal.
- Saved identity in the invocation root takes precedence, followed by the already-in-run case and the exact configured branch and its registered worktree. When those paths select no run, fallback discovery matches the change id and normalized chain at the same nested-project prefix and Git common directory. Multiple matching saved runs refuse with candidate branches and roots, including baseline suffix branches. Resume from the intended worktree to select it. Registration order never selects an identity. Selected saved identity is revalidated under its branch lock and before setup returns success, including after original source cleanup or at custom registered locations.
- Runtime setup prints one JSON object and exits 0. `reason: null` and an absolute `runRoot` identify success. Failures carry a bounded `reason` and `runRoot: null`, retaining partial resources for inspection. Usage errors exit 2 with a diagnostic on stderr. Both skills stop before `init` on failed setup, nonzero exit or invalid JSON. `root` retains the invocation directory and `notInRun` lists repository-relative paths. Ordinary setup returns an empty `left` array. Post-init cleanup populates `left` with original-project-relative surviving paths.
- Every other input (the project override `context/foundation/agent-smith-policy.json`, `context/foundation/`, `context/domain/`, `context/map/`, the code) is read as committed at the branch point. Commit it before a run. The orchestrator prints one line that lists the uncommitted paths of the main checkout outside the change folder when it creates the branch.
- Every prompt of an isolated run starts with the rules of `skills/10x-pipeline/prompts/worktree.md`, which name the run root and tell the subagent to work only there. Reading an installed skill, plugin or tool file outside the run root, such as a `SKILL.md` in the home directory, is allowed; changing it is not. The orchestrator runs every router call with `cd` into the run root.
- After fresh setup with `case: created` and `copied: true`, both skills preserve its original JSON independently and send it verbatim on stdin to `prepare-run.mjs <id> --cleanup` from the original project root, adding `--chain openspec` for that chain. This runs once after successful `init` returns `run`, `done` or `archive`, before the first step launch, terminal reporting/PR handling or archive dispatch respectively, with the host timeout of 600000 ms. Resumes and halted initialization skip cleanup. A completed fresh 10x change can immediately return `done` or `archive` while still retaining its start commit.
- Cleanup validates distinct original/run roots, matching project prefixes, the registered branch/worktree and shared Git common directory under the setup lock. The original setup `branch`, effective policy and router-owned `meta.branch` must agree before unlinking. It requires an isolated run with a valid `meta.startCommit` reachable from the run branch. It lists the source entries, checks the complete list, individually unlinks only untracked regular files whose raw bytes equal regular-file blobs in that immutable commit, and prunes empty directories deepest first. A path in either the original HEAD or index is tracked. Edited, additional, unretained and unsupported entries, including symlinks, survive in `left`. Identity, tracking and bytes are rechecked before unlinking. External editors do not share the lock, so a filesystem race remains between final revalidation and unlink.
- Cleanup keeps the setup-result JSON shape. Runtime failures report a bounded `reason`, `runRoot: null` and surviving paths, including after partial pruning. Invalid arguments or stdin exit 2 before mutation. The skills validate cleanup JSON, report retained original paths or diagnostics and continue from the independently saved initialized run root. The final worktree message names the branch, root and any retained original paths. Repeating cleanup with the original fresh result is safe, and a later ordinary setup resumes the existing run after complete source removal.
- A run that ends `done` without `--archive` leaves `report.md`, the last `run.jsonl` entry and `meta.json` uncommitted after the router's last write. A successful leftover commit records them as `chore(<change-id>): final run state` before the push. If the commit is skipped or fails, preserve and commit those files locally before merging or removing the worktree. Resolve unfinished Git state in the run worktree before retrying publication or removing it. See "Pull request (always)".
- With `--pr-comment` the orchestrator posts from the run root, after the pull request step, to the pull request of the run branch (`--pr <url>`).
- Open question: `.claude` is a protected directory. Claude Code exempts "Claude's own git worktrees under `.claude/worktrees/`", and the docs do not say whether a worktree made by `git worktree add` counts. If it does not, Edit and Write under the worktree prompt even in `acceptEdits`, and an unattended run stalls there. A live run has not checked it yet.
- Opt out with `{ "isolation": { "require": false } }` in `context/foundation/agent-smith-policy.json`: no worktree, no `meta.isolated`, no start or step commit, no rollback and no cheaper first attempt; the run works in the project root as before. A project without git needs it. The router and the orchestrator read only the boolean `true` as on. The opt-out acts on a run that starts after it: a run that started isolated keeps `meta.isolated`, so when it resumes in its worktree the router still makes its step commits, rollbacks and cheaper first attempts there. Finish such a run before you opt out.
- Start commit: the first `init` of an isolated run records `meta.baseSha` (HEAD before the commit, so churn and the baseline procedure are unchanged), writes `meta.json`, then commits the change folder as `chore(<id>): start run` (`isolation.commit.startMessage`) and stores the hash in `meta.startCommit` (`null` when there was nothing to commit, or when the commit was made and git could not report its hash). The first step starts from that commit, so a rollback of the first step keeps `research.md`, `frame.md`, a ready `plan.md` and an edited `change.md`. A hook that rejects the commit halts `init`; the next `init` tries again. So does a halt of the checks after it when no commit was made (the change folder is still dirty after `git add`, for example a nested repository with untracked files): `meta.startCommit` stays absent until an `init` passes them. A resume never makes one.
- Step commits: after each verified successful step the router commits what the step left as `chore(<id>): step <n> <step>` (`isolation.commit.message`), before it reads any file for the next decision. Nothing to commit gives no commit. The log entry records `startSha` (HEAD when the step started, read with `isolation.gitTimeoutMs`; a HEAD that cannot be read halts the run before the step is logged) and `commit`; `report.md` shows `ok (<short hash>)` and `status` shows `commit`. Before the commit the router reads the staged names (`git diff --cached --name-only --no-renames -z`, so both sides of a move) and keeps those outside the change folder, sorted, as `swept` on the entry, only when there are any (ADR-010 Amendment 1). The commit still carries the `chore` subject, which release-please hides, so `swept` names the code that went in under it: `status` shows it, and `report.md` has a header line `Code under chore commits: ...` and a `## Code committed by the router` section. A failed name read halts like a failed add, with nothing committed. A pre-commit hook that stages more files is not seen. Hooks and signing apply; the router never passes `--no-verify` and never pushes. A staged file left by the step, or a hook failure, halts the run with git's message, and the router unstages its own add.
- Bash limit: the skills run every `route.mjs`, `open-pr.mjs` and `pr-comment.mjs` call with the Bash tool's `timeout: 600000`, its maximum. The shipped `isolation.gitTimeoutMs` and `archive.gitTimeoutMs` are 120000 ms each, applied per git call, so with the Bash default of 120000 ms the router's own git timeout would not fire first and the Bash tool would kill the router inside `git commit` before it unstages its own add (`routerCommit`). The rule: the one git call that runs hooks (`git commit`) is bounded by its key, and that key plus the other git calls of the router call (safety reads, add, staged-name reads, post-commit checks) must fit in the Bash limit. Those other calls run no hook and are normally fast, so with the shipped 120000 ms the sum stays far under 600000 ms. The worst case, where every git call of one router call hangs for its full timeout, can exceed 600000 ms; it needs git itself to hang (a lock on a network mount, a stalled filesystem), not a slow hook, and the shipped values do not guard against it. A project whose hooks run longer than 120 s raises both keys in `context/foundation/agent-smith-policy.json` and keeps the raised key plus the other git calls of one router call under 600000 ms; raising a key is the only direction that helps, the shipped values are not lowered. `open-pr.mjs` pushes and commits with a fixed 120000 ms (`GIT_TIMEOUT_MS`, no override); `pr-comment.mjs` runs only `gh` calls, bounded by `--timeout-ms` (default 20000), no git. A Bash kill inside `git commit` leaves the router's `git add` staged, and the next `next` halts in the staged-index check without naming the cause; check with `git diff --cached --name-only`. Both chains share this bullet; the OpenSpec section inherits what it does not name.
- Rollback: after a failed step the router snapshots the worktree, staged and untracked files included, as a commit under `refs/agent-smith/<id>/<run>/failed-<n>` (`isolation.rollback.ref`, which must render under `refs/agent-smith/`; `<run>` is the first 12 hex characters of the run's start commit, `meta.startCommit` or, when that was empty, the first step's `startSha`, so two runs of one change id, such as the baseline arms, never share a ref; plumbing, so no hook runs), resets the worktree to the step's `startSha` with `git reset --hard` (no `git clean`, so ignored files stay), sets back the file times of `plan.md` and the two review files, and only then decides the next step. The retry, a `plan-replan` or any other next step starts from `startSha`, and the entry gets `rolledBack`. Commits the failed step made itself, such as the phase commits of `/10x-goal-implement`, leave the branch with the reset and stay reachable from the side ref, whose first parent is the head the step left; the retry redoes them. Uncommitted edits present when the step started (a human's edits after a halt, what a fallback step left) are swept into the side ref too, so commit them before you resume. The router publishes the original index as a commit under the same recovery ref before staging working files. The final snapshot's second parent holds that index, so different staged and working versions both survive. A retry keeps any interrupted snapshot in its ancestry. Inspect the working snapshot with `git show <ref>:<path>` and the staged version with `git show <ref>^2:<path>` (the entry's `rolledBack` or `kept` value); the first parent remains the undo target. A final snapshot is a merge commit, so cherry-picking its working diff requires `-m 1`.
- Not rolled back: a `blocked` fallback step, a failed `score` attempt, a tdd or e2e step whose rows are listed as `uncommitted` (the `implement-retry` step needs those ticks and that code) and a step whose result carries `signals.needsHuman`. When the call that rolled back ends in a halt (budget, the attempt cap, a `decide` halt, a `Router error:`), the router undoes the reset first: the branch is back at the head the failed step left, the worktree holds the partial edits with their file times, and the entry gets `kept`. A kept or rolled-back step is never rolled back again. `report.md` lists both under `## Rolled-back steps`, a kept one as `kept (run halted)`.
- Interrupted timestamp restoration: after a rollback or undo finishes its Git resets, the router writes the restored metadata, then atomically publishes the log with the recovery ref and a pending timestamp checkpoint. The checkpoint pins the checkout commit and fingerprints the bytes Git checked out. Under the run lock, `init` resume and `next` restore matching files' timestamps before taking another result or routing, even if HEAD has advanced. Recovery preserves edits with different contents and treats a timestamp-only change as ambiguous. A redirected, unreadable or otherwise unverifiable target halts with its path and recovery ref. If a matching file has multiple hard links, recovery halts to protect the shared inode. Fix the cause and resume in the same run worktree. Recovery finishes the recorded direction without another reset or undo, and records completion in the log. Finish pending checkpoints before downgrading the router.
- Checkout comparison for legacy entries or targets without a fingerprint uses Git 2.40 or later to inspect the pinned attributes. If the comparison needs pinned `ident` or `working-tree-encoding` conversion, it uses Git 2.41 or later. A Git error or custom filter leaves the comparison unproved.
- An interruption before the checkpoint is published requires recovery-ref inspection. Find the failed step's ref under `refs/agent-smith/<id>/<run>/` and inspect `git show <ref>:<path>` for working files and `git show <ref>^2:<path>` for staged files. The consumed result is in the snapshot's `context/changes/<id>/agent-smith/run.jsonl` or `openspec/changes/<id>/agent-smith/run.jsonl`, with any nested project prefix relative to the Git root. Use the snapshot and current worktree to reconcile the interrupted run before retrying.
- Co-author: every commit the router makes (the start commit, step commits, the rollback snapshot, the pre-archive commit and the late-usage commit) and the leftover commit of `open-pr.mjs` end with the trailer `Co-Authored-By: Agent Smith <agent-smith@ksycki.pl>`, from the policy key `coAuthor: { "name", "email" }` (ADR-021). The subject stays as it was. Set `{ "coAuthor": null }` in `context/foundation/agent-smith-policy.json` to turn it off. A malformed value (not an object, or a `name` or `email` that is blank or holds a newline, `<` or `>`) halts the first router commit it would apply to, before anything is staged, with a reason that starts `policy.coAuthor`; `usage` refuses it before it writes; read-only commands such as `status` never read it, and `open-pr.mjs` then commits with no trailer. Commits made inside step subagents (plan, implement, fix) are made by Claude and are not changed. `coAuthor` is in `provenance.ignore`, so it changes no hash. The trailer uses `git commit --trailer`, which needs git 2.32 or later.
- The router never resets, commits in or writes refs from the main checkout: the step commit and the rollback check that the run is in a linked worktree with HEAD on `meta.branch`, and halt otherwise. It never deletes the run branch, the worktree or a side ref.
- `isolation` is a policy section, so provenance hashes it and `compare` warns when two arms differ in it.
- Release note: `isolation.require` ships `true`, so a run in the main checkout now halts at `init` until it runs in a worktree or the project opts out. It shipped as a breaking change (`feat!`). The rules are in ADR-010.

Pull request (always):

- At every end of a run (`done`, `archive` and `halt`) the orchestrator runs `skills/10x-pipeline/scripts/open-pr.mjs <change-id>` from the run root, before the PR comment step and before any STOP, with `--chain openspec` for the OpenSpec chain. No flag turns it off. The rules are in ADR-017. The router never runs it, never pushes and never calls `gh`.
- Guards require a Git work tree, a linked worktree (`git rev-parse --git-dir` differs from `--git-common-dir`), attached HEAD and active isolation. Effective policy validates the prefix and branch, protecting configured defaults, `origin/HEAD` and the selected remote default. Saved identity from the requested chain or the `--report` change directory must match the change id, normalized chain, isolated flag and HEAD. Missing or legacy empty metadata requires the exact configured prefix plus id. Malformed, partial or contradictory identity refuses with `run is not isolated: ...` before leftover commits, push or GitHub calls. A detached HEAD, including during a rebase, takes this earlier refusal with null commit fields and requires returning to the validated run branch before retrying. `isolation.require: false` skips before prefix validation and is the opt-out retained by ADR-017.
- Base: `--base <branch>`, else the nearest remote branch the run descends from (among `refs/remotes/<remote>/*` without `<remote>/HEAD`, the run branch's own remote ref and branches under either the effective prefix or the legacy `agent-smith/` namespace, the ancestor of HEAD with the fewest commits up to HEAD, ties to the branch `<remote>/HEAD` points to; one `git for-each-ref --merged HEAD` call finds and counts them, and a git older than 2.41 without `%(ahead-behind)` counts with one `rev-list` per ancestor), else the branch `<remote>/HEAD` points to, else `gh repo view`, else a skip. A run branched from a pushed feature branch therefore gets that branch as base, and its pull request does not carry the feature branch's commits. No commit beyond the base skips with `no commits on the run branch` and commits nothing. Every automatic candidate, including remote-default and GitHub-default fallbacks, must pass literal branch validation and these run-namespace exclusions.
- Before the leftover commit, the shared router guard checks worktree-local merge, rebase, cherry-pick, revert and sequencer markers and searches the entire index for unmerged entries. An operation marker, unmerged entry or failed probe skips the commit before status or staging. The working files, index, operation state and local HEAD stay intact. CLI JSON reports `committed: false`, the reason in `commitError` and null `commit` and `swept`. The script still attempts the ordinary non-force push of existing commits and proceeds to PR handling after a successful push.
- With the guard satisfied, a nonempty `git status --porcelain` triggers `git add -A` and `git commit -m "chore(<change-id>): final run state"`, with hooks and signing. A successful commit sweeps unignored files, including `evidence/`. The script lists its files (`git show --name-only --no-renames -z --format= HEAD`) and returns those outside the change folder as `swept`. A failed `git add` or commit unstages the paths its own add staged (`git reset -q` on those paths, read from `git status --porcelain` before the add). An entry staged before the script ran stays staged if its working copy was unchanged. A path edited again after staging goes back to its committed state in the index. The script reports `committed: false` with `commitError` and still attempts to push the existing commits.
- Push: `git push <remote> refs/heads/<branch>:refs/heads/<branch>` (`--remote`, default `origin`). A rejected push (a diverged remote branch, no access) gives `pushed: false` with git's first line; the script never retries with force.
- Pull request: `gh pr list --repo <owner>/<repo> --head <branch> --state all`. An open pull request is `existing` (the push updated it, its body is left as it is). A merged or closed one is `skipped` with its state and nothing is created. None gives `gh pr create --repo <owner>/<repo> --head <branch> --base <base> --title <title> --body-file <tmp>` (`--draft` only with the flag): the title is `<type>(<change-id>): <title>`, with `<title>` the `title:` of `change.md`, else the id, and `<type>` the highest-ranked Conventional Commit type of the subjects in `<base>..HEAD` (`chore` when none parses; `!` only from the highest-ranked subject), cut to 256 characters, untyped if `git log` fails, set once at creation (ADR-017, Amendment 1); the body is a hidden marker `<!-- agent-smith:pr change=<change-id> -->` and the report lines before its first table row, with `@mentions` neutralized and a cap of 60000 code units. `<owner>/<repo>` comes from `git remote get-url <remote>`; a remote that is not on `github.com` is a pull request skip after the push. A missing, unauthenticated or timed-out `gh` is a pull request skip with `pushed: true`.
- Output: one JSON object `{ pushed, committed, commit, commitError, swept, branch, remote, base, pr: { action, url, state, reason }, reason, manual }`, exit 0 for every runtime outcome and 2 for a usage error. `swept` is `null` when no leftover commit was made or the list could not be read, else a sorted array (empty when the commit held only the change folder). The orchestrator prints `Pull request: <action>, <url or reason> (branch <branch>, pushed <true|false>)`, and when `pushed` is `false` also `Pull request: NOT pushed, <reason>. Branch <branch> is local only: <manual>`. Reporting uses publication `branch`, then saved setup `branch`, then explicit `unavailable` when both lack identity, including script-error paths. A failure never changes the outcome of the run and is never retried.
- Recovery commands quote each dynamic argument as a shell literal, including worktree path, remote, complete push refspec, repository, branch and base. Runtime Git and GitHub execution uses argument arrays.
- Cleanup: an error while removing the temporary folder of the pull request body never changes the printed result (shared `withTempDir` of `pr-common.mjs`, also used by `pr-comment.mjs`).
- Timeout: `open-pr.mjs` and `pr-comment.mjs` take `--timeout-ms <n>`, a positive integer in milliseconds for each `gh` call; git calls keep their own limit; the default is 20000 (`DEFAULT_TIMEOUT_MS` in `pr-common.mjs`), and any other value is a usage error.
- In `archive` the step runs after `verify-archive`, whatever it reports, so the `chore(archive)` commit is pushed; on `archived: true` it gets `--report "<archivePath>/agent-smith/report.md"`.
- Never: `--force`, `-f`, `--force-with-lease`, `-u` or `--set-upstream` (no git config write), `--no-verify`, `--amend`, a rebase, `gh pr merge`, `gh pr review`, `git branch -d`/`-D`, `git worktree remove` or `git push --delete`. The side refs under `refs/agent-smith/` are not pushed.
- A resumed run starts from its current branch HEAD. If publication made a leftover commit, that commit records the halted step's kept partial edits. A later rollback resets to its step's `startSha`, at or after the pushed head, preserving the pushed history and those committed edits. If the guard skipped the leftover commit, resolve the Git state and commit any kept edits and run artifacts you want included before resuming.
- Unverified live: `gh pr list --head` and `gh pr create --head` on a branch without upstream config behave as the tests' fake `gh` simulates; a live run has not checked it yet.

Review routing on open findings:

- Plan reviews accept `SOUND`, `REVISE` and `RETHINK`. Implementation reviews accept `APPROVED`, `NEEDS ATTENTION` and `REJECTED`. Write one standalone `**Verdict**:` or `**Verdict:**` line in the opening metadata before the first level-two or deeper heading, code fence or preformatted HTML block. Both forms can be bare or in a Markdown bullet. Labels inside comments, blockquotes or code spans are ignored. The verdict is case-insensitive and can follow an emoji. It can be wrapped in square brackets or take a terminal period, a whitespace-prefixed complete parenthetical annotation or a spaced hyphen followed by annotation text. Use the listed spellings, including the space in `NEEDS ATTENTION`.
- A review step fails verification if the artifact is missing, unreadable, stale or has no recognized verdict. `status` shows the diagnostic in `invalid`. An ordinary attempt can retry under the existing caps, and a halt at either cap includes the diagnostic. A confirmation with an invalid artifact halts and preserves the failed step's edits for inspection. An existing review selected for routing with an invalid verdict halts with the path, the problem and the accepted values. When no invalid attempt is recorded for the current plan or code, an absent or stale review can prompt a new review and an applicable plan-review skip still counts as handled.
- To resume after a verdict halt, resolve any findings and save the review with a recognized verdict. The corrected artifact must have a new modification time after the failed attempt started. In isolation, commit the edit in the run worktree so later rollback can preserve it. The failed attempt stays in the log, and a corrected review goes through the ordinary findings and confirmation gates. Older failed review entries can record only `verified: false` and `ok: false`. They use the same recovery checks. For a legacy rollback or undo without a timestamp marker, the router also compares the review with the checkout source. Matching contents, including line-ending-only differences, and unverifiable checkout contents leave the review's freshness unproved.
- The `Findings` line accepts both `**Findings**:` and `**Findings:**`. The router reads each `### F<n>` block of a review file: its `**Severity**` line (CRITICAL, WARNING or OBSERVATION; a line that names none counts as a warning) and its `**Decision**` line. The decision is the first run of ASCII letters after `**Decision**:`, upper-cased, so `APPLIED - abc1234` reads `APPLIED` and `ACCEPTED-AS-RULE: <title>` reads `ACCEPTED`. A finding is closed when its decision is in `review.openFindings.closedDecisions` (default `APPLIED`, `FIXED`, `ACCEPTED`, `SKIPPED`, `DISMISSED`; `FIXED` is the word the review skills' own triage writes). A missing, `PENDING` or unknown decision is open, and an observation never counts. A header count above the CRITICAL or WARNING blocks the file lists adds the difference as open, so a review that lists fewer blocks than its header claims is never read as cleaner than it says.
- A review is "aware" when `review.openFindings.enabled` is `true` (the default) and at least one block has a `Decision` line. An aware plan review `REVISE` with no open critical and open warnings within `review.reviseToleranceWarnings` goes on to implement. Any other open count halts the run for a human with the open finding ids. Before implementation starts, `RETHINK` or a `REVISE` over tolerance follows the applicable re-plan or halt rule. Once an Automated row is ticked or an `implement` or `fix` step has run, either blocking verdict halts if any Automated row is unchecked or would be reopened for retry.
- An aware implementation review `NEEDS ATTENTION` with no open critical and open warnings within the same tolerance goes to `done` with no `fix` step. Any other open count halts. `review.fixOnNeedsAttention` applies only to a review without `Decision` lines. `REJECTED` keeps its routing. `review.reviseToleranceWarnings` therefore bounds the open warnings of both reviews (before, it bounded the plan review only), and the tolerated open warnings stay visible in `## Review findings` of the report.
- `review.openFindings.onOpen` is `"halt"` (default) or `"retry"`. With `"retry"` an aware `REVISE` above the tolerance re-plans before implementation starts. An aware `NEEDS ATTENTION` above the tolerance runs `fix`. It brings back neither a re-plan for a `REVISE` with nothing open nor a `fix` for a `NEEDS ATTENTION` with nothing open or open warnings within the tolerance. `review.openFindings.enabled: false` is the full opt-out: every review routes on the header counts. A value of the wrong shape (`openFindings` not an object, `closedDecisions` not an array of non-blank strings, `onOpen` other than `halt` or `retry`) reads as the shipped default, a non-boolean `enabled` reads as off, and none of them halts the run.
- Fallback: a review with no `Decision` line in any block (a project that overrides a review prompt with a plain string, or a review written by hand) routes on the measured header counts under the verdict and remaining-work gates above.
- A `REVISE` that carries `Decision` lines never re-plans under the default `halt`. The `preplan.loops` REVISE-to-research loop and `limits.maxPlanRevisions` therefore act on a `REVISE` only for a review without `Decision` lines, or with `onOpen: "retry"`. `RETHINK` can reach both before implementation starts.
- Halt text and the way back in: `Plan review REVISE left <n> open critical and <m> open warnings (F1, F3). Needs a human.` (or `Implementation review NEEDS ATTENTION ...`), then `Set each finding's Decision in <review path> (<closed words>) or triage with /10x-plan-review <review path>, then run /agent-smith:10x-pipeline <change-id> again.` (`/10x-impl-review` for the implementation review). Findings counted in the header with no block are named as a count. In an isolated run the text ends with `Commit the edit in the run worktree first: a failed step rolls back uncommitted edits.`, because the next failed step resets the worktree to its `startSha` and would restore the open lines. After the edit, run that command.
- Confirmation round (`review.confirmRounds`, per rigor level, `0` everywhere by default, so off): after an aware plan review `REVISE` or implementation review `NEEDS ATTENTION` that applied at least one CRITICAL or WARNING fix (`APPLIED` or `FIXED`) and left nothing open, the router returns one more review of the same kind (same step name, template `plan-review-confirm` or `impl-review-confirm`) before it goes on. The confirm prompt tells the subagent to read the earlier round, review the current plan or code in full and check every `APPLIED` fix as a claim. The confirmation is routed by the same open-findings rule: an open finding halts (or retries), and one that again applied fixes and left nothing open schedules the next confirmation only while fewer than the level's count ran. The cap counts every executed confirmation of that kind, failed ones included. A plan review confirms only before implementation starts. `RETHINK`, `REJECTED`, a review without `Decision` lines and a level with `0` or a malformed value never confirm.
- Budget cost of a confirmation round: each round is one more `plan-review` and one more `impl-review` step on the longest path. `rigor.budgetDelta` ships sized for the path without the round, so a project that turns it on raises `rigor.budgetDelta` by 2 per round at each level that turns it on, for example `{ "review": { "confirmRounds": { "standard": 1 } }, "rigor": { "budgetDelta": { "standard": 7 } } }` for the shipped `5`. Without it the budget can halt a run that has a failed step to retry.
- The log entry of a verified review step carries `review`: `{ verdict, critical, warnings }` (measured, from the header) plus `openCritical` and `openWarnings` for an aware review. `status` shows it per row, and `report.md` lists it under `## Review findings` (see "Usage report").
- Upgrade note: the policy gains keys and the two apply prompts and the two confirm templates change, so a run in flight when the plugin is upgraded records `provenance.drift` for `review` and `prompts` at its next `next` call, and `compare` warns `provenance-drift:<side>:prompts,review`. That is expected and changes no routing. A review with `Decision` lines that a run in flight already holds is routed on its open findings from its next `next` call.
- Behaviour change for the release PR: a `REVISE` or `NEEDS ATTENTION` whose findings are all closed now continues instead of re-planning or running `fix`, and an open finding now halts instead of re-planning. `onOpen: "retry"` restores the old reaction to open findings. Whether it ships as `feat` or `feat!` is the owner's call at commit time. The rules are in ADR-011.

Rigor:

- Every run has a rigor level, `lean`, `standard` or `thorough`, stored in `meta.json` and kept on resume. It starts from the goal class (a short goal is `lean`) or from `init <id> --rigor <level>`, and it only rises: with 3 or more phases (`standard`) or 6 or more (`thorough`), after failed steps (a failed cheap first attempt does not count), when the plan or the diff touches a hot path, and when a subagent result carries `signals.rigor`.
- The rigor thresholds are configurable through `rigor.fromPhases` and `rigor.fromFailures`. A hot path prevents the lowest rigor. Missing, too-short or unreadable history records risk as unmeasured and flags no path. At the lowest rigor, `rigor.tierOffset` also lowers implementation review one tier, subject to its effort floor.
- Hot paths come from churn: paths that change often in the repository history, counted up to the commit the run started from (`meta.baseSha`). The parameters sit under `risk` in `policy.json` and are uncalibrated. `node skills/10x-pipeline/scripts/route.mjs risk <change-id>` prints the hot paths, the plan hits and the diff hits and writes nothing.
- At `lean` the router skips plan review before implementation starts, if risk was measured (history readable, the plan names at least one path, and every named path can be matched against the hot set: a file, a directory, a glob or an absolute path under the project root) and no named path is hot. The skip is logged in `run.jsonl` with its reason and listed in `report.md`. If risk could not be measured, plan review runs. Implementation review is never skipped.
- The step budget is `limits.maxTotalSteps` plus a delta per level (`rigor.budgetDelta`: -2, +5 and +10, so 12, 19 and 24 steps). Skipped steps use no budget, and failed `score` attempts use none either. See "Budget" below for the longest path each level is sized for.
- A subagent can end its `RESULT:` line with an optional `signals` object. The router keeps three keys: `rigor` (raises the level; dropped from a `score` result, because the score only advises), `needsHuman` (halts the run once with a report) and `lessonCandidates` (an `impl-review` result only; see "Lesson candidates"). It ignores the rest.
- Prompt rules follow the GIVEN/WHEN/THEN form with one bold RFC 2119 keyword (ADR-004). `node --test skills/10x-pipeline/test/*.test.mjs` checks the form and the router behavior.

Archive (opt-in):

- A 10x run that ends `done` without `--archive` prints `changeStatus`: the `status` of `change.md` at that call, or `null` when it cannot be read. The router never writes `change.md`. `archive`, `halt`, `meta.json`, `report.md` and the OpenSpec chain carry none; the 10x skill uses it in its `done` branch to tell the user the change is still open.
- `init <id> --archive` stores `archive: true` in `meta.json`; a resume keeps it and `--archive false` turns it off. Without the flag the router makes no pre-archive commit: `done` stays `done`. A run that is not isolated then writes nothing to git and only reads history, for churn risk; an isolated run also makes the start and step commits and the rollback of "Run isolation".
- `init --archive` halts, and writes nothing, when the project is not a git work tree or git ignores any of `agent-smith/run.jsonl`, `agent-smith/meta.json`, `agent-smith/report.md` or `change.md` of the change. The same checks run again at `done`.
- At `done`, the router checks the git state first. It halts for a detached HEAD, an unfinished Git operation, unmerged index entries, a failed safety probe or staged changes. A missing `created: YYYY-MM-DD` line in `change.md` or an existing `context/archive/<created>-<id>` also halts the archive. With `archive.haltOnManualPending` set to `true` it also halts when Manual rows are pending. The default is `false`.
- Then it writes the final `report.md`, commits `context/changes/<id>/` as `chore(<id>): commit change folder before archive` (`archive.commitMessage` in the policy), and returns an `archive` action. The commit is skipped when it would be empty.
- Three checks follow the commit, because a hook can stage or write other files: the index is empty, the commit touched only the change folder, and the folder is clean. A failed `git add` or `git commit` halts with git's message and unstages the router's own add. Hooks and signing apply; the router never skips them and never pushes.
- The commit lands on the current branch. Protected branches such as `main` are not detected.
- Every file in the change folder that git does not ignore is committed, editor junk such as `.DS_Store` included. Ignored files outside the four files above are not committed. The `archive` action lists them (at most ten) and the final message shows them as "not committed (ignored by git)"; they still move with the folder.
- Manual gate (ADR-014): when the `archive` action has `summary.manualPending` rows, or ticks nobody proved (`summary.manualUnproven`, `summary.uncommittedTicks`), the orchestrator, after it reports the run and before the move (the PR comment now follows the move, ADR-017), asks one question through the host's native question capability (`AskUserQuestion` under Claude, an available native Codex question tool under Codex, header `Archive`; options `No, keep it unarchived`, recommended, and `Yes, archive anyway`) that lists at most 10 pending rows, each non-empty unproved list and the `manualNotProved` lines. Only a yes continues. Any other answer, an error or no question tool (headless `claude -p`) fails closed: no archive subagent, no `verify-archive`, the line `Archive: skipped, <n> Manual check(s) pending or unproved.` (`<n>` counts the distinct row ids across the three lists) and a final message that the change is committed on the run branch but not archived, with the checklist and `/10x-archive <id>`. Running the pipeline command again asks again. `report.md` keeps its stale `Archive: requested` line, and the pre-archive commit stays. No pending rows and no unproved ticks, no question. The router does not change.
- The orchestrator then runs `/10x-archive <id>` in one subagent. Its prompt gives the answers to the skill's questions as rules: continue past warnings, archive without repointing, never ask. A blocking warning, such as missing review coverage, ends the step as `blocked`.
- `route.mjs verify-archive <id> [--path <p>]` confirms the move from files alone: the archive folder has `status: archived` in its `change.md` and `context/changes/<id>/` is gone. It does not call git, so check `git status` afterwards. `--path` names the exact folder (`context/archive/<date>-<id>`); the orchestrator passes the `archivePath` of the `archive` action. When an id was archived more than once and no `--path` is given, the answer is `archived: false` with an `ambiguous` list of the folders. `archivedAt` is a string, or `null` when the field is absent or `null`.
- A usage figure that reaches the orchestrator after the router returned the `archive` action is attached before the archive subagent starts: `route.mjs usage` commits the change folder again as `chore(<id>): add late usage figure of step <n>` (`archive.usageMessage`), so the folder is clean when `/10x-archive` runs. In an isolated run, running `next` again resumes with `commit: null`. See "Late usage figure".
- The shared `guardArchived` check makes `init`, `next` and `status --report` halt without writes when the live folder is gone and an archive exists, or when the live 10x `change.md` is stamped `status: archived`. An additional init-only check rejects a live folder beside matching archives in the resolved chain before acquiring the run lock, naming the live path and every matching archive. Argument and chain validation still apply. Other live-folder commands keep their existing behavior.
- `report.md` carries `Archive: requested - runs after this report was written`. Pending Manual rows are listed there as `Manual checks pending: N`, and, after a `manual-verify` step, with their reasons as `Manual checks not proved: N`, because this report is the only router file that survives the move. The archive step has no log entry, no usage figure and no report row, so the totals cover the steps before it.
- A halt is never archived. A halt printed by the `done` branch or by the end of the run carries `archive: "skipped: ..."` and `committed`. `committed: false` means nothing was committed: the folder is uncommitted and `/10x-archive` needs a commit first. `committed: true` means the pre-archive commit exists locally and the router did not undo it; `next` repeats the checks safely after the cause is fixed, without a second commit. On that repeat the check that the commit touched only the change folder is skipped, because no new commit is made. A halt of the commit step, after `report.md` was written, also carries `report`, so `--pr-comment` can post it; the pre-check halts and the halt for a `report.md` that could not be written carry none. Halts printed elsewhere carry neither field: a missing result file, a guard halt for an archived change, usage and flag errors, errors at `init` and `Router error:`.

Pre-plan steps:

- Three optional steps can run before the first `plan` step, in this order, and two loops can send a run back after plan review. Both sit under `preplan` in `policy.json`. Every gate and both loops default to rigor `thorough`. Their word lists and thresholds are uncalibrated: no run data exists yet.
- Pre-plan steps open only for a run that starts at `thorough`, for example `init <id> --rigor thorough`. They are decided once, before the first plan attempt. Every other way to reach `thorough` (a `signals.rigor` in a step result, a plan of 6 or more phases, three failed steps, three hot paths) needs a plan or a finished step first, so a later rise does not open them.
- The loops read the run's current level. Before implementation starts, a standard run that rises to `thorough` can reach the frame round on its next `RETHINK`, including when the plan already has 6 or more phases. At `standard` or `lean`, `RETHINK` and `REVISE` follow the review routing above without a frame or research round.
- A gate closed by the rigor level is silent. A gate that is open and does not run logs a skip with its reason, in `run.jsonl`, `status` and `report.md`. All three steps can skip in one call.

| Step | Opens at | Runs when | Skipped when | Template |
| --- | --- | --- | --- | --- |
| `research` | `thorough` | always | `research.md` exists | `research`, or `research-with-map` when `context/map/repo-map.md` has `artifact: repo-map` in its frontmatter |
| `domain-brief` | `thorough` | `aggregateGap` or `dependencyLeak` hits | a brief file exists (`refactor-invariant-aggregate.md` or `refactor-anti-corruption-layer.md`), or no signal | `domain-aggregate` when `aggregateGap` hits (it wins), else `domain-acl` |
| `frame` | `thorough` | `framingDoubt` hits | `frame.md` exists, or no signal | `frame` |

`frame` is pinned to one tier by `steps.frame` in the policy. Each step is verified by the file it writes: `research.md` needs `status` frontmatter, `frame.md` needs a `## Reframed` heading (the Confidence label is never read), and a brief needs `type: refactor-plan`. The file must also be newer than the step start. A failed attempt retries at the next tier and halts after three. The plan prompt lists the upstream artifacts that exist, so `/10x-plan` reads them.

| Predicate | What it reads | Default |
| --- | --- | --- |
| `framingDoubt` | the goal, lowercased; a phrase matches where it starts at a word start. Or a `signals.rigor` on an earlier `research` or `domain-brief` result, whatever valid level it names (the key says the change is riskier than the goal suggested) | `root cause`, `should we even`, `is this the right`, `challenge the assumption`, `rethink`, `before i plan`, `caused by`, `because`, `assuming` |
| `dependencyLeak` | the goal, same matching | `vendor`, `sdk`, `third-party`, `third party`, `wrapper`, `adapter`, `leak`, `anti-corruption`, `swap out`, `external api` |
| `aggregateGap` | the first existing of `context/domain/domain-distillation.md` and `context/domain/01-domain-distillation.md`, section `## Invariants and policies` up to the next `## ` line | rows with status `declared`, `ignored` or `contradicted` |
| `repoMapExists`, `researchExists`, `frameExists`, `briefExists` | a file in the project or the change folder | n/a |

- The skill's own triggers `fix`, `bug` and `broken` are left out of `framingDoubt` on purpose: they would open a frame step for `fix typo`. To add them, override `preplan.predicates.framingDoubt.goalWords` in `context/foundation/agent-smith-policy.json`. Arrays are replaced whole, so repeat the defaults:

```json
{ "preplan": { "predicates": { "framingDoubt": { "goalWords": ["root cause", "should we even", "is this the right", "challenge the assumption", "rethink", "before i plan", "caused by", "because", "assuming", "fix", "bug", "broken"] } } } }
```

- `aggregateGap` reads every pipe table in that section whose header has a cell starting with `invariant` or `policy` and a `status` cell. The status of a row is the first alphabetic word of the cell, without `*`, `_` and backticks (`**declared** (soft)` reads as `declared`). A row hits when a status in the list shares a whole word with the goal. The words come from the `candidate` column (when present), the invariant or policy cell and the `gap` cell, as lowercase letter tokens of at least 4 letters that are not in `preplan.predicates.aggregateGap.stopwords`. A `###` heading is not a word source, and lists such as "Code-only rules" are not read. No file, no section or no matching row is no hit.
- `frame` runs unattended under a decision guide (`skills/10x-pipeline/prompts/frame-unattended.md`). A goal that names a task but no separate cause is confirmed as the problem statement and the run goes on. A `signals.needsHuman` in the result halts the run, whatever `frame.md` says.

Plan review loops before implementation starts (`preplan.loops.minRigor`, default `thorough`):

- At or above `loops.minRigor`, a plan review `RETHINK` runs `frame` once (template `frame-rethink`), then re-plans. A second `RETHINK` after that re-plan halts for a human.
- At or above it, a `REVISE` that needs a re-plan, after one earlier `REVISE` re-plan, runs `research` once (template `research-revise`), then re-plans. A `REVISE` whose review has `Decision` lines needs a re-plan only under `review.openFindings.onOpen: "retry"`; under the default `halt` it halts instead, so this loop sees only a review without `Decision` lines or a `retry` run (see "Review routing on open findings").
- A failed re-plan keeps spending a revision, as before, so `limits.maxPlanRevisions` still ends the run. Under the default `halt` a `REVISE` with `Decision` lines never reaches it, only a `RETHINK`, a review without `Decision` lines or a `retry` run. `loops.rethinkToFrame`, `loops.reviseResearchAfter` and `loops.reviseResearchMax` set the counts; a value that is not a positive integer turns that loop off.
- Below `loops.minRigor`, `RETHINK` and `REVISE` re-plan exactly as without these loops.

Budget:

- The steps count against the step budget; skips do not. The budgets are 12 (`lean`), 19 (`standard`) and 24 (`thorough`). The longest failure-free path with every feature in play is 10 steps at `lean`, 17 at `standard` and 22 at `thorough`, so one failed step and its retry still fit and a second failure can end the run with the budget spent. Each path holds a `manual-verify` attempt and its retry, which are outside the extra-step pool.
- The budget halts only a run that still has a step to run. `next` asks `decide` first: a run that is complete at the budget ends `done` (and, with `--archive`, goes on to the archive), and a `halt` of `decide` itself shows its own text, not `Step budget <n> spent.` The budget halt logs no skip: a skip `decide` returned in that call is decided again when the run resumes, from the files it then finds. Both chains share it.
- A successful `score` step counts like any other step; it is outside the extra-step pool. Failed `score` attempts use no budget. The attempt cap of 3 bounds their cost, so a scorer that fails three times and then skips still leaves the longest path inside the budget. A test lets the router walk saturating plans and checks this; the same test shows that a pool allowance raised by one without a larger delta breaks it. `lean` has an empty pool, so `manual-verify` is its only extra step. The lean walk of the budget test is plan, plan-review, implement, `manual-verify` and its retry, then impl-review, fix, impl-review, fix, impl-review: 10 steps, two below the budget of 12. A lean run whose plan loop re-plans can still spend its budget, as before. Once a failure raises the level, the run has the pool of 2 and the budget of 19 of `standard`. A `lean` run gets no `score` step, also after the rise, because a plan attempt is already logged.
- A failed cheap first attempt (`cheap: true`, see "How routing works") uses no budget either, so it leaves the longest path inside the budget. A drop that the score shift, the clamp or the floor cancelled is no cheap attempt, and its failure counts as usual.
- A neutral rerun after an orchestrator fault adds no log entry and uses no budget: the step keeps its one entry however often it is rerun (see "Neutral rerun after an orchestrator fault").
- Typical worst paths at `standard`: the score step (1), the plan loop (6 steps), a segment, an e2e step and a plain tail (3), `manual-verify` and its retry (2), then impl-review, fix, impl-review, fix, impl-review (5) is 17. At `thorough`: three pre-plan steps, the score step, a `RETHINK` with a frame round and a plan loop (11), segment, e2e, tdd and a plain tail (4), `manual-verify` and its retry (2), then 5 is 22.
- A project that overrides `rigor.budgetDelta` keeps its values. With a pool allowance above 0 and an old delta, the budget can halt a run that uses extra steps. An override that keeps the earlier deltas (-4, +3 and +8) has no room for `manual-verify` and its retry: raise each by 2, or turn the step off with `{ "manualVerify": { "minRigor": null } }`.

Phase executors:

- The step name stays `implement`; the template changes. For the first pending phase of `### Phase N` headings the router returns `implement-e2e` (a valid `/10x-e2e-setup` record in `context/foundation/test-stack.md` and a browser word in the phase), `implement-tdd` (rigor `thorough`, a phase whose files are code and whose rows name a test command) or the plain step. Goal phases in front of a special phase run as `implement-segment`, which stops after its last phase.
- The extra-step pool (`extraSteps.allowance`: `lean` 0, `standard` 2, `thorough` 3) pays for segments, e2e and tdd at 1 each and for the `plan-rejected` re-plan at 2. `manual-verify` is outside the pool: a pool of 0 does not keep it away, and an override of `extraSteps.cost["manual-verify"]` charges nothing. When the pool cannot pay for a segment and the executor after it, plain `implement` runs the whole plan.
- A tdd or e2e step counts as done only with ticked rows and a code commit since it began (read-only `git`; docs, lock files, `assets/**` and `context/**` do not count). The check is per step, not per row: one counted commit covers every row the step ticked. Without git, in a repository with no commit yet or with a head that cannot be resolved, the first check falls back to the count rule, so there is no strict check there. Rows left ticked without a commit get one `implement-retry` step; if they still have none, or the retry cannot check (no git, no commit yet, an unreadable head), the run goes on without a failure and the implementation review prompt carries a warning, with a note when commit evidence was unavailable. The rows are listed as `uncommittedTicks` in the final message, the `archive` summary and `meta.outcome`, and in `report.md` of an `--archive` run.
- A tdd or e2e step that ends `blocked` is a fallback: no failed attempt, no tier bump, no rigor rise, and the executor is not chosen again for that phase. The report shows `fallback`, and `compare` does not count it as a failed attempt. The report shows `implement (<template>)` in the Step cell.
- Code re-plans, at `standard` or above, one per run: `plan-replan` after two implement failures in a row, `plan-rejected` after a first implementation review `REJECTED` before any fix (cost 2 of the pool). A failed `plan-replan` halts the run.
- Word lists and extension lists (`executors`) are uncalibrated. Nothing here has run against a live `/10x-e2e`, `/10x-tdd` or `/10x-goal-implement` session.

Manual verification:

- `manual-verify` runs at every rigor level (`manualVerify.minRigor`, default `lean`) once no Automated row is pending, before the first implementation review, when a Manual row is pending or the last attempt left a tick without valid evidence. It never runs after an implementation review, so a `fix` does not re-run it, and ticked rows stay ticked. It is outside the extra-step pool and each attempt counts one step of the budget (ADR-012).
- Every pending Manual row is in scope, a row with no command and a row that asks a person to read, judge or decide included. A subagent that starts with no memory of earlier steps proves each row by running the row's command, by a green automated test that covers it, by a throw-away script in a `mktemp -d` scratch directory or under `evidence/` (never in the source or test tree), with the Chrome tools, or by a written judgment that quotes what it checked. It saves the proof under `context/changes/<id>/evidence/` and ticks the row with ` — evidence: evidence/<name>`.
- The evidence file name starts with its kind: `command-`, `test-`, `script-`, `browser-` or `judgment-` (`manualVerify.evidenceKinds`). The router records `proved: [{ id, kind, file }]` in the log entry, one item per ticked row; any other prefix, or none, reads `other` and the row still counts. A judgment is weaker proof than a run, and the report says which is which.
- Browser rows (change `browser-row-proof`, issue #37, ADR-012 amendment 1): a pending Manual row whose text, without its ` — evidence:` suffix, names a word of `manualVerify.browserRowWords` is a browser row. The default is `playwright`, `e2e`, `end-to-end`, `browser` and `chrome` (the `executors.e2e.rowWords` plus `chrome`; uncalibrated), matched as the other word lists are: lower-case, a phrase starts at a word start, so `Rebrowser` does not hit. Only a kind of `manualVerify.browserProofKinds` (default `browser`, `test`, `command`, `script`) proves a browser row. A tick whose evidence is valid but of another kind (`judgment` or `other`) is listed as unproven with the reason `browser row ticked with <kind> evidence; only browser, test, command, script evidence proves it`; it follows the existing unproven path, so the retry one tier up runs as for any unproven tick and the run goes on after the last attempt. A kind of `browserProofKinds` that `evidenceKinds` leaves out reads `other` and never proves a browser row. Both keys follow the rule "a wrong shape reads as the default and never halts"; an empty `browserRowWords` turns browser rows off, and an empty `browserProofKinds` reads as the default. The old keys `browserWords`, `commandWords`, `humanWords` and `maxRuns` stay ignored. The attempt count and the step budget do not change.
- The router checks that the evidence file exists, is regular and non-empty, lies inside the real `evidence` folder (a symlinked evidence file is refused) and is newer than the step start, and that no Automated row, row title or SHA suffix changed. It never reads the content and never edits `plan.md`. Ticks without valid evidence, a mangled evidence suffix included, are listed as `manualUnproven`.
- Attempts: the first runs on `sonnet/medium` (`steps["manual-verify"]`). A second attempt runs one tier up on `sonnet/high` (`manualVerify.retryBump`, `tierWhy` reads `+1 from manual-verify retry after 1 attempt(s)`) when the first failed its checks or ended `done` with rows still pending. `manualVerify.maxAttempts` (2) caps them. A failed attempt is neutral: no failed attempt counted, no rigor rise, no rollback. After the last attempt the run goes on to the implementation review; an unproved row never halts it.
- Unproved rows: a row the subagent cannot prove stays `[ ]`, and the subagent lists it in `evidence/unproven.md` (`manualVerify.unprovenFile`) as `- <row id> — <reason>`, rewriting the file for every row still pending at the end of each attempt. The router reads it for display only, and only when it is a regular file (not a symlink) inside the real `evidence` folder, at most 65536 bytes and newer than the step start. Each reason is made one line and cut to `manualVerify.reasonMaxChars` (200) code points. A missing, stale or malformed file gives no reasons and never changes the outcome. The log entry gets `reasons` (`{ <row id>: <reason> }`) and `pending` (the row ids still pending).
- Outputs: a `done` run where the step ran lists every row still pending as `manualNotProved`, `<row text> — not proved: <reason>` (`no reason recorded` without one), in the final message, `meta.outcome` and the `archive` summary, next to `manualPending`. `status` shows `proved` (a count per kind) and `pending` (a count) next to `ticked` and `unproven` on the row of each `manual-verify` step, and, for an entry that carries them, `browserRows` (a count) and `unprovenWhy` (`{ <row id>: <reason> }`). The router reason of a browser row rejected for its evidence kind is stored once on the log entry (`unprovenWhy`, with `browserRows`, the ids of every baseline browser row) and read from there by every output: the final message and `meta.outcome` carry `manualUnprovenWhy` (`<row text> — <reason>`, next to `manualUnproven`), the `archive` summary too, and the archive lines of `report.md` and its committed copy list `Manual checks unproven, reasons: N`. - Safety: the prompt (`skills/10x-pipeline/prompts/manual-verify.md`) tells the subagent never to push, deploy, publish or post to an external service, never to write outside the run root and its scratch directory or, in the run root, outside `plan.md` and `evidence/`, to use only read-only git, never to delete a branch, worktree or ref, never to run a command that does not end by itself or waits for input, to start a server only in the background and stop it before the step ends, and to redact credentials, tokens, environment dumps and personal data before saving evidence, because the step commit stores `evidence/` in the run branch. The router enforces none of these: it never reads evidence content and never checks for files written outside the change folder. The step commit and the implementation review see the diff.
- `--chrome` (an `init` flag, kept in `meta.json`): the Chrome tools are on by default. The first line of both templates lists the browser rows (`Browser rows: {browserRows}`, the router's own list, `none` when empty). Complexity score:

- `score` is a pipeline step (ADR-007). At `score.minRigor` (default `standard`) and above, the router returns it once before the first `plan`, after any `research`, `domain-brief` or `frame` step. `steps.score` pins it to the lowest tier of the ladder; a retry runs one tier up. A `lean` run never pays for it. The step is outside the extra-step pool.
- The subagent follows `skills/10x-pipeline/prompts/score.md`. It reads `change.md`, the goal and the upstream artifacts, never `plan.md`, and writes `context/changes/<id>/complexity.json`:

```json
{
  "schemaVersion": 1,
  "factors": {
    "ambiguity": { "score": 0, "evidence": "..." },
    "novelty": { "score": 0, "evidence": "..." },
    "coupling": { "score": 0, "evidence": "..." },
    "discovery": { "score": 0, "evidence": "..." },
    "volume": { "score": 0, "evidence": "..." },
    "verification": { "score": 0, "evidence": "..." }
  },
  "unknowns": ["..."],
  "confidence": "medium"
}
```

- Each factor scores 0 to 3 with a one-line `evidence`. The cognitive sum (`ambiguity`, `novelty`, `coupling`) and the execution sum (`discovery`, `volume`, `verification`) each run from 0 to 9. Factor names, the scale and the thresholds sit in the `score` block of `policy.json` and are uncalibrated.
- The step counts as done only when `complexity.json` is newer than the step start and is a regular file (not a symlink) of at most `score.maxBytes` (65536) bytes, with `schemaVersion` 1, an integer score from 0 to 3 and non-empty evidence for every factor, `unknowns` as an array and `confidence` `low`, `medium` or `high`. Extra keys are ignored. The router never judges whether the evidence is true.
- The router copies the factor scores, the two sums, the confidence and the number of unknowns into the `score` log entry; the evidence text stays in the file. Every later tier and the report read that copy, so a later edit or deletion of `complexity.json` changes nothing.
- A valid `complexity.json` that exists before the first attempt skips the step with a logged reason and is trusted as-is. An invalid one does not skip the step, and the subagent writes a new file.
- A failed attempt retries one tier up. After 3 failed attempts or 2 invalid files the router logs a skip with the last note and goes on with the deterministic signals; the run never halts for a failed scorer. A failed attempt uses no step budget, raises no rigor and withholds no simple-change discount. A `signals.needsHuman` in a score result halts the run once, as for any step; `signals.rigor` is dropped.
- Shift up: a cognitive sum of 7 or more moves the first plan (template `plan`) up one tier. An execution sum of 7 or more moves an implement step (`implement`, `implement-segment`, `implement-tdd` or `implement-e2e`) up one tier. Up shifts have no guards. A retried first plan or implement step keeps the up shift on top of the failure bump. Re-plans (`plan-revise`, `plan-replan`, `plan-rejected`), `implement-retry`, reviews and fixes get no shift.
- The plan never moves down (`score.shift.plan.down` is `null`): churn risk is not measured before the first plan, and a hard-keyword goal keeps the plan's base tier on purpose.
- Shift down: an execution sum of 2 or less moves an implement step down one tier only when every guard holds: confidence `medium` or `high`, at most 2 unknowns, churn risk measured (the same test as the `lean` plan-review skip) with no hot plan or diff path, no failed step, no simple-change discount and no phase-count bump on the step. The window is narrow on purpose: it opens only for a plan of 2 phases, or of 1 phase with more than 6 rows, whose named paths are all measured and none is hot.
- The shift goes in before the clamp and the effort floor. The floor applies to interactive steps (ADR-003), so `plan`, `implement-tdd` and `implement-e2e` never go below it, while a down shift on plain `implement` or a segment can reach the step's `minTier`, as the simple-change discount can. A shift never changes the rigor level.
- `report.md` gets a `## Complexity score` section with the sums, the factor scores, the confidence, the number of unknowns and one line per shifted step, such as `implement -1 (step 5)`. A shift that the clamp or the floor absorbed reads `not applied (clamp or floor)`. `status` shows `score`, `invalid` and `scoreShift` on the rows that have them. `scoreShift.effective` is the difference of the final tier indexes with and without the shift, so it can read 2 for a shift of 1 when the floor skips a rung.
- A run that starts with a `plan.md` that already has `## Progress` gets no score and no skip entry, and so does a run that already logged a `plan` step.
- Turn the step off per project with `{ "score": { "minRigor": null } }` in `context/foundation/agent-smith-policy.json`. With no score, every tier is what it was without the step.

Override any policy key per project in `context/foundation/agent-smith-policy.json`. An override file that does not parse halts every command with the file name and the parse error, and so does one whose JSON is not an object (an array, `null`, a string, a number or a boolean); a missing file is no override. The values of the keys inside it are not checked there; `init`, `next` and `usage` check the keys that cap spend and the prompt placeholders right after (see "Policy validation"). Run state lives in `context/changes/<change-id>/agent-smith/`.

Prompt overrides: every template key of `prompts`, `archive` and `suffix` included, is a string or an array of strings joined with newlines. The reserved `byFile` option accepts only a boolean; omitted or false retains inline dispatch. A string, or an array part, that starts with `@prompts/` is always a reference to `skills/10x-pipeline/prompts/<file>.md` of the plugin (`@prompts/<file>.md`, the name made of letters, digits, `.`, `_` and `-`), and one that starts with `@<skill>/prompts/`, where `<skill>` is lowercase letters, digits and `-` (no dot, no slash), is a reference to `skills/<skill>/prompts/<file>.md`, for example `@openspec-pipeline/prompts/os-apply.md`. A reference is never literal text, and the trimmed text of that file replaces it. A reference that does not resolve halts `init` and `next` with `Router error: policy.prompts.<key> ...` before a result is consumed and before the pre-archive commit. Literal text that must name such a path starts with any other character, for example `See @prompts/<file>.md`. The OpenSpec decision guides moved to `skills/openspec-pipeline/prompts/` (ADR-013 Amendment 1): an override that still names `@prompts/os-<step>.md` halts with `cannot be read`; the fix is `@openspec-pipeline/prompts/os-<step>.md`.

Rule levels (ADR-023):

- The rules handed to a step come in three levels: level 1 for every step of both chains, level 2 for one chain, level 3 for one step. Each level has **always-true** rules, in files no policy key and no project override reaches, and **defaults**, in policy keys you can override. `skills/10x-pipeline/rules/README.md` has the table and lists every rule file.
- Always-true: `skills/10x-pipeline/rules/top.md` (level 1, both chains: unattended subagent, short status, Git preservation and orchestrator publication ownership, the delete rules of ADR-016, the nesting rule of ADR-018, the two precedence rules and the `RESULT:` format), `<chain skill>/rules/chain.md` (level 2; shipped for OpenSpec: the change name as `--change "{id}"`, no `--store`) and `<chain skill>/rules/steps/<step>.md` (level 3, keyed by step so it covers every template of the step; shipped step owners include `research`, `plan`, `plan-review` and OpenSpec `os-propose`). The router reads them by fixed path. A missing `rules/top.md`, or a rule file that exists but cannot be read, halts `init`, `next` and `usage` with `<path> cannot be read. Restore the plugin file. Nothing was written.`
- Defaults: `prompts.suffix` (level 1: commit only where told, decide from evidence, `blocked` when no evidence exists, `signals.rigor` **MAY**), `prompts.chain-10x` and `prompts.chain-openspec` (level 2, none shipped) and the step templates (level 3).
- Order of every prompt: the worktree rules (isolated run), the rendered template, the advisor rules (opt-in), the chain defaults, the generic defaults (`prompts.suffix`), then the step file, the chain file and `top.md`, each when it exists. `top.md` is last, so the `RESULT:` format ends the prompt. Precedence, stated in `top.md`: an always-true rule wins over every other rule, and between two always-true rules the higher level wins (top, then chain, then step); among the other rules the one written earlier wins, so the step template wins over the chain defaults, which win over the suffix.
- The step file, the chain file and `prompts.chain-<chain>` are rendered with the template's placeholders at a run step and with `{id}` only at the archive step. `top.md` and `prompts.suffix` are not rendered.
- Upgrade notes: an override of `prompts.suffix` now replaces only the defaults; the always-true rules stay. An override that copies the old full suffix text carries the `RESULT:` block twice, which is harmless. The prompts and the new rule files change, so a run in flight records `provenance.drift` for `prompts` and `ruleFiles` at its next call. Routing is unaffected.

### Step prompt handoff by file

Opt in per project with `{ "prompts": { "byFile": true } }` in `context/foundation/agent-smith-policy.json`. The shared default is false. Both chains and both providers support it for numbered `run` actions; `archive` and `os-archive` stay inline.

The router writes the exact rendered task, including every rule and the unchanged RESULT contract, to `<change>/agent-smith/prompt.md`. The action carries a run-root-relative `promptFile` (like `resultFile`) and a short `prompt` naming its absolute path. The orchestrator forwards the short prompt verbatim without reading or expanding the file. The child reads the entire task; the wrapper repeats its final RESULT contract and asks for a failed result if reading fails.

The pending entry retains the full `pendingPrompt` and the exact `pendingHandoff: { promptFile, prompt }`. Neutral retries restore the task from that stored text and replay the same descriptor and dispatch even after a policy change. Legacy entries without a handoff remain inline. Turning the option off affects new steps only. Finish a pending file-mode step with a supporting router before downgrading.

After shared result cleanup, handoff cleanup removes the task before step commits, rollback snapshots, terminal publication and pre-archive commits. The state-temp cleanup also recognizes exactly `prompt.md.<pid>.tmp` regular files. The task cleanup marker stays durable until task deletion and publication of marker removal succeed. Cleanup errors halt before those operations; fix the filesystem problem and run `next` again. A new step may immediately replace the same path. Missing results and validation refusals preserve the pending task. A neutral-retry-cap halt removes the file but keeps enough pending state to restore it if the cap is raised. Unowned collisions, redirects and non-regular files halt without overwriting them.

Task files are transient and must not be staged by a child. Cleanup cannot remove prompt text from an earlier child-authored commit, and an unconsumed task retained after a halt may still be staged by the final PR helper. Template/rule provenance hashes are unchanged by transport alone.

The [comparison evidence](../context/archive/2026-11-12-step-prompt-by-file/evidence/comparison.md) separates emitted byte measurements from live acceptance. Smaller copied output does not establish token, cost or task-quality improvements: the full task still reaches the child and adds a file read. With zero matched live pairs and no orchestrator telemetry, the default remains false.

Tier order expresses intended model capability. Effort labels are calibrated per model, so opus/max to fable/high lowers the effort label. The shipped lean/standard/thorough floors remain medium/high/high and both appended rungs satisfy them. The final effort floor applies after clamps and can exceed a lower step ceiling. These ceilings permit higher dispatch targets. Ordinary first plans, score shifts and bounded retries have their existing reach. In the two-phase RETHINK path, the revision runs at tier 7 opus/max, its first failed retry reaches tier 8 fable/high, and two failed revisions hit the unchanged revision cap. Pure tier calculations with larger bumps can reach tier 9. Opting in can increase paid usage and latency, with no measured capability equivalence or cost ordering.

To stop opting in, restore the previous ladder and the four previous ceilings together. Removing only the appended rungs leaves invalid out-of-range maxima. Preserve unrelated keys. Pending and neutral retries can retain stored dispatch targets, and historical logs keep their recorded targets.

Usage report:

- When a run ends (`done` or `halt`, including a spent step budget or repeated failures), the router writes `context/changes/<change-id>/agent-smith/report.md` and adds its path to the output as `report`.
- The report has the goal, the rigor level and the outcome, then one table row per executed step: model, effort, tier, simple-change flag, result and tokens. A totals line sums the tokens and gives the number of skipped steps. A `## Skipped steps` section lists each skip with its reason. A `## Review findings` section (after `## Rolled-back steps` and `## Neutral reruns`) lists one line per step with a stored review record: `- step <n> <step>[ (confirmation)]: <VERDICT>, <c> critical, <w> warnings measured[; <oc> critical, <ow> warnings open]`. The measured pair is the header count before the review's own fixes; the open part appears only for a review with `Decision` lines and shows what was still open, so tolerated open warnings stay visible. The figures are those stored in `run.jsonl` when the step ended, and the section says that a later edit of a review file (an owner closing a finding after a halt) is not reflected. The section is omitted when the log has no review records. A `## Manual checks` section follows it when a `manual-verify` step ran: the rows the last attempt counted as proved, grouped by evidence kind (`- <id> <title> — <kind> (<file>)`), then the rows still pending with their reasons (`- <id> <title> — not proved: <reason>`). A browser row carries ` [browser row]` after its title in every group. An `Unproven: N` group follows when the last attempt left ticks the router rejected: `- <id> <title> — unproven: <reason>`, the router reason for a browser row ticked with the wrong kind, else `no valid evidence`. The router never reads the evidence content, and the section says so and that only browser, test, command or script evidence proves a browser row. No `manual-verify` step, no section.
- Token figures are optional non-negative safe integers. The current producers supply `usage` (`totalTokens`, `toolUses`, `durationMs`) and normalized sibling `usageEvidence`; earlier scalar figures remain readable as legacy/unverified scope without rewriting their stored bytes. Notifications may corroborate invocation identity and independent counters, but their final-request `subagent_tokens` is not a whole-step measurement. A missing token cell is `-`; an observed explicit zero is `0`. A partial total says `subtotal`; overflow is unavailable rather than a selectively smaller sum. The compact `## Token coverage` section counts verified, unavailable, legacy/unverified and missing figures and lists bounded unavailable reasons. Failed executed attempts remain included; skipped steps and archive-only execution remain excluded.
- `status` adds normalized per-step `usage`, `usageEvidence` (or `null`) and `tokenScope`, top-level `usageCoverage: { verified, unavailable, legacy, missing }`, token/tool/duration aggregates with `stepsWithFigures`, and `groupingScope: "enclosing-dispatch"`. Counts describe executed entries, including a pending dispatch as missing until its intake. Legacy coverage counts only valid token figures, including measured zero; missing or counter-only legacy entries do not create a mixed token scope. Aggregates preserve numeric zero plus zero coverage in JSON for compatibility; rendered missing totals stay `-`. An overflow total is `null`. Plain readers never migrate or backfill stored ledgers.
- A step the router returned again after an orchestrator fault shows `, <k> neutral rerun(s)` after its result in the Result cell (`-, 1 neutral rerun` while it is still pending), and a `## Neutral reruns` section after `## Rolled-back steps` lists each such step with the orchestrator's notes, each made one line, without backticks and cut to 200 code points. `status` shows `neutralRetries` (a count) on that row. No rerun, no section and no field (see "Neutral rerun after an orchestrator fault").
- `node skills/10x-pipeline/scripts/route.mjs status <change-id> --report` rewrites the report on demand. For a run in progress it prints `Outcome: not ended`. Plain `status` stays read-only.
- A halt for a missing result file writes no report. A run that continues after a halt keeps the old `report.md` until it ends again or you run `status --report`.

### Observed token accounting

The bounded schema is `usageEvidence: { schemaVersion: 1, status, scope: "step-tree", source, hostVersion, invocation, ... }`. Verified evidence adds `sessionCount`, `requestCount` and reconciliation (`response-snapshot` for Codex, `request-records` for Claude). `sessionCount` counts independently measured execution contexts: Codex threads or Claude agents, even when several share one outer session. Invocation identity is `{ host: "codex", rootThreadId, rootTurnId }` or `{ host: "claude", sessionId, agentId, runId }`. These are host IDs, never descriptions invented by the step. Unavailable evidence keeps an exact identity only when observed and carries a fixed sanitized reason/explanation. No prompt, transcript, tool body or absolute telemetry path enters router state or reports.

The supported Claude accounting schema is 2.1.311. An operator may supply a local capture already authorized for that invocation; the plugin installs no hooks, configures no exporters and enables no telemetry. Collection needs paired `PreToolUse`/`PostToolUse` Agent records and `SubagentStop`, exact session/agent/Agent `tool_use_id` matching (`runId`), matching regular-file native transcript paths, and OTLP JSON logs. Transcripts must prove one complete UUID/parent path from the final assistant to the launch user, including recognized attachment nodes even when serialized out of order. Broken, disconnected or cyclic history is unavailable. Native request/message usage and `api_request` membership and counters must agree exactly. Each available `assistant_response` must match its native request/UUID, and the terminal response is required; tool-only requests need no text response event. OTLP integer values accept nonnegative safe integers in numeric or decimal-string form. OTLP resource `process.pid` and `process.creation.time` must match the observed process, with a contiguous process event-sequence prefix from zero through the enclosing Agent `tool_result`; child terminal and return records must precede parent close. A quiet file, completion notification, final-message footprint, session total or a supplied “complete” boolean supplies no such proof. Default captures often lack these provenance fields and therefore remain unavailable. Four Claude buckets are additive: uncached input, output, cache read and cache creation. This differs from Codex cache/reasoning subsets.

Invoke the model-free collector from the run root with `node <absolute-plugin-scripts>/claude-usage.mjs`, passing one descriptor on stdin:

```json
{
  "router": { "change": "example", "chain": "10x", "n": 1, "step": "plan" },
  "hostVersion": "2.1.311",
  "invocation": { "host": "claude", "sessionId": "native-session", "agentId": "step-agent", "runId": "tool-root" },
  "process": { "pid": 4242, "createdAt": "2026-11-18T00:00:00.000Z" },
  "sources": { "root": "/absolute/local/capture", "nativeFile": "/absolute/local/capture/hooks.jsonl", "telemetryFile": "/absolute/local/capture/otel.jsonl" }
}
```

The descriptor is an illustrative shape, not captured telemetry. Replace every identity and source with the actual matched invocation; OpenSpec uses its chain/step names, archive uses `n: null` and its archive step. Optional `usage` may carry independently measured tool/duration counters. The CLI returns only normalized usage/evidence; the enclosing orchestrator merges that accounting over the step report after settlement and uses existing router intake. For late input, collect at most once from the matching invocation and use the structured command below. No polling, model session, permission change or billing query is involved.

Limits: descriptor/late-input 64 KiB, normalized evidence 4 KiB, one source record 1 MiB, an invocation 32 MiB, 512 contexts and 100000 requests; Claude also caps events at 200000. Source reads require stable local regular files within canonical roots and reject symlink redirects or file replacement. The read budget is 2 seconds; Codex usage metadata and source reads share its deadline. Synchronous deadlines cannot interrupt a blocked filesystem syscall, so blocking remote storage remains unqualified. Reasons include `unsupported-host`, `unsupported-schema`, `missing-source`, `missing-identity`, `incomplete-capture`, `conflicting-duplicate`, `snapshot-mismatch`, `ambiguous-history`, `unsafe-path`, `resource-limit` and `invalid-evidence`.

- `node skills/10x-pipeline/scripts/route.mjs usage <change-id> <n> (--usage-file <path> | --tokens N [--tool-uses N] [--duration-ms N]) [--chain 10x|openspec]` attaches a usage figure to executed step `<n>` when the figure reached the orchestrator after `next` ran for that step. It works the same on both chains. `<n>` is the step number recovered from the matched earlier launch, a positive integer that directly follows the change id. See [ADR-019](ADR/ADR-019-late-usage-figure.md).
- Steps with a recorded evidence contract require `--usage-file`. Supply a bounded, stable regular JSON file within the run root with the shape `{ change, chain, n, step, usage: { totalTokens }, usageEvidence }`. This form is mutually exclusive with all numeric flags. The completed target must already carry the exact observed source, host version and invocation. Only verified evidence for that same invocation may fill missing tokens. Any supplied tool or duration counters must agree with existing values. Missing counters stay missing. Recorded numbers and their verified evidence cannot be replaced. Exact replay is a no-op. A legacy row without recorded attribution cannot be upgraded. Invalid identity/schema, unsafe path, oversized file, pending or archived target and conflicting values refuse before writes. Success returns normalized `usageEvidence` too.
- Legacy steps without recorded usage evidence accept any one or more of `--tokens`, `--tool-uses` and `--duration-ms`. Supply a non-negative safe integer for each flag used. The router refuses invalid numeric input before reading the usage log. The figure then goes through the same cleaning as an on-time one, which keeps `totalTokens`, `toolUses` and `durationMs`. Before writing, the router checks the arguments, that the change is not archived, that the OpenSpec change folder exists when applicable, and that the run log contains step `<n>` with a result. For a pending step, put the figure in its result file as `usage`. An equal figure answers `unchanged: true` and writes nothing. The router refuses a different figure. Legacy flag mode cannot validate a host invocation and can accept a wrong step number when its entry has no figure. Recover `<n>` from the matched earlier launch using the identity check under Orchestrator anti-stall, and use the printed `Step <n>` line only to corroborate the change, number and step against the exact launch description. Use the matched launch to identify the step even if a newer step has run or a step name repeats. Leave unmatched or ambiguous figures unattached. Archive-agent usage belongs only in the final message.
- The orchestrator creates an exclusive uniquely named transient input outside the change folder and unlinks only its owned file in `finally`; it never writes router state directly or includes raw source data. Structured input reuses the same run lock, atomic publication, report refresh, archive-state commit and recovery path as flag mode. No `next` replay is involved.
- A refusal prints `{ action: "usage", attached: false, n, reason }`, exits 1 and leaves the change folder byte-identical. A success prints `{ action: "usage", attached: true, n, step, usage, unchanged, report, commit }`, plus `reportError` when the report could not be written. It is no step result and no orchestrator fault: it changes no tier, rigor, budget, rollback or attempt count.
- The log entry gets `usage` and `usageLate: true`, so `status`, `report.md` and `compare` read the figure like any other: the Tokens column, the totals, the `Cost (est.)` column and the `usage-incomplete` check. A run that has ended (`meta.outcome` is set) gets its `report.md` written again, so the report shows the figure. A run in progress gets no report.
- In an isolated run the figure survives the rollback and the undo on halt of the next call, because they write the in-memory log back. Outside the archive state, the next step commit or a successful leftover commit records the figure. When the publication guard skips the leftover commit, the late usage and other uncommitted run artifacts stay in the worktree.
- The archive state is an ended run that started with `--archive` and ended in `done`. The folder is committed for `/10x-archive` at that point, so a figure written to it would dirty the folder and make the archive refuse. The command therefore checks first (a non-blank `archive.usageMessage`, the git safety checks of the archive commit, the run branch of an isolated run, and change-folder cleanliness that tolerates only exact untracked regular state-temp candidates), refuses before it writes anything, then writes the log and the report and commits the change folder as `chore(<id>): add late usage figure of step <n>` (`archive.usageMessage` in the policy), with the folder-only checks of the archive commit. A failure before the commit exists restores the exact saved Buffers of `run.jsonl` and `report.md` through atomic publication, or their original absence, and refuses with `The figure was not kept; the change folder is as committed.`. A commit that exists but fails a later check answers `attached: true` with a `reason`. This commit is the one git write of the command (ADR-019); hooks and signing apply and nothing is pushed.
- Recovery attempts every saved file. An incomplete restoration halts with the affected path and error, so the operator can inspect state before retrying.
- Cut-off points: the orchestrator calls the command first in the `done` and `halt` branches, before `status` and the pull request step, and in step 1 of the `archive` branch before `status`, so before the archive subagent launches. A figure that arrives after that point is dropped. The command itself works until the change is archived; a figure attached after the pull request step stays uncommitted in the worktree of a run without `--archive`.
- Run lock: execution, `init`, `next`, `usage` and `status --report` take a per-run lock file `agent-smith-<16 hex of sha256 of the run's agent-smith folder path>.lock` in `os.tmpdir()`, outside the change folder. It starts with the owner PID, written to a temp file and linked atomically. Execution replaces it atomically with runner and child ownership as described under Codex dispatch. A second call while the owner or its child process group runs halts with exit 1 and writes nothing. Legacy dead-PID and unparsable plain-text locks are replaced. Structured execution locks with uncertain termination remain until inspected. Plain `status`, `risk`, `verify-archive` and `compare` take none. Limits: the key follows `os.tmpdir()` (the `TMPDIR` of the call), so callers with different `TMPDIR` do not exclude each other; two calls that find a stale lock at the same moment can both take it; a reused PID keeps a stale lock alive.
- After an archive-state commit in an isolated run, `next` resumes the `archive` action: HEAD is no longer the pre-archive commit, so the router writes the report again, finds nothing to stage and returns the action with `commit: null`; the folder stays clean.
- Upgrade note: `policy.json` gains `archive.usageMessage`, so a run in flight records `provenance.drift` for `archive` at its next `next` call, and `compare` warns `provenance-drift:<side>:archive`. Entries without `usageLate` read as before. Routing is unaffected.

Cost estimate:

- Off by default: `policy.json` ships `"prices": null`, so no price is invented. Turn it on in `context/foundation/agent-smith-policy.json` with `{ "prices": { "usdPerMillionTokens": { "opus": 30, "sonnet": 6, "haiku": 2, "fable": 12 } } }`, USD per million tokens per model alias (the `model` the log records, never a model id). All numbers in this example are illustrative user-supplied blended rates. Supply current rates for your deployment. Pricing is a separate opt-in from the ladder. Rates are keyed by model across providers and efforts. Estimates carry no billing or savings guarantee. Omit unknown prices, since `0` is a real zero rate.
- The rate is blended: the persisted accounting exposes one `totalTokens` per step, with no pricing split by input, output or cache, so a step costs `totalTokens * price / 1e6`. Only steps with a token figure and a price count. A `0` price is a price.
- `report.md` then gets a `Cost (est.)` column after `Tokens` (`$` and 4 decimals, `-` for a step with no figure or no price) and a line under the totals line: `Cost (estimate): $X.XX at a blended rate (USD per million tokens, no input/output split) · priced N of M steps with a token figure`, plus ` · no price for: <aliases>` when an alias with a figure has no price. With nothing priced the line reads `Cost (estimate): - (no step with a token figure has a price) at a blended rate`. Without prices the report is as before.
- `status` then adds `cost` (USD at 4 decimals, or `null`) to each executed step row and a top-level `cost: { usd, currency: "USD", rate: "blended", priced, withFigures, unpriced }`; `usd` is `null` when nothing is priced. Without prices it has no `cost` key.
- With an active table missing fable, its per-step status cost is `null`, the report cell is `-` and the summary names `no price for: fable`. Mixed runs total only priced steps. All-unpriced status totals are `null`. Compare adds `cost-incomplete:routed` while preserving its token verdict. With prices off, status/report omit costs and compare side costs remain `null`.
- Verified subtrees add `scope: "enclosing-dispatch-routing-rate"` to JSON cost summaries and a routing-rate approximation explanation to Markdown. Child models can differ from the enclosing dispatch model, so grouped estimates price their usage at that enclosing rate. Unavailable token claims are excluded. Nonfinite estimates or aggregate overflow show `null`/`-`, never an incomplete smaller cost. Ordinary legacy arithmetic and keys remain compatible.
- Both chains read the same log entries, so an OpenSpec run gets the same column, line and `status` object.
- A `prices` block of another shape reads as off, and an entry that is not a number of 0 or more is dropped (that alias is unpriced); nothing halts.
- The report computes the estimate with the override as it reads when the report is written. An archived `report.md` keeps the text it was written with; a later price change does not touch it.
- `prices` is display-only: it is in `provenance.ignore`, so it is never hashed and never raises `provenance-differs`.

Lesson candidates:

The prompt asks for them and states both caps and the `RESULT` shape. Other steps' `lessonCandidates` are dropped.
- The router cleans each candidate (one line, no backticks, no format characters), drops case-insensitive repeats and keeps at most `lessons.maxCandidates` (default 3) per review, each cut to `lessons.maxChars` (default 200) code points, back to the last space when the cut falls inside a word. The caps are per review, not per run: a run with three accepted reviews lists at most 9. An invalid value reads as the default.

- Override the caps in the `lessons` block of `context/foundation/agent-smith-policy.json`. A project that overrides the `impl-review` prompt with a plain string never asks for candidates.

Baseline comparison:

- The baseline is a full run of the same change with every step on the `sonnet` alias at `high` effort, at `standard` rigor, with plan review never skipped and no `score` step (`baseline-policy.json` sets `score.minRigor` to `null`). It needs its own checkout: run state is per checkout, and a second `init` on the same change id resumes the first run.
- Make the baseline: read `meta.baseSha` of the routed run. Choose a branch such as `<effective-prefix><change-id>-baseline` under the committed effective `isolation.branchPrefix`, then run `git worktree add -b <branch> <path> <baseSha>` with shell-quoted arguments. The default example is `agent-smith/<change-id>-baseline`, and a saved baseline retains its exact suffix branch. Preserve the project's `isolation.branchPrefix` when merging `baseline-policy.json` into the baseline override. Copy into it every input file the routed change folder held when its `init` ran (`change.md`, `research.md`, `frame.md` and similar) and none of the files the run produced (`plan.md`, `plan-brief.md`, `complexity.json`, `reviews/`, `agent-smith/`). For an isolated routed run these are the files of its start commit, `git show --name-only <meta.startCommit>`, without `agent-smith/`; copy `<plugin dir>/skills/10x-pipeline/baseline-policy.json` to `context/foundation/agent-smith-policy.json` there (`<plugin dir>` is the installed plugin directory, not a project path; if the project already has an override, merge by hand: arrays are replaced whole and `rigor` merges key by key); run `/agent-smith:10x-pipeline <change-id> <same goal text>` with no extra flag, because the file fixes `standard` rigor, keeps plan review on and turns the score step off. The baseline arm is isolated too, so it runs the cheaper first attempt: on its all-`sonnet`/`high` ladder the drop changes no model or effort, and a failed first attempt is treated as in the routed arm.
- Compare: `node skills/10x-pipeline/scripts/route.mjs compare <change-id> --baseline <worktree> [--routed <dir>] [--format md] [--unpinned]`. It is read-only and writes nothing; redirect stdout to keep the output. `--routed` defaults to the current project. For an isolated routed run pass `--routed <routed run root>`, the run root in its worktree, because the change folder of the main checkout holds no run log. Each `<dir>` is a project root, or the `agent-smith` folder itself, and is read from `context/changes/<id>/agent-smith/` or, when the change is archived, from `context/archive/<date>-<id>/agent-smith/` (a live folder wins over an archived one and adds a warning; two archive folders for one id halt).
- Damaged logs add independently attributed `baseline.logProblems` and `routed.logProblems`. Any nonempty collection adds exactly one `log-problems:baseline` or `log-problems:routed` reason for that side. Either reason gives `comparable: false`, `dropPercent: null` and `verdict: "not comparable"` on both 10x and OpenSpec, including with `--unpinned`. JSON and Markdown retain partial totals, coverage and token splits from usable entries, plus sanitized diagnostics. Markdown includes a partial-log warning with each affected side, absolute file and physical line, or the file alone for a read failure. Both formats perform read-only inspection.
- The output has per-side totals and coverage (`stepsWithFigures` of `steps` for tokens, tool uses and duration), tokens per model alias (`tokens.byModel`) and per tier (`tokens.byTier`, keyed `<model>/<effort>`, with `unknown` for a missing model or effort), `pinned`, `comparable`, `reasons`, `warnings`, `dropPercent`, `targetDropPercent` and `verdict` (`target not set`, `met`, `not met`, `unpinned` or `not comparable`). `--format md` prints both token splits as `Tokens by model, ...` and `Tokens by tier, ...` lines. A pair is comparable only when neither side has log diagnostics, both runs ended `done`, every executed step of both has a token figure and the baseline has at least one executed step, all on `sonnet` at `high`. A baseline whose token total is 0 is not comparable either (`baseline-total-zero`). A failed step that has no token figure makes its whole side not comparable (`usage-incomplete`), so a pair with a crashed or timed-out step usually is not comparable. A `meta.json` that is missing or unreadable shows only as `outcome-not-done` on that side, plus goal and `baseSha` mismatch warnings; nothing names the file. Skipped steps on the baseline, a different goal or `baseSha`, and differing input file names are warnings. `complexity.json` (the file named by `score.file`) is a produced file, like `plan.md`, so it never counts as an input file.
- Accounting coverage adds each side’s `usageCoverage`, normalized `usageSteps` and `groupingScope: "enclosing-dispatch"`, preserving the existing `tokens.byModel`, `byTier`, `byProviderModel` and `byProviderTier` keys. Token/tool/duration and group sums reject unsafe-integer overflow: JSON total/group becomes `null`, Markdown says unavailable/overflow and `usage-overflow:<side>` prevents a verdict. Missing totals render `-`; measured zero stays `0`; partial totals are labelled subtotals with missing counts and unavailable reasons. Any verified plus legacy mixture within or across sides refuses a verdict with `usage-scope-mismatch`, even when numeric totals match or `--unpinned` is set. Legacy-only comparisons preserve their calculation with warning `legacy-usage-scope`; legacy against unavailable coverage also warns and remains subject to completeness checks. No reader mutates legacy evidence or figures.
- Each side's `failedAttempts` and the Markdown `Failed attempts` row count executed entries accepted by the shared `isFailure` predicate. An entry counts when `ok === false` and both `advisory` and `fallback` are falsy. Ordinary legacy failures with absent flags count. Advisory score failures and executor fallbacks contribute zero. Failed cheap first attempts count, following ADR-010's measurement semantics, with their exemptions applying to rigor and budget. Successful, pending and skipped entries contribute zero. All executed entries, including neutral advisory failures and fallbacks, contribute their usage to totals and completeness checks. A neutral failure missing a token figure still produces `usage-incomplete`.
- `--unpinned` is for the scorer A/B check, where the baseline is a routed run too. It waives only the `baseline-not-pinned` reason, adds the warning `baseline-unpinned` and gives a comparable pair the verdict `unpinned`. Log-integrity reasons and all other eligibility checks still apply on both chains. `dropPercent` is then the share of tokens the scorer saved, negative when it cost more. A bare `--unpinned` or `--unpinned true` turns it on, `--unpinned false` turns it off, and any other value halts before anything is read. A word after the bare flag is read as its value, so `--unpinned md` halts: put the flag last or before another `--` flag.
- Cost: with `prices` set in the policy of the project that runs `compare`, each side carries `cost: { usd, priced, withFigures, unpriced, byModel }` (`byModel`: USD per alias over priced steps; `usd` and each `byModel` value at 4 decimals, summed before rounding; `usd` is `null` when nothing is priced, as in `status`), and `--format md` prints a `Cost (estimate)` row (`$X.XX (P of S priced)`, or `- (0 of S priced)`), `Cost by model, baseline: ...` and `Cost by model, routed: ...` lines and `Cost is an estimate at a blended rate and does not enter the verdict.` after the unit line. Both sides are priced from that one table. Without prices each side has `cost: null` and the Markdown is as before. A side with a token figure on an unpriced alias adds the warning `cost-incomplete:<side>`. `comparable`, `reasons`, `dropPercent` and `verdict` never read `cost`.
- `dropPercent` is the exact drop rounded down to 2 decimals; the verdict uses exact tokens. Run `compare` from the project whose override file holds the target: `compare.targetDropPercent` is read from that project's policy, not from `--routed`'s. It ships as `null`, so the verdict is `target not set` until the owner fills it.
- The unit is raw tokens, a proxy for the weekly limit. It understates savings from `haiku` steps and overstates a drop bought by moving work to `opus`. Orchestrator-session tokens are not counted; retries are counted.
- One pair is an anecdote. Compare per-pair drops across several changes, run the two sides close in time and alternate which runs first. A halted or incomplete side makes the pair not comparable instead of being dropped. Read the warnings before trusting the number.
- The baseline file keeps its keys, so the baseline arm runs the same phase executors, segments, `manual-verify` and re-plans as the routed arm. For a routing-only comparison add this to the baseline override by hand: `{"extraSteps": {"allowance": {"lean": 0, "standard": 0, "thorough": 0}}, "codeReplan": {"afterFailures": 0}, "manualVerify": {"minRigor": null}}`. A pool allowance of 0 turns off segments, executors and the `REJECTED` re-plan, all of which draw from the pool; `afterFailures` 0 turns off the failure re-plan, which does not; `manualVerify.minRigor: null` turns off `manual-verify`, which is outside the pool, so a pool of 0 no longer turns it off. The commit check, the retry and the fallback act only after an executor step ran, so with the allowance at 0 they never fire. When both runs carry a provenance record, `compare` warns `provenance-differs:codeReplan,extraSteps,manualVerify` for these additions (see "Run provenance").
- Keep the baseline worktree until `compare` has run, because its `run.jsonl` exists nowhere else; remove it with `git worktree remove <path>` afterwards.

Scorer A/B check:

- ADR-007 keeps the score step only if it saves more than it costs. One pair is one change run twice from the same `baseSha`: the scorer off as the baseline, the scorer on as the routed side. Both arms use the shipped routing, not `baseline-policy.json`.
- Make the scorer-off arm like the baseline above (a worktree at `meta.baseSha`, the same input files, the same goal text), but with only this override in `context/foundation/agent-smith-policy.json`: `{ "score": { "minRigor": null } }`. The scorer-on arm runs with the shipped default. Run both arms at `standard` or above, for example with the same `--rigor` on both: a `lean` run never scores.
- Compare: `node skills/10x-pipeline/scripts/route.mjs compare <change-id> --baseline <scorer-off dir> --routed <scorer-on dir> --unpinned`. Keep `dropPercent`, `tokens.byModel` and `tokens.byTier` of both arms, and the reasons of a pair that is not comparable.
- Make one A/A pair too: the same change with the scorer off on both arms, compared the same way. Its absolute `dropPercent` is the run-to-run spread.
- Alternate which arm runs first and run the two arms close in time.
- Decision rule, fixed before any run. The scorer stays on only when all three hold over at least 5 comparable pairs: the median `dropPercent` is above 0; the median per-pair difference of `opus` tokens (on minus off, from `byModel`) is 0 or less; the median `dropPercent` is above the absolute A/A `dropPercent`. Any other outcome turns it off: fewer than 5 comparable pairs, no A/A pair, or a result inside the A/A spread. To turn it off, set `score.minRigor` to `null` in `policy.json`; the router does not change. A pair that is not comparable is recorded with its reasons and does not count.
- Five pairs is a screen, not a significance test. The rule reads raw tokens and does not credit an effort move beyond the tokens it saves. The result goes into ADR-007 under "A/B result"; no pair has run yet.

Run provenance:

- `init` records what a run runs with in `meta.provenance`, once, while the run has no executed step: `schemaVersion` 1, `plugin` (the `version` of `.claude-plugin/plugin.json`), `sections` and `flags`.
- `sections` holds one hash per section of the merged policy: the first 16 hex characters of a SHA-256 over JSON with sorted keys. `prompts` hashes the resolved text of every template, so an edit of a `prompts/*.md` file changes it. `agentFiles` hashes the `agents/*.md` files of the plugin, and `ruleFiles` the always-true rule files under `skills/10x-pipeline/rules/` and `skills/openspec-pipeline/rules/` (every `.md` but `README.md`; ADR-023). `hookFiles` independently hashes the shipped `hooks/hooks.json` and `skills/10x-pipeline/scripts/step-guard.mjs`, keyed by plugin-relative path. Hook edits and additions produce drift and comparison warnings alongside `agentFiles` and `ruleFiles`.
- The sections in `provenance.ignore` (default `compare`, `provenance`, `prices` and `coAuthor`) are not hashed. Setting `compare.targetDropPercent` changes no hash.
- `flags` holds `archive` and `chrome` from `meta.json`, `score.minRigor` from the merged policy (`null` when unset), `agents.restricted` and `advisor.enabled`. `chrome` is the effective setting: `true` unless the run stored `--chrome false`, so a run that never set the flag records `true`. Any other flag that is missing or malformed reads `false`.
- Computing the record never halts a run. An unreadable `plugin.json` gives `plugin: null`, a missing `agents/` folder gives `agentFiles: null`, an unreadable hook input gives `hookFiles: null`, and a prompt reference that does not resolve gives `prompts: null`; the run then halts at `next` as before.
- The record is never rewritten, also on a resume. Each `next` hashes the sections again and adds every section that differs from the record to `provenance.drift`, sorted, each name once. `drift` is absent while empty. `plugin` and `flags` are not tracked for drift. `next` writes `meta.json` for drift only when the list changes.
- A run whose log already holds executed steps and has no record, because it started before provenance existed, gets none. Nothing halts for a missing record.
- `compare` prints the record of each side as `provenance` (`null` when absent) and appends these warnings after the others. They never change `comparable`, `reasons`, `dropPercent` or `verdict`.
- `provenance-unknown:<side>`: exactly one side has no record. Two sides without a record stay silent.
- `provenance-differs:<names>`: the sections, or `plugin`, that differ between the two records, sorted and comma-joined.
- `flags-differ:<keys>`: the flags that differ.
- `provenance-drift:<side>:<names>`: the `drift` list of that side.
- Names the pair is expected to differ in raise no warning. Without `--unpinned` the set is `provenance.expected.pinned` (default `ladder`, `rigor` and `score`, the sections `baseline-policy.json` changes). With `--unpinned` it is `provenance.expected.unpinned` (default `score`, the scorer A/B arms). The mode follows the flag only, never the `pinned` value `compare` measures.
- A flag is exempt when its first dot segment is an expected section, so `score.minRigor` raises no warning in either mode.
- The expected sets come from the policy of the project that runs `compare`. A list that is not an array of strings reads as the default.

Restricted step agents (opt-in):

- `agents.restricted` in the policy turns it on. It ships as `false`. Only the boolean `true` turns it on; a block of another shape reads as off and never halts.
- When enabled, a usable `agents.steps` mapping selects that type for a normal Claude step. Its `run` output and log entry carry `agent`, and `status` shows it. The orchestrator forwards the selected type as `subagent_type`. A missing or malformed mapping uses `agent-smith:step`. Claude archive actions also use `agent-smith:step`. The preceding safety section documents historical retries and provider boundaries.
- The shipped map names only `score`: `agent-smith:score`, defined in `agents/score.md` at the plugin root. Its `tools` list is `Read`, `Grep`, `Glob` and `Write`, so the scorer can read and search the repository and write files, and cannot use `Bash`, `Edit`, `Skill`, `Agent` or web tools. The definition sets no `model` and no `effort`, so the router's model and effort for each call stay in control.
- `Write` cannot be scoped to one path. The scorer can still write any file; only the prompt rule "change no other file" and the router's check of `complexity.json` hold it to that file. Plugin agent-frontmatter `hooks` and `permissionMode` are ignored. Plugin-level settings hooks can run inside subagents, and the scoped Bash guard is registered there. The restricted scorer has its own type and tool list.
- An unresolved selected Claude agent follows failed-attempt handling for its step, with no general-purpose retry. For the restricted scorer, that means an advisory failure, a retry one tier up with the same agent, no step budget or rigor rise, and a logged skip after three failed attempts.
- ADR-009 records the live `agent-smith:score` resolution check. The new guarded type still needs fresh-host acceptance on both chains.
- A/B reading: both arms run the same model and effort, and the restricted arm has fewer tools, so no token drop is expected and none is the criterion. The restriction earns the default `true` only when the restricted arm has no more failed `score` attempts than the unrestricted arm and no halts.
- Provenance records the flag as `agents.restricted` in `flags`, the block as the `agents` section and the definition files as `agentFiles`, so `compare` warns when two arms differ in any of them.

Advisor (opt-in):

- `advisor.enabled` in the policy turns it on. It ships as `false`. Only the boolean `true` turns it on; a block of another shape, or an `advisor.templates` value that is not an array of strings, reads as off and never halts.
- When it is on, the prompt of a step whose template `advisor.templates` names (shipped: `plan`, `implement`, `implement-segment`) gets the rules of `skills/10x-pipeline/prompts/advisor.md` after the step's own text and before the chain defaults and the generic suffix, and its log entry gets `advisor: true`. The rules ask the subagent to consult the advisor once, after the plan draft or the implementation is complete and before the `RESULT` line, only when an advisor tool is available, to act on the advice or say why not, to leave the workers of `/10x-goal-implement` out of it, and to add one `assumptions` entry that says a consult happened. Re-plans, `implement-retry`, the tdd and e2e executors, reviews, `fix`, `score` and the pre-plan steps get no advisor text.
- `advisor.enabled` cannot configure or cap the advisor. It only adds prompt text. The advisor is the native Claude Code tool, and your own `advisorModel` setting (or `--advisor`, `/advisor`) decides whether one exists and which model it is. The pairing rule applies: the advisor must rank at or above the step's model, so a Sonnet 5.5 step needs an advisor at or above Sonnet 5.5 (Fable, Opus 5 or later, or Sonnet 5.5), and Claude Code attaches no weaker one, without an error. With no advisor the rules tell the subagent to go on without it.

- Provenance records the flag as `advisor.enabled` in `flags` and the block as the `advisor` section. It cannot see `advisorModel`, so for an A/B pair record the advisor setting and the Claude Code version of both arms by hand; both arms need the same ones.
- Whether the step's reported `totalTokens` includes the advisor's tokens is not known yet. The flag stays off until a live run settles it. The precondition and the A/B decision rule are in `docs/ADR/ADR-009-managed-agent-patterns.md`.

File deletion (ADR-016):

- Never delete a directory with `rm -rf`, `rm -r`, `rm -R`, `rm --recursive`, `rimraf`, `find ... -delete`, or `fs.rm`/`fs.rmSync`/`fs.rmdir`/`fs.rmdirSync` with `recursive: true`: reasonable people block them in their harness, and an unattended step that hits the block stalls.
- The procedure instead: list the files, check that the list holds only what you meant to remove, delete the files one by one, then `rmdir` the empty directories, deepest first.
- Where the rule lives: two rules in the always-true `skills/10x-pipeline/rules/top.md` (ADR-023), so every prompt the router returns carries them whatever the project overrides (the `os-` templates and the `archive` prompt included); one rule in `prompts/manual-verify.md` for its `mktemp -d` scratch directory; one bullet in each orchestrator skill, `skills/10x-pipeline/SKILL.md` and `skills/openspec-pipeline/SKILL.md`.
- Code and tests delete a tree with `removeTree` from `skills/10x-pipeline/scripts/remove-tree.mjs`, the Node form of the procedure. It never follows a symlink, ignores a missing path and refuses an empty path, the filesystem root, the home directory, the working directory and their ancestors.
- `skills/10x-pipeline/test/no-recursive-delete.test.mjs` fails when a banned form appears in `skills/`, `agents/`, `docs/`, `tools/`, `.github/`, `hooks/`, `README.md` or `AGENTS.md`, or when a place above loses the rule. Unclassifiable Node delete-call options fail the source check.
- Shared prompt rules, source scanning and the scoped Claude direct-shell guard enforce their documented boundaries. Runtime limits and host requirements are in the step safety section above.
- Safety upgrades add `ruleFiles`, `agentFiles` and `hookFiles` provenance drift. Stored pending dispatches replay exactly until consumed.

Orchestrator anti-stall:

- Before a Claude call, inspect the exposed Agent schema: set `run_in_background` to `false` only when declared, otherwise omit it. Always supply `description` as `agent-smith <change-id> step <n> <step>` for a numbered step, or `agent-smith <change-id> archive` for archive (OpenSpec uses `<change-name>`). Record the exact description, router change, number and step for each invocation, with any returned agent id.

- Six rules in `skills/10x-pipeline/SKILL.md` (section "Anti-stall rules", the same text in `skills/openspec-pipeline/SKILL.md`) keep the orchestrator from stalling between steps. Rules 1, 2, 3 and 6 hold for every `run` step, rules 4 and 5 for the whole run, and rules 1 and 6 also for the archive subagent.
- If the Agent tool returns a launch notice instead of a final report, the orchestrator ends its turn and continues the Loop when the subagent's final report arrives. It starts no other step and does not poll. The same holds for the archive subagent.
- The same identity check governs on-time and late usage. Loop step 4 takes accounting only for the current matched invocation, replacing step-authored claims with observed collector output; a notification does not prove whole-step tokens. An earlier numbered step's figure follows the late-usage path, even when already present as the current report arrives; unmatched or ambiguous figures remain unattached. Without a verified current total, retain normalized unavailable evidence and any independent counters and run `next` in the same turn.
- A usage figure that arrives after `next` ran for its step is attached with one call of `route.mjs usage` of its own, never alongside another router call, first in the `done` or `halt` branch, before `status` and the pull request step, and in step 1 of the `archive` branch before the archive subagent launches (see "Late usage figure"). The result file is not rewritten and `next` is not called again. A figure that arrives after that point is dropped: any still-missing step shows `-` for tokens in `report.md`, and `compare` counts the side as `usage-incomplete`.
- While the run has not ended in `done`, `archive` or `halt`, the orchestrator does not end its turn into an idle state, unless a launched subagent is still running.
- When you ask what the run is doing, the orchestrator states only what tool output in this session shows, and says so when nothing is running.
- A hand-back from a subagent the orchestrator did not launch for the current step is never a step result (ADR-018). Its own report is the direct result of the awaited Agent invocation or a notification matched to that invocation. A known agent id selects its recorded launch and any supplied description must agree. Otherwise the exact description must identify one recorded launch uniquely, with no conflict against its known id; associate a newly supplied id when that unique launch has no recorded id. Keep separate invocation records even when a neutral retry repeats the description. Only the awaited invocation can supply its completion: superseded invocations and ambiguous description-only notifications cannot advance it. A report from another change, an earlier numbered step or the archive agent cannot complete the awaited step. The orchestrator writes no result file from it and does not call `next` on it; it keeps the step's own report as the only result, under rules 1 and 4. Upgrade note: both skills change; the router and its provenance do not.
- Headless limit of the first rule. It relies on the host giving the orchestrator a new turn when a background subagent ends, as an interactive Claude Code session does. In a headless `claude -p` run the process is expected to end when the orchestrator ends its turn, and the background subagent most likely ends with it: the run exits early instead of stalling. This has not been verified in a live headless run. The interrupted step writes no result file, and the router logged the step when it returned it, so re-running `/agent-smith:10x-pipeline <change-id>` halts with `Step <n> (<step>) has no result. Write <resultFile> first.` When no subagent of that step can still be running, write `{"status":"orchestrator-error","note":"interrupted"}` there and re-run: the router returns the same step with the same prompt and counts no failed attempt (see "Neutral rerun after an orchestrator fault"). Any other status than `done` there (for example `{"status":"failed","note":"interrupted"}`) counts the step as a failed attempt, which the router handles like any other failed step. A killed subagent may leave partial edits in the working tree, and a neutral rerun continues over them; check `git status` before the re-run.

Neutral rerun after an orchestrator fault:

- The orchestrator writes `{"status":"orchestrator-error","note":"<what happened>"}` as the result file when the fault is its own and no subagent of the step is running: the Agent call was refused or errored before any subagent started, for a cause other than the router's `agent`; the prompt could not be passed whole, for example because it was cut; or the call returned neither a reply nor an error. A launch notice is none of them. Both skills carry the rule in step 2 of the `run` branch.
- When the last executed log entry has no result and `last-result.json` parses with that status, `next` consumes the file, appends `{ at, note }` to `neutralRetries` of that entry (the note made one line and cut to 200 code points, empty when absent) and prints `run` with the entry's `n`, `step`, `agent`, `model`, `effort`, `reason` and `resultFile`, the stored prompt and `neutralRetry: { count, cap }`. The orchestrator ends its `Step <n>` line with `Neutral rerun <count> of <cap>.`
- The rerun is the same step: no new log entry, no result, no failed attempt, no tier bump, no rigor rise and no budget use, and in an isolated run no rollback, step commit or reset. The entry keeps `startedAt`, `startSha`, `before`, `tier`, `tierWhy` and `rigor`. A `meta.outcome` of an earlier end is removed, as before any new step.
- The prompt: `next` stores the rendered prompt of each new step as `pendingPrompt` on its log entry, and the intake of a real result of any status deletes it, so `run.jsonl` holds only the prompt of the pending step. The step commit rewrites `run.jsonl` from the log in memory first, so the prompt never lands in a step commit. A rollback snapshot is taken before that rewrite, so the side ref of a failed step under `refs/agent-smith/` holds the on-disk entry with `pendingPrompt`; that ref is local. A step subagent that stages the router's `run.jsonl` itself (for example with `git add -A`) commits the pending prompt with it. Nothing breaks, because the next step commit records the file without the prompt, but the prompt text stays in the run branch history. No prompt names the router files: the `os-apply` guide stages its code by name and never the router files, the `os-verify` guide forbids staging, `manual-verify` allows only read-only git, the tdd and e2e executors commit only the planned set, and the other 10x steps have no staging rule.
- A rerun after a lost report continues over the lost run's edits. `startedAt` stays, so a file the lost run wrote still counts as fresh for the step check, and a later failed result rolls back to the original `startSha`.
- Declare the status only when no subagent of the step can still be running. A background subagent that outlives the declaration would edit the same files as the rerun. That is also why the router never returns the step again by itself when the result file is missing: a missing file can mean that the subagent still runs (see "Orchestrator anti-stall"). The missing-result halt now ends with `When the fault is the orchestrator's own and no subagent of the step is running, write {"status":"orchestrator-error","note":"..."} to rerun the step unchanged.`
- Cap: `limits.maxNeutralRetries` (default 2) per step. An `orchestrator-error` result on a step that already had that many reruns consumes the file and ends the run with a halt, a report and `meta.outcome`: `Step <n> (<step>) hit its limit of <cap> neutral reruns after orchestrator faults (limits.maxNeutralRetries). Needs a human.` The text names the two ways forward: write a result file with the real status (the router verifies the step by its files), or raise `limits.maxNeutralRetries` in `context/foundation/agent-smith-policy.json` and write the `orchestrator-error` result file again, then run `next`.
- `{ "limits": { "maxNeutralRetries": 0 } }` turns it off: the status then reads as any status other than `done`, a failed attempt. A value that is not a non-negative integer halts at load (see "Policy validation").
- Faults that stay failures: an agent type that does not resolve (the router's `agent`) and a reply without a parsable `RESULT:` line, a cut-off one included, are `unknown`, a failed attempt. So is a subagent `RESULT:` line that itself carries `orchestrator-error`: only the orchestrator declares the status, so it writes `unknown` in its place and keeps the other keys. The router cannot tell who wrote the file, so this rule lives in the two skills. The `archive` action has no log entry and no result file, so it has no neutral rerun.
- `compare` counts no reruns, and a lost run has no token figure. Both chains share the rule, because both skills go through `next`.
- Upgrade note: an entry logged before this change has no `pendingPrompt`. For it an `orchestrator-error` result halts without a report (`Step <n> (<step>) was logged without a stored prompt, so it cannot be rerun unchanged after an orchestrator fault.`) and leaves the file in place; replace it with `{"status":"failed","note":"..."}` to count the attempt. `limits` gains a key, so a run in flight when the plugin is upgraded records `provenance.drift` for `limits` at its next `next` call, and `compare` warns `provenance-drift:<side>:limits`. That is expected and changes no routing.
- The rules are in ADR-015. No live run has declared the status yet, and the cap of 2 is uncalibrated.

Policy validation (ADR-022):

- `init`, `next` and `usage` check the merged policy right after loading it, before the run lock, `meta.json`, the log or any commit is written, and halt with `{ "action": "halt", "reason": ... }` on the first problem. The text names the key, the value it got and `context/foundation/agent-smith-policy.json`, and ends `Nothing was written.` The check runs before the chain is resolved, so both chains halt the same way.
- `policyProblems(policy)` in `scripts/state.mjs` checks, in this order: `limits`, `escalation`, `rigor`, `rigor.budgetDelta` and `steps` are objects and `ladder` is a non-empty array; `limits.maxTotalSteps` and `escalation.maxAttemptsPerStep` are positive safe integers; `limits.maxPlanRevisions`, `limits.maxFixLoops` and `limits.maxNeutralRetries` are non-negative safe integers; every `rigor.budgetDelta.<level>` is a safe integer; every `ladder[i]` has a non-empty string `model` and an `effort` that is one of `rigor.effortOrder` (a plain non-empty string when that list is missing or empty); every `steps.<name>` has integer `baseTier`, `minTier` and `maxTier` in `0..ladder.length-1` with `minTier <= maxTier`. `baseTier` may lie outside `[minTier, maxTier]`: `tierFor` clamps it.
- `promptProblem(policy)` in `scripts/flow.mjs` halts on a `{name}` in a prompt template that the router never fills for it: the 17 names of `PROMPT_PLACEHOLDERS` in `scripts/steps.mjs`, or the shorter list of `NARROW_PLACEHOLDERS` for a template the router renders with fewer names (`archive`, `os-archive`, `frame-authority`, `chain-10x` and `chain-openspec`: `id`; `worktree`: `workdir`; `suffix`, which is not rendered: none). A template that does not resolve is left to `checkPrompts`.
- `status` never halts on it: it prints the usual JSON plus `policyProblem` when there is a problem. `risk`, `verify-archive` and `compare` do not check.
- Not checked: `escalation.perFailure`, the bumps, `rigor.fromGoal`, `complexity.*` and the message templates of `archive.*` and `isolation.*`. There is no upper bound on `limits.*`.

PR comment (opt-in):

- Needs the GitHub CLI `gh`, authenticated, and only with `--pr-comment`. Without the flag no comment is posted; the pull request step (see "Pull request (always)") still uses `gh` to open the pull request. The permission a fine-grained token needs is not verified yet (pull requests or issues write is the expected one).
- Opt-in because the comment is visible to collaborators and carries the goal text. The comment goes to the repository named in the pull request url, which for a pull request from a fork is the base repository and can be public. Besides `@mentions`, the report text is posted as it is (links, images and HTML included); a halt can quote subagent text, and the lesson candidates are subagent text too. The PRD wording "is posted" is therefore met only when the flag is given.
- When the run ends (`done`, `archive` or `halt` with a `report`), the orchestrator runs `skills/10x-pipeline/scripts/pr-comment.mjs <change-id>` from the run root, after the pull request step (see "Pull request (always)"). It posts `report.md` as one comment on the pull request that step reported, named with `--pr <url>`, because a run branch pushed without upstream config may not be found by `gh pr view` of the current branch; without a url it uses the open pull request of the current branch. In an `archive` run it posts after the move, with `--report "<archivePath>/agent-smith/report.md"` when the archive succeeded. `--pr` accepts only a `https://github.com/<owner>/<repo>/pull/<n>` url; anything else is a usage error. Initialization accepts boolean `--pr-comment` in either flag form and stores intent in router-owned `meta.json`. Direct router resumes without the flag preserve it. Each explicit skill invocation forwards true when requested and false when absent or explicitly false. Terminal actions carry `prComment: true` only for strict opt-in. Missing legacy intent reads false. Task tools carry no authorization.
- One comment per change per pull request. The first line is a hidden marker, `<!-- agent-smith:pr-report change=<change-id> -->`. A later run edits the comment of the same author that holds the marker, even after you edited it in the GitHub web UI. It never edits another comment. The author is the login from `gh api user`. When that call fails (a timeout, a 5xx or a token without access to `/user`, such as some integration tokens), the script posts nothing and skips with `viewer lookup failed`, because it cannot tell its own comment from one planted by another user. The edit replaces the earlier text; GitHub keeps the edit history.
- Skip reasons, each with exit code 0 and no effect on the run: `gh is not installed`, `gh is not authenticated`, `no pull request for this branch`, `not a git work tree`, `pull request is MERGED` or `CLOSED`, `unsupported host <host>` (no GitHub Enterprise), `viewer lookup failed`, `gh timed out` (each call has 20 seconds; a pull request with hundreds of comments can exceed that while the comment list is read, and the skip posts nothing and cannot duplicate), `comment lookup failed` (also when `gh` prints a list the script cannot read, so an unexpected format cannot create a duplicate), `comment request failed`, a missing, empty or foreign report. A draft pull request gets the comment.
- The orchestrator prints a `PR comment:` line when the flag was given. A missing line means the step was dropped.
- Mentions such as `@name` in the report get a zero-width space after the `@`, so nobody is notified. A body over 60000 UTF-16 code units is cut and says how many characters were omitted.
- Nothing is written to the change folder, so `report.md` cannot say whether it was posted. The result is in the final message only.
- A report with a `Cost (estimate)` line (see "Cost estimate") posts the dollar estimate to the pull request like any other report text.
- The PR scripts accept change ids of at most 100 characters (the marker must fit in the comment head). Both chains enforce this limit at `init`. A legacy longer-id run still exceeds the PR scripts’ limit and ends in `PR comment: skipped, script error` when the comment script is called.
- A run that ended before the pull request existed: open the pull request, check out its branch and run `node <plugin>/skills/10x-pipeline/scripts/pr-comment.mjs <change-id> [--report context/archive/<date>-<change-id>/agent-smith/report.md]` from the project root. The comment goes to the pull request of the branch checked out now, so run it from the branch of that pull request. The result prints the pull request url. `--report` accepts only a file named `report.md` inside a directory named `agent-smith`, whose first line is `# Run report: <change-id>`.

### Chain behavior

Chain switch (`--chain`):

- Every router command takes `--chain 10x|openspec`. Any other value halts before anything is read.
- `init --chain openspec` stores `chain: "openspec"` in `openspec/changes/<change-name>/agent-smith/meta.json`. A 10x `meta.json` never gets a `chain` key, and the provenance `flags` gain `chain` only when `meta.chain` is set, so a 10x run's record keeps its keys.
- `init` without `--chain` is a 10x init. It halts when the live `openspec/changes/<change-name>/agent-smith/meta.json` holds `chain: "openspec"`, and names `--chain openspec`.
- Every other command without the flag uses the stored chain: `chain: "openspec"` in the live `meta.json`, or, when the live folder is gone, in the `meta.json` of an archive folder of the name, unless a 10x change uses the name, live under `context/changes/` or archived under `context/archive/`. Otherwise it is a 10x command. A `--chain` that contradicts the stored chain halts. A live 10x run counts as a stored chain too: `--chain openspec` on a name whose `context/changes/<change-name>/agent-smith/meta.json` exists halts, writes nothing and says the change is a 10x run.
- `archive` is not a change name for the OpenSpec chain, because `openspec/changes/archive/` is OpenSpec's archive folder: every command that resolves to the OpenSpec chain halts on it and writes nothing.

Run state and collisions:

- The shared persist-before-unlink intake, completed-owner result recovery, atomic publication, locked temp cleanup and strict/tolerant log rules in "State publication and log recovery" apply to the OpenSpec run folder.
- Run state (`run.jsonl`, `meta.json`, `last-result.json`, `report.md`) and the verdict file `verify.md` live in `openspec/changes/<change-name>/agent-smith/`, so `openspec archive` moves them with the change. OpenSpec's `validate`, `status` and `archive` accept the extra folder (`evidence/check-3-cli.md`).
- `init --chain openspec` halts, and writes nothing, when `context/changes/<change-name>/` exists: a 10x change already uses the name (D8). A run branch belonging to a 10x change holds that folder, so a run of the other chain on it halts the same way. Both chains share the configured branch prefix, worktree directory convention and recovery namespace.
- Run isolation works as in "Run isolation" above, using the configured literal prefix plus change name for fresh setup (default `agent-smith/<change-name>`) and the validated recorded branch for saved runs. The shared setup script runs with `--chain openspec` and copies `openspec/changes/<change-name>/` into the new worktree with preserved timestamps only when it creates the run branch. The start commit commits `openspec/changes/<change-name>/`. The isolation gate and `init --archive` check that git does not ignore `agent-smith/run.jsonl`, `agent-smith/meta.json`, `agent-smith/report.md` and `tasks.md` of the change. The shared timestamp checkpoint restores the file times of `tasks.md` and `verify.md`.
- With isolation off, the `os-apply` guide commits the code it writes under a typed subject (`<type>(<id>): <summary>`, never `chore`), but nothing commits the change folder: the router makes step commits only in an isolated run, and the pre-archive commit and the `os-archive` commit hold only `openspec/` paths. The skill's final message says so; commit the files of the change folder yourself.
- `guardArchived` halts `init`, `next` and `status` for a name whose live folder is gone and whose archive folder exists under `openspec/changes/archive/`. OpenSpec stamps no status, so the shared guard treats live folders as present. The additional init-only preflight rejects a live OpenSpec folder beside any matching archive before acquiring the run lock, naming all paths without modifying files, index, refs or router temps. Matching includes date-prefixed ids kept verbatim by OpenSpec and excludes suffix collisions. Setup and post-init cleanup follow the shared lifecycle above with `--chain openspec`.

Routing order (D4):

- The router reads the change from files and never runs the `openspec` CLI (D2). An artifact exists when its file does. Planning is complete when `proposal.md`, at least one `specs/**/*.md` and `tasks.md` exist (predicate A); `design.md` is optional. OpenSpec's own `isPlanningComplete` stays `false` without `design.md` while `openspec instructions apply` already reports `state: "ready"`; the router follows apply readiness, because `os-apply` is the step that needs it.
- A task row is a line the CLI's own pattern matches (OpenSpec 2.0.0, `TASK_LINE_PATTERN`): a list item under `-`, `*`, `+` or `1.`/`1)`, nested rows included, with a checkbox that holds at most one non-space marker. A row is complete only for `x` or `X`; every other marker (`[ ]`, `[]`, `[~]`) is open work. A link bullet such as `- [doc](x.md)` and a bracket with a word in it such as `- [WIP]` are no rows, as in the CLI.
- The order: no change folder halts; planning incomplete returns `os-propose` (the reason names the missing files); a `tasks.md` with no task row halts for a human; an open row returns `os-apply`; every row ticked and no verified `os-verify`, or a verified step after the last one, returns `os-verify`. Otherwise the verdict of `verify.md` decides (see "Verify verdict and fix loop").
- `os-propose` writes the planning artifacts only. `os-apply` implements every open task and ticks it. `os-verify` runs the verify skill read-only and writes `verify.md`. Each prompt carries a decision guide (`skills/openspec-pipeline/prompts/os-propose.md`, `os-apply.md`, `os-verify.md`, `os-archive.md`, see the `README.md` of that folder): the subagent decides from evidence and lists the decision as an assumption, and with no evidence-backed answer ends `blocked` with `signals.needsHuman`, which halts the run.

Step verification:

- `os-propose`: the status is `done`, planning is complete and at least one artifact file (`proposal.md`, `design.md`, `tasks.md` or a `specs/**/*.md`) is newer than the step start.
- `os-apply` (template `os-apply`): the status is `done` and `tasks.md` has more ticked rows than when the step started (`before.ticks` in the log entry).
- `os-apply` in fix mode (template `os-apply-fix`): the reported status decides, as for the 10x `fix` step; the next `os-verify` checks the code.
- `os-verify`: the status is `done`, `verify.md` is a regular file newer than the step start and its header parses. The log entry gets `review: { verdict, critical, warnings }`, so `status` and the `## Review findings` section of `report.md` show it. It never has an open part: ADR-011 does not apply.
- A step that fails its check counts as a failed attempt: its retry runs one tier up, the run halts after `limits.maxAttemptsPerStep` (3) failed attempts of the same step, and the rigor level rises as for any failed step.
- An `orchestrator-error` result is no step result: the router returns the same `os-` step with the same prompt (in fix mode its `{findings}` included) and the same `before.ticks`, as in the 10x chain (see "Neutral rerun after an orchestrator fault").

Verify verdict and fix loop:

- `verify.md` starts with three lines: `Verdict: PASS`, `Verdict: PASS WITH WARNINGS` or `Verdict: FAIL`, then `Critical: <n>` and `Warnings: <n>`. Then `## Critical` and `## Warnings` with one `- ` line per issue, then the skill's report. A `Critical` count above 0 reads as `FAIL` whatever line 1 says, and so does a `- ` line under `## Critical` under a lower count: the critical count is the larger of the header count and the number of lines, so the file is never read as cleaner than it says.
- The router reads the verdict from the file each time it decides, not from the log copy, so a human who fixes the code or edits `verify.md` after a halt is routed on the file. A `verify.md` that a fresh `os-verify` leaves malformed fails that step; one that becomes unreadable or malformed after a verified `os-verify` halts the run and names the file and the line that does not parse.
- `PASS` or `PASS WITH WARNINGS` ends the run `done`, or, for a run started with `--archive`, goes to the archive branch below.
- `FAIL` returns `os-apply` with template `os-apply-fix` while fewer verified fix steps than `limits.maxFixLoops` (2) ran. The prompt carries the `- ` lines under `## Critical` (at most 20, each made one line and cut to 300 code points) as `{findings}`, or `see verify.md` when there are none. A verified fix step returns `os-verify`. Only verified fix steps count toward the cap, unlike the 10x fix loop, which counts every `fix` attempt; failed fix attempts are bounded by `limits.maxAttemptsPerStep` and the step budget.
- `FAIL` at the cap halts: `OpenSpec verify FAIL after <n> fix loops. Needs a human. Fix the issues, set the first lines of <verify.md path> to "Verdict: PASS" and "Critical: 0", then run /agent-smith:openspec-pipeline <change-name> again.` In an isolated run it ends with `Commit the edit in the run worktree first: a failed step rolls back uncommitted edits.`

Tiers, rigor and budget:

- `skills/openspec-pipeline/policy.json` `steps` holds the four steps with the pins of the 10x step each one mirrors (D9, uncalibrated): `os-propose` as `plan` (base 5, min 2, max 7, interactive), `os-apply` as `implement` (base 3, min 2, max 7), `os-verify` as `impl-review` (base 3, min 2, max 6, interactive), `os-archive` as `archive` (pinned at 3, interactive).
- The tier is the base tier, plus one rung per trailing failed attempt of the same step (`escalation.perFailure`), clamped to the step's bounds, with the effort floor of `rigor.minEffort` for the interactive steps. The fix step is an `os-apply` step and gets no bump of its own: a verified `os-apply` before it leaves no trailing failure, so it runs at the `os-apply` base unless an earlier fix attempt failed. No phase-count bump, simple-change discount, score shift, cheaper first attempt (`escalation.firstAttempt.templates` names only 10x templates) or `rigor.tierOffset` (it names `impl-review`) applies, because an OpenSpec change has no plan.
- Rigor starts from the goal class or `--rigor` and rises with failed steps and `signals.rigor`. There is no plan, so neither the phase count nor churn risk raises it, and `risk --chain openspec` reports no plan hits.
- The step budget is that of the 10x chain (12, 19 and 24). The longest failure-free path is 7 steps (propose, apply, verify, then two rounds of fix and verify); a third `FAIL` halts on the fix-loop cap before the `lean` budget.

Archive (`--archive`, D5):

- The Manual gate of the 10x archive (ADR-014) is mirrored in the skill's `archive` branch and is dormant here: `summary.manualPending`, `manualUnproven` and `uncommittedTicks` are always `[]`, because there is no plan and an open `tasks.md` row halts first. A no would point at `openspec archive <change-name> --yes --json`.
- `init --archive` stores the flag as for the 10x chain and checks that the project is a git work tree and git ignores none of the router files named above.
- At a passing verdict the router runs the same Git safety checks as the 10x archive. OpenSpec changes have no `created:` line to validate. The router halts when `tasks.md` has an open row or when the target folder exists. For an existing target it names `archive_target_exists`, the CLI error it would hit. A halt carries `archive: "skipped: ..."` and `committed`, as in the 10x chain.
- Then it writes `report.md`, whose `Archive: requested` line names the CLI command `openspec archive <change-name> --yes --json`, commits `openspec/changes/<change-name>/` with `archive.commitMessage`, and returns an `archive` action with the `os-archive` prompt at the pinned tier, `archivePath`, `commit` and `ignored`.
- `archivePath` is `openspec/changes/archive/<local YYYY-MM-DD>-<change-name>`, or `openspec/changes/archive/<change-name>` when the name already starts with a date, as the CLI names it.
- The orchestrator runs the `os-archive` prompt in one subagent. It runs `openspec archive <change-name> --yes --json` once from the run root, never the archive skill or `/opsx:archive`, and on success commits only the paths the CLI changed (`openspec/changes/<change-name>/`, the archive folder and `openspec/specs/`) as `chore(archive): close <change-name>`; when anything else is staged it ends `blocked` without committing. A CLI error (for example `archive_target_exists` or a validation error) ends it `blocked` with each error's `code` and `message` quoted, plus `fix` when supplied, without a retry. The step has no log entry, no usage figure and no report row, as the 10x `archive` step.
- `verify-archive <change-name> --chain openspec [--path <p>]` then reads files only: `archived: true` when the archive folder exists and `openspec/changes/<change-name>/` is gone. It prints `{ archived, path, report }`; OpenSpec stamps no status, so there is no `archivedAt`. Without `--path`, several matching folders give `archived: false` with an `ambiguous` list. With a `--path` that is not an archive folder of the name, the reason lists the `<date>-<change-name>` folders that exist.

Read-only commands:

- `verify-archive` includes log diagnostics from the live folder and selected archive, including failed truth checks. An exact `--path` selects that archive. Ambiguous output includes problems from all matching candidate logs, with file paths preserving attribution. Archive truth conditions, exit codes and ambiguity information follow the existing lookup rules on both chains.
- `status <change-name> --chain openspec` adds `openspec: { planningComplete, tasks: { total, complete } }`, the reading the contract test compares with the CLI.
- `compare <change-name> --chain openspec` reads each side from `openspec/changes/<change-name>/agent-smith/` or `openspec/changes/archive/<date>-<change-name>/agent-smith/` (a live folder wins, with the same warning as for 10x). The baseline procedure of "Baseline comparison" is written for the 10x chain; `baseline-policy.json` pins no `os-` step. The input files of a side exclude `proposal.md`, `design.md`, `tasks.md`, `verify.md` and `complexity.json`, which a run produces, so a `proposal.md` that existed before the run is not listed as an input either. Pass `--chain openspec`: without it `compare` takes the chain from the project it runs in, not from `--routed` or `--baseline`.
- `risk <change-name> --chain openspec` prints the churn numbers with no plan paths.

**Late usage**

- `usage <change-name> <n> --usage-file <path> --chain openspec` attaches a late usage figure under the same rules as 10x. Numeric flags are available for legacy steps without recorded evidence. Its archive-state commit holds `openspec/changes/<change-name>/`. Refused or identical usage preserves state temps. Eligible archive usage completes read-only eligibility checks, removes recognized temps, then publishes and stages. A failed restoration identifies incomplete recovery and the affected file. Dropped in this chain (D10): `score`, the pre-plan steps, the phase executors, `manual-verify` (so no `--chrome`), the code re-plans, plan review, the confirmation round, lesson candidates, the advisor text (`advisor.templates` names no `os-` template) with the shipped restricted map naming only `score` in the 10x chain. Limits:

- The router reads OpenSpec state from files, so it can drift from the OpenSpec parser. `skills/openspec-pipeline/test/openspec-contract.test.mjs` compares `status --chain openspec` with `openspec instructions apply --change <name> --json` on fixture changes (`OPENSPEC_BIN`, default `openspec`). An unavailable executable or failed version probe skips fixtures locally when `CI` is absent or empty and throws when `CI` is nonempty. A successful probe must return exactly `2.0.0`. Successful incompatible or malformed version responses fail both locally and in CI. CI installs and explicitly selects `@fission-ai/openspec@2.0.0` under the approved CI-tool exception. A pin upgrade requires a deliberate commit and successful execution of every real contract fixture. The original five fixtures retain apply readiness, including optional design, and task-count compatibility. Additional isolated fixtures cover custom/core setup, twelve-workflow legacy update, retained customizations and project bytes, read-only preview, repeated-update idempotence, tracked shared skills and fresh-checkout Claude links, valid/invalid validation and archive merge, preservation and structured errors. Setup fixtures isolate HOME and XDG configuration/data/cache paths and disable telemetry and update checks. Shared Git availability failures also throw when `CI` is nonempty. The conditional skip inventory is in `skills/openspec-pipeline/test/README.md` and beside the workflow installation step. The contract fixtures bound parser drift.
- The task row pattern is a copy of the CLI's `TASK_LINE_PATTERN` of version 2.0.0. A later CLI version can change it, and the router then drifts until the pattern is updated. The contract test covers standard rows and rows in every list form and marker.
- `tasks.md` and `verify.md` are read only as regular files whose real path lies inside the change folder, at most 256 KiB and 64 KiB. A larger or symlinked file reads as unreadable: `tasks.md` counts no row, and `verify.md` fails the `os-verify` step or halts the run with the reason. Control and format characters in the critical lines that reach the fix prompt become a space or are dropped. The caps are constants in `skills/openspec-pipeline/scripts/openspec.mjs`, not policy keys.
- A router call without `--chain` on a name that only an OpenSpec change holds, such as `next demo` run by hand before `init`, resolves to the 10x chain and halts with `No change folder. Run /10x-new demo first.`; it creates no folder. The orchestrator skill always passes `--chain openspec`.
- A change whose schema skips specs (`skip_specs`) never satisfies predicate A. The `os-propose` guide ends such a step `blocked` with `signals.needsHuman`, so the run halts at once; a subagent that ignores the rule makes the run return `os-propose` until the attempt cap halts it.
- Archive date at midnight: the router computes `archivePath` with the local date when it returns the `archive` action, and the CLI takes the local date when it runs. A run that crosses midnight between the two gets another folder name, and `verify-archive --path` reports `archived: false`; its reason lists the folder that exists.
- Changes hosted in a store (`--store`) are not supported (D3): such a change sits outside the worktree and outside the rollback.
- `verify.md` has no `### F<n>` blocks or `Decision` lines, so ADR-011's open-findings routing does not apply and a passing verdict with warnings never halts.
- The guides passed five live probes. The whole skill completed `openspec-project-rules` on 2026-11-09 with verification PASS, zero critical findings and zero warnings, and the CLI archived the change. See the [archived probes](../context/archive/2026-11-09-openspec-pipeline/evidence/check-3-live.md), [archived plan row 5.6](../context/archive/2026-11-09-openspec-pipeline/plan.md) and [run report](../openspec/changes/archive/2026-11-09-openspec-project-rules/agent-smith/report.md).
- Upgrade note: the policy gains `steps` and `prompts` keys, so a 10x run in flight when the plugin is upgraded records `provenance.drift` for `prompts` and `steps` at its next `next` call, and `compare` warns `provenance-drift:<side>:prompts,steps`. That is expected and changes no routing. A 10x run never gets a `chain` key.

### Delegation migration and rollback

Pin a coherent plugin revision for each run and start fresh Claude sessions with verified depth and awaited-mode settings. Historical inline and file prompts remain byte-exact through retries, including flat-delegation instructions and legacy agent selection. Settings changes never rewrite pending prompts. Before downgrade, await or stop children through their existing native parent/runner and prove closure, then resolve every pending child-enabled dispatch (including neutral retries) on its enabling revision through completion or router-owned recovery. Otherwise keep that run pinned and report the unavailable recovery prerequisite with `signals.needsHuman`. Only then revert the feature through preserving Git history and restore prior host settings in a fresh session. Retain logs, evidence and failed-work refs. No persistent schema migration is needed. The twelve-cell final-candidate matrix remains [pending](../context/archive/2026-11-16-nested-step-delegation/evidence/acceptance.md); primitive probes are not full pipeline support claims.
