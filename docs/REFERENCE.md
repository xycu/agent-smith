# agent-smith reference

Full behavior of `/agent-smith:10x-pipeline`: routing, run isolation, review routing, rigor, archive, pre-plan steps, budget, executors, manual verification, scoring, reports, comparison, provenance, opt-in features and limits. The OpenSpec chain, `/agent-smith:openspec-pipeline`, has its own section at the end; everything it does not name works as in the 10x chain. For install and a first run, see the [README](../README.md). Decisions and their reasons are in [`docs/ADR/`](ADR/).

## `/agent-smith:10x-pipeline <change-id> [goal] [--archive] [--chrome false] [--pr-comment]`

Runs a 10xDevs change end to end: plan, plan review, implement, implementation review, fix. With `--archive` it also commits the change folder and archives the change when the run is done (see "Archive (opt-in)").

Requirements in the target project:

- The 10x toolkit skills: `10x-plan`, `10x-plan-review`, `10x-goal-implement`, `10x-impl-review`.
- A change folder made with `/10x-new <change-id>`.
- Node.js 24 or later (ADR-006). Claude Code does not guarantee a `node` on PATH (a native install is a single binary), so install it yourself. Churn risk also reads `git` history; without it the router flags no hot path. `--archive` needs a git work tree and the `10x-archive` skill.
- The `10x-research` and `10x-frame` skills are used when a pre-plan gate opens or when a `thorough` run loops (see "Pre-plan steps"). A step whose skill is missing fails three times and halts the run. A run that stays at `standard` or `lean` runs no such step and needs neither skill.
- The `score` step at `standard` and `thorough` needs no toolkit skill: its rules are in `skills/10x-pipeline/prompts/score.md` (see "Complexity score").

How routing works:

- `skills/10x-pipeline/policy.json` defines a ladder of model/effort tiers, a base tier per step, and escalation rules.
- `skills/10x-pipeline/scripts/route.mjs` reads `plan.md` (`## Progress`) and `reviews/*.md` (verdict, finding counts) after every step and returns the next step, model, effort and prompt. It stays a script: it makes no model or network call (ADR-006). The complexity score comes from a step it schedules (ADR-007).
- The tier goes up for large plans, `RETHINK`/`REVISE`/`REJECTED` verdicts (a `REVISE` or `NEEDS ATTENTION` counts when findings are still open) and failed attempts. It goes down after a clean review and for a simple change (a small plan or a short goal). A hard keyword in the goal, such as `refactor` or `security`, keeps the first plan at the plan step's base tier.
- In a run with its own worktree (see "Run isolation") the first attempt of an implement step (`implement`, `implement-segment`, `implement-tdd`, `implement-e2e`) runs one tier lower (`escalation.firstAttempt`), because a failed attempt is rolled back and retried. No drop applies when that step already failed in the run or the simple-change discount applies, and the clamp and the effort floor still bound it: a tdd or e2e step on the floor keeps its tier and `tierWhy` reads `-1 first attempt not applied (clamp or floor)`. An execution-sum score up shift cancels it the same way (`-1 first attempt not applied (cancelled by the score shift)`), and the step runs on the tier it would have without both. The entry carries `cheap: true` only when the drop survived the score shift, the clamp and the floor. Its failure raises no rigor and uses no step budget, but it counts as a failed attempt for the retry tier, `maxAttemptsPerStep` and the code re-plan, so the retry runs two tiers above it. The drop counts as a discount for the score down shift, so the two never stack. A failed cheap attempt is neutral only for rigor and the step budget, on purpose: the implementation review after it still runs one tier up, and for the rest of the run the simple-change discount is withheld and the score down shift is blocked, as after any failed step. `drop: 0` turns it off.
- The ladder has an `opus/medium` rung between `sonnet/high` and `opus/high`. A move up from `sonnet/high` reaches `opus/medium` first for a non-interactive step, such as implement or fix.
- The first plan reads the goal text. A brief goal (at most 25 words, no hard keyword) lowers the plan tier by 2 and earns the simple-change discount. Any other goal lowers it by 2, and a goal with a hard keyword lowers it by nothing. The word limit and the keyword list sit under `complexity.firstPlan` in `policy.json` and can be overridden per project.
- Effort floor: plan, plan review and implementation review ask questions, so they never run below the floor in `rigor.minEffort` for the run's rigor level. The floor beats the simple-change discount, and the report marks a step as simple only when the discount survived. The floor also skips a rung whose own effort is below it, because the ladder is not ordered by effort: at `standard` and `thorough` such a step moves from `opus/medium` up to `opus/high`. A failed attempt of an interactive step moves it one rung up counting only the rungs that clear its floor, so a step that starts on `sonnet/high` runs `opus/high` on its second attempt and `opus/xhigh` on its third.
- A step counts as failed when the subagent does not report `done` or the expected file did not change. A result with the status `orchestrator-error` is the exception: it is no step result, and the router returns the same step again with no failed attempt (see "Neutral rerun after an orchestrator fault").
- Both reviews apply their own fixes (`prompts/plan-review-apply.md`, `prompts/impl-review-apply.md`): a finding with a clear fix is applied to `plan.md` (plan review) or to the code, tested and committed (implementation review) before the step ends, and marked `Decision: APPLIED` in the review file. Findings that need an owner decision stay `PENDING`. The `Verdict` and `Findings` header counts stay as measured before the edits, and the router now routes a `REVISE` or `NEEDS ATTENTION` on the findings that are still open (see "Review routing on open findings"). A review without `### F<n>` blocks that carry a `Decision` line is routed on the header counts, as before.
- The archive step is not moved by any of these rules: the policy pins its tier.
- From `standard` up the router runs one `score` step before the first plan, on a tier the policy pins. A subagent scores the change on six factors and writes `complexity.json`. The cognitive sum can move the first plan up one tier. The execution sum can move an implement step up or down one tier; a down shift needs measured churn risk with no hot path and a few more guards. A failed scorer is skipped after its attempts and never halts the run. See "Complexity score".
- At rigor `thorough` the router can run `research`, `domain-brief` and `frame` before the first plan, and a plan review `RETHINK` or a repeated `REVISE` re-plan can send the run back to `frame` or `research` once before the re-plan. Both are off below `thorough` by default. See "Pre-plan steps".
- From `standard` up the router can swap the plain implement step for a phase executor (`implement-e2e`, `implement-tdd`, `implement-segment`), and re-plan after code ran (`plan-replan` after two implement failures in a row, `plan-rejected` after a first `REJECTED` review). A tdd or e2e step also needs a code commit to count as done, and a step that ends `blocked` falls back with no failure counted. See "Phase executors".
- At every rigor level the router runs `manual-verify` before the first implementation review when a Manual row is pending: a subagent proves every pending Manual row it can, with evidence, and gives a reason for each row it cannot. It runs on `sonnet/medium` first and once more on `sonnet/high` when rows stay pending, outside the extra-step pool, and the run goes on whatever it leaves. See "Manual verification".
- The run halts for a human after repeated failures, too many plan revisions or fix loops, a review that leaves an open finding (see "Review routing on open findings"), or when the step budget is spent.

Run isolation:

- Each run works in its own linked git worktree on the branch `agent-smith/<change-id>`. `isolation.require` in `policy.json` ships `true`.
- `init` halts, and writes nothing, when the project is not a git work tree, is the main checkout instead of a linked worktree, has a detached HEAD, is on a default branch (`isolation.defaultBranches`, plus the branch `origin/HEAD` points to) or on a branch that does not start with `isolation.branchPrefix` (`agent-smith/`), or when git ignores a router file of the change. The halts for no git work tree and for the main checkout name the opt-out.
- The first `init` of a run stores `isolated: true` and `branch` in `meta.json`. A resume on another branch halts. A run that already has executed steps and was not started isolated halts at `init` and names the opt-out, so a run is isolated from its first step or not at all.
- The orchestrator makes the worktree before `init`, at `<project root>/.claude/worktrees/agent-smith-<change-id>`. The run root is that directory plus the project root's path below the repository top level, if any. When git does not ignore `.claude/worktrees/`, the orchestrator adds it to the local exclude file (`.git/info/exclude`), never to `.gitignore`.
- Only when it creates the run branch does it copy the change folder into the worktree, keeping file times (`cp -Rp`). A resume reuses the worktree, or adds one for the existing branch, and copies nothing, so edit the run's files in the worktree. An in-flight run in the main checkout stays there and halts at `init` until the project opts out.
- Every other input (the project override `context/foundation/agent-smith-policy.json`, `context/foundation/`, `context/domain/`, `context/map/`, the code) is read as committed at the branch point. Commit it before a run. The orchestrator prints one line that lists the uncommitted paths of the main checkout outside the change folder when it creates the branch.
- Every prompt of an isolated run starts with the rules of `skills/10x-pipeline/prompts/worktree.md`, which name the run root and tell the subagent to work only there. The orchestrator runs every router call with `cd` into the run root.
- The change folder in the main checkout is a stale copy: the run's copy lives on the run branch. Remove or stash the main-checkout copy before you merge the run branch, because git refuses a merge that would overwrite untracked files.
- A run that ends `done` without `--archive` leaves `report.md`, the last `run.jsonl` entry and `meta.json` uncommitted in the worktree. Commit them before the merge and before `git worktree remove`, which refuses a worktree with modified or untracked files.
- With `--pr-comment` the orchestrator posts from the main checkout, whose branch holds the pull request, and passes the worktree's report with `--report`.
- Open question: `.claude` is a protected directory. Claude Code exempts "Claude's own git worktrees under `.claude/worktrees/`", and the docs do not say whether a worktree made by `git worktree add` counts. If it does not, Edit and Write under the worktree prompt even in `acceptEdits`, and an unattended run stalls there. A live run has not checked it yet.
- Opt out with `{ "isolation": { "require": false } }` in `context/foundation/agent-smith-policy.json`: no worktree, no `meta.isolated`, no start or step commit, no rollback and no cheaper first attempt; the run works in the project root as before. A project without git needs it. The router and the orchestrator read only the boolean `true` as on. The opt-out acts on a run that starts after it: a run that started isolated keeps `meta.isolated`, so when it resumes in its worktree the router still makes its step commits, rollbacks and cheaper first attempts there. Finish such a run before you opt out.
- Start commit: the first `init` of an isolated run records `meta.baseSha` (HEAD before the commit, so churn and the baseline procedure are unchanged), writes `meta.json`, then commits the change folder as `chore(<id>): start run` (`isolation.commit.startMessage`) and stores the hash in `meta.startCommit` (`null` when there was nothing to commit). The first step starts from that commit, so a rollback of the first step keeps `research.md`, `frame.md`, a ready `plan.md` and an edited `change.md`. A hook that rejects the commit halts `init`; the next `init` tries again. A resume never makes one.
- Step commits: after each verified successful step the router commits what the step left as `chore(<id>): step <n> <step>` (`isolation.commit.message`), before it reads any file for the next decision. Nothing to commit gives no commit. The log entry records `startSha` (HEAD when the step started, read with `isolation.gitTimeoutMs`; a HEAD that cannot be read halts the run before the step is logged) and `commit`; `report.md` shows `ok (<short hash>)` and `status` shows `commit`. Hooks and signing apply; the router never passes `--no-verify` and never pushes. A staged file left by the step, or a hook failure, halts the run with git's message, and the router unstages its own add.
- Rollback: after a failed step the router snapshots the worktree, staged and untracked files included, as a commit under `refs/agent-smith/<id>/<run>/failed-<n>` (`isolation.rollback.ref`, which must render under `refs/agent-smith/`; `<run>` is the first 12 hex characters of the run's start commit, `meta.startCommit` or, when that was empty, the first step's `startSha`, so two runs of one change id, such as the baseline arms, never share a ref; plumbing, so no hook runs), resets the worktree to the step's `startSha` with `git reset --hard` (no `git clean`, so ignored files stay), sets back the file times of `plan.md` and the two review files, and only then decides the next step. The retry, a `plan-replan` or any other next step starts from `startSha`, and the entry gets `rolledBack`. Commits the failed step made itself, such as the phase commits of `/10x-goal-implement`, leave the branch with the reset and stay reachable from the side ref, whose parent is the head the step left; the retry redoes them. Uncommitted edits present when the step started (a human's edits after a halt, what a fallback step left) are swept into the side ref too, so commit them before you resume. Inspect a snapshot with `git show <ref> --stat` (the entry's `rolledBack` or `kept` value) and cherry-pick from it.
- Not rolled back: a `blocked` fallback step, a failed `score` attempt, a tdd or e2e step whose rows are listed as `uncommitted` (the `implement-retry` step needs those ticks and that code) and a step whose result carries `signals.needsHuman`. When the call that rolled back ends in a halt (budget, the attempt cap, a `decide` halt, a `Router error:`), the router undoes the reset first: the branch is back at the head the failed step left, the worktree holds the partial edits with their file times, and the entry gets `kept`. A kept or rolled-back step is never rolled back again. `report.md` lists both under `## Rolled-back steps`, a kept one as `kept (run halted)`.
- The router never resets, commits in or writes refs from the main checkout: the step commit and the rollback check that the run is in a linked worktree with HEAD on `meta.branch`, and halt otherwise. It never deletes the run branch, the worktree or a side ref.
- `isolation` is a policy section, so provenance hashes it and `compare` warns when two arms differ in it.
- Release note: `isolation.require` ships `true`, so a run in the main checkout now halts at `init` until it runs in a worktree or the project opts out. It shipped as a breaking change (`feat!`). The rules are in ADR-010.

Review routing on open findings:

- The router reads each `### F<n>` block of a review file: its `**Severity**` line (CRITICAL, WARNING or OBSERVATION; a line that names none counts as a warning) and its `**Decision**` line. The decision is the first run of ASCII letters after `**Decision**:`, upper-cased, so `APPLIED - abc1234` reads `APPLIED` and `ACCEPTED-AS-RULE: <title>` reads `ACCEPTED`. A finding is closed when its decision is in `review.openFindings.closedDecisions` (default `APPLIED`, `FIXED`, `ACCEPTED`, `SKIPPED`, `DISMISSED`; `FIXED` is the word the review skills' own triage writes). A missing, `PENDING` or unknown decision is open, and an observation never counts. A header count above the CRITICAL or WARNING blocks the file lists adds the difference as open, so a review that lists fewer blocks than its header claims is never read as cleaner than it says.
- A review is "aware" when `review.openFindings.enabled` is `true` (the default) and at least one block has a `Decision` line. An aware plan review `REVISE` with no open critical and open warnings within `review.reviseToleranceWarnings` goes on to implement. Any other open count halts the run for a human with the open finding ids. `RETHINK` keeps its routing.
- An aware implementation review `NEEDS ATTENTION` with no open critical and open warnings within the same tolerance goes to `done` with no `fix` step. Any other open count halts. `review.fixOnNeedsAttention` applies only to a review without `Decision` lines. `REJECTED` keeps its routing. `review.reviseToleranceWarnings` therefore bounds the open warnings of both reviews (before, it bounded the plan review only), and the tolerated open warnings stay visible in `## Review findings` of the report.
- `review.openFindings.onOpen` is `"halt"` (default) or `"retry"`. With `"retry"` an aware `REVISE` above the tolerance re-plans and an aware `NEEDS ATTENTION` above it runs `fix`, instead of halting. It brings back neither a re-plan for a `REVISE` with nothing open nor a `fix` for a `NEEDS ATTENTION` with nothing open or open warnings within the tolerance. `review.openFindings.enabled: false` is the full opt-out: every review routes on the header counts. A value of the wrong shape (`openFindings` not an object, `closedDecisions` not an array of non-blank strings, `onOpen` other than `halt` or `retry`) reads as the shipped default, a non-boolean `enabled` reads as off, and none of them halts the run.
- Fallback: a review with no `Decision` line in any block (a project that overrides a review prompt with a plain string, or a review written by hand) routes on the measured header counts: same step, same `reason`, same tier as before this change.
- A `REVISE` that carries `Decision` lines never re-plans under the default `halt`. The `preplan.loops` REVISE-to-research loop and `limits.maxPlanRevisions` therefore act on a `REVISE` only for a review without `Decision` lines, or with `onOpen: "retry"`. `RETHINK` still reaches both.
- Halt text and the way back in: `Plan review REVISE left <n> open critical and <m> open warnings (F1, F3). Needs a human.` (or `Implementation review NEEDS ATTENTION ...`), then `Set each finding's Decision in <review path> (<closed words>) or triage with /10x-plan-review <review path>, then run /agent-smith:10x-pipeline <change-id> again.` (`/10x-impl-review` for the implementation review). Findings counted in the header with no block are named as a count. In an isolated run the text ends with `Commit the edit in the run worktree first: a failed step rolls back uncommitted edits.`, because the next failed step resets the worktree to its `startSha` and would restore the open lines. After the edit, run that command.
- Confirmation round (`review.confirmRounds`, per rigor level, `0` everywhere by default, so off): after an aware plan review `REVISE` or implementation review `NEEDS ATTENTION` that applied at least one CRITICAL or WARNING fix (`APPLIED` or `FIXED`) and left nothing open, the router returns one more review of the same kind (same step name, template `plan-review-confirm` or `impl-review-confirm`) before it goes on. The confirm prompt tells the subagent to read the earlier round, review the current plan or code in full and check every `APPLIED` fix as a claim. The confirmation is routed by the same open-findings rule: an open finding halts (or retries), and one that again applied fixes and left nothing open schedules the next confirmation only while fewer than the level's count ran. The cap counts every executed confirmation of that kind, failed ones included. A plan review confirms only before implementation starts. `RETHINK`, `REJECTED`, a review without `Decision` lines and a level with `0` or a malformed value never confirm.
- Budget cost of a confirmation round: each round is one more `plan-review` and one more `impl-review` step on the longest path. `rigor.budgetDelta` ships sized for the path without the round, so a project that turns it on raises `rigor.budgetDelta` by 2 per round at each level that turns it on, for example `{ "review": { "confirmRounds": { "standard": 1 } }, "rigor": { "budgetDelta": { "standard": 7 } } }` for the shipped `5`. Without it the budget can halt a run that has a failed step to retry.
- The log entry of a verified review step carries `review`: `{ verdict, critical, warnings }` (measured, from the header) plus `openCritical` and `openWarnings` for an aware review. `status` shows it per row, and `report.md` lists it under `## Review findings` (see "Usage report").
- Upgrade note: the policy gains keys and the two apply prompts and the two confirm templates change, so a run in flight when the plugin is upgraded records `provenance.drift` for `review` and `prompts` at its next `next` call, and `compare` warns `provenance-drift:<side>:prompts,review`. That is expected and changes no routing. A review with `Decision` lines that a run in flight already holds is routed on its open findings from its next `next` call.
- Behaviour change for the release PR: a `REVISE` or `NEEDS ATTENTION` whose findings are all closed now continues instead of re-planning or running `fix`, and an open finding now halts instead of re-planning. `onOpen: "retry"` restores the old reaction to open findings. Whether it ships as `feat` or `feat!` is the owner's call at commit time. The rules are in ADR-011.

Rigor:

- Every run has a rigor level, `lean`, `standard` or `thorough`, stored in `meta.json` and kept on resume. It starts from the goal class (a short goal is `lean`) or from `init <id> --rigor <level>`, and it only rises: with 3 or more phases (`standard`) or 6 or more (`thorough`), after failed steps (a failed cheap first attempt does not count), when the plan or the diff touches a hot path, and when a subagent result carries `signals.rigor`.
- Hot paths come from churn: paths that change often in the repository history, counted up to the commit the run started from (`meta.baseSha`). The parameters sit under `risk` in `policy.json` and are uncalibrated. `node skills/10x-pipeline/scripts/route.mjs risk <change-id>` prints the hot paths, the plan hits and the diff hits and writes nothing.
- At `lean` the router skips plan review before implementation starts, if risk was measured (history readable, the plan names at least one path, and every named path can be matched against the hot set: a file, a directory, a glob or an absolute path under the project root) and no named path is hot. The skip is logged in `run.jsonl` with its reason and listed in `report.md`. If risk could not be measured, plan review runs. Implementation review is never skipped.
- The step budget is `limits.maxTotalSteps` plus a delta per level (`rigor.budgetDelta`: -2, +5 and +10, so 12, 19 and 24 steps). Skipped steps use no budget, and failed `score` attempts use none either. See "Budget" below for the longest path each level is sized for.
- A subagent can end its `RESULT:` line with an optional `signals` object. The router keeps three keys: `rigor` (raises the level; dropped from a `score` result, because the score only advises), `needsHuman` (halts the run once with a report) and `lessonCandidates` (an `impl-review` result only; see "Lesson candidates"). It ignores the rest.
- Prompt rules follow the GIVEN/WHEN/THEN form with one bold RFC 2119 keyword (ADR-004). `node --test skills/10x-pipeline/test/*.test.mjs` checks the form and the router behavior.

Archive (opt-in):

- `init <id> --archive` stores `archive: true` in `meta.json`; a resume keeps it and `--archive false` turns it off. Without the flag the router makes no pre-archive commit: `done` stays `done`. A run that is not isolated then writes nothing to git and only reads history, for churn risk; an isolated run also makes the start and step commits and the rollback of "Run isolation".
- `init --archive` halts, and writes nothing, when the project is not a git work tree or git ignores any of `agent-smith/run.jsonl`, `agent-smith/meta.json`, `agent-smith/report.md` or `change.md` of the change. The same checks run again at `done`.
- At `done`, the router checks the git state first. It halts if anything is staged, HEAD is detached, a merge, rebase, cherry-pick or revert is in progress, `change.md` has no `created: YYYY-MM-DD` line, or the archive folder `context/archive/<created>-<id>` already exists. With `archive.haltOnManualPending` set to `true` it also halts when Manual rows are pending; the default is `false`.
- Then it writes the final `report.md`, commits `context/changes/<id>/` as `chore(<id>): commit change folder before archive` (`archive.commitMessage` in the policy), and returns an `archive` action. The commit is skipped when it would be empty.
- Three checks follow the commit, because a hook can stage or write other files: the index is empty, the commit touched only the change folder, and the folder is clean. A failed `git add` or `git commit` halts with git's message and unstages the router's own add. Hooks and signing apply; the router never skips them and never pushes.
- The commit lands on the current branch. Protected branches such as `main` are not detected.
- Every file in the change folder that git does not ignore is committed, editor junk such as `.DS_Store` included. Ignored files outside the four files above are not committed. The `archive` action lists them (at most ten) and the final message shows them as "not committed (ignored by git)"; they still move with the folder.
- Manual gate (ADR-014): when the `archive` action has `summary.manualPending` rows, or ticks nobody proved (`summary.manualUnproven`, `summary.uncommittedTicks`), the orchestrator, after it reports the run and posts the PR comment, asks one `AskUserQuestion` (header `Archive`; options `No, keep it unarchived`, recommended, and `Yes, archive anyway`) that lists at most 10 pending rows, each non-empty unproved list and the `manualNotProved` lines. Only a yes continues. Any other answer, an error or no question tool (headless `claude -p`) fails closed: no archive subagent, no `verify-archive`, the line `Archive: skipped, <n> Manual check(s) pending or unproved.` (`<n>` counts the distinct row ids across the three lists) and a final message that the change is committed on the run branch but not archived, with the checklist and `/10x-archive <id>`. Running the pipeline command again asks again. `report.md` keeps its stale `Archive: requested` line, and the pre-archive commit stays. No pending rows and no unproved ticks, no question. The router does not change.
- The orchestrator then runs `/10x-archive <id>` in one subagent. Its prompt gives the answers to the skill's questions as rules: continue past warnings, archive without repointing, never ask. A blocking warning, such as missing review coverage, ends the step as `blocked`.
- `route.mjs verify-archive <id> [--path <p>]` confirms the move from files alone: the archive folder has `status: archived` in its `change.md` and `context/changes/<id>/` is gone. It does not call git, so check `git status` afterwards. `--path` names the exact folder (`context/archive/<date>-<id>`); the orchestrator passes the `archivePath` of the `archive` action. When an id was archived more than once and no `--path` is given, the answer is `archived: false` with an `ambiguous` list of the folders. `archivedAt` is a string, or `null` when the field is absent or `null`.
- `init`, `next` and `status --report` halt, and write nothing, for a change that is archived or stamped `status: archived` with its folder still in place.
- `report.md` carries `Archive: requested - runs after this report was written`. Pending Manual rows are listed there as `Manual checks pending: N`, and, after a `manual-verify` step, with their reasons as `Manual checks not proved: N`, because this report is the only router file that survives the move. The archive step has no log entry, no usage figure and no report row, so the totals cover the steps before it.
- A halt is never archived. A halt printed by the `done` branch or by the end of the run carries `archive: "skipped: ..."` and `committed`. `committed: false` means nothing was committed: the folder is uncommitted and `/10x-archive` needs a commit first. `committed: true` means the pre-archive commit exists locally and the router did not undo it; `next` repeats the checks safely after the cause is fixed, without a second commit. On that repeat the check that the commit touched only the change folder is skipped, because no new commit is made. Halts printed elsewhere carry neither field: a missing result file, a guard halt for an archived change, usage and flag errors, errors at `init` and `Router error:`.

Pre-plan steps:

- Three optional steps can run before the first `plan` step, in this order, and two loops can send a run back after plan review. Both sit under `preplan` in `policy.json`. Every gate and both loops default to rigor `thorough`. Their word lists and thresholds are uncalibrated: no run data exists yet.
- Pre-plan steps open only for a run that starts at `thorough`, for example `init <id> --rigor thorough`. They are decided once, before the first plan attempt. Every other way to reach `thorough` (a `signals.rigor` in a step result, a plan of 6 or more phases, three failed steps, three hot paths) needs a plan or a finished step first, so a later rise does not open them.
- The loops read the run's current level, so any rise to `thorough` opens them from then on: a standard run that rises to `thorough` mid-run gets the frame round on its next `RETHINK`. An in-flight standard run whose plan already has 6 or more phases starts the frame round on its next `RETHINK`. A run that stays at `standard` or `lean` behaves as before: no new step, no skip entry, and `RETHINK` and `REVISE` re-plan as described above.
- A gate closed by the rigor level is silent. A gate that is open and does not run logs a skip with its reason, in `run.jsonl`, `status` and `report.md`. All three steps can skip in one call.

| Step | Opens at | Runs when | Skipped when | Template |
| --- | --- | --- | --- | --- |
| `research` | `thorough` | always | `research.md` exists | `research`, or `research-with-map` when `context/map/repo-map.md` has `artifact: repo-map` in its frontmatter |
| `domain-brief` | `thorough` | `aggregateGap` or `dependencyLeak` hits | a brief file exists (`refactor-invariant-aggregate.md` or `refactor-anti-corruption-layer.md`), or no signal | `domain-aggregate` when `aggregateGap` hits (it wins), else `domain-acl` |
| `frame` | `thorough` | `framingDoubt` hits | `frame.md` exists, or no signal | `frame` |

`frame` is pinned to one tier by `steps.frame` in the policy. Each step is verified by the file it writes: `research.md` needs `status` frontmatter, `frame.md` needs a `## Reframed` heading (the Confidence label is never read), and a brief needs `type: refactor-plan`. The file must also be newer than the step start. A failed attempt retries at the next tier and halts after three. The plan prompt lists the upstream artifacts that exist, so `/10x-plan` reads them.

| Predicate | What it reads | Default |
| --- | --- | --- |
| `framingDoubt` | the goal, lowercased; a phrase matches where it starts at a word start. Or a `signals.rigor` on an earlier `research` or `domain-brief` result, whatever valid level it names (the key says the change is riskier than the goal suggested) | `root cause`, `should we even`, `is this the right`, `challenge the assumption`, `rethink`, `before i plan`, `caused by`, `because`, `assuming` |

| `repoMapExists`, `researchExists`, `frameExists`, `briefExists` | a file in the project or the change folder | n/a |

- The skill's own triggers `fix`, `bug` and `broken` are left out of `framingDoubt` on purpose: they would open a frame step for `fix typo`. To add them, override `preplan.predicates.framingDoubt.goalWords` in `context/foundation/agent-smith-policy.json`. Arrays are replaced whole, so repeat the defaults:

```json
{ "preplan": { "predicates": { "framingDoubt": { "goalWords": ["root cause", "should we even", "is this the right", "challenge the assumption", "rethink", "before i plan", "caused by", "because", "assuming", "fix", "bug", "broken"] } } } }
```

- `aggregateGap` reads every pipe table in that section whose header has a cell starting with `invariant` or `policy` and a `status` cell. The status of a row is the first alphabetic word of the cell, without `*`, `_` and backticks (`**declared** (soft)` reads as `declared`). A row hits when a status in the list shares a whole word with the goal. The words come from the `candidate` column (when present), the invariant or policy cell and the `gap` cell, as lowercase letter tokens of at least 4 letters that are not in `preplan.predicates.aggregateGap.stopwords`. A `###` heading is not a word source, and lists such as "Code-only rules" are not read. No file, no section or no matching row is no hit.
- `frame` runs unattended under a decision guide (`skills/10x-pipeline/prompts/frame-unattended.md`). A goal that names a task but no separate cause is confirmed as the problem statement and the run goes on. A `signals.needsHuman` in the result halts the run, whatever `frame.md` says.

Loops (`preplan.loops.minRigor`, default `thorough`):

- At or above `loops.minRigor`, a plan review `RETHINK` runs `frame` once (template `frame-rethink`), then re-plans. A second `RETHINK` after that re-plan halts for a human.
- At or above it, a `REVISE` that needs a re-plan, after one earlier `REVISE` re-plan, runs `research` once (template `research-revise`), then re-plans. A `REVISE` whose review has `Decision` lines needs a re-plan only under `review.openFindings.onOpen: "retry"`; under the default `halt` it halts instead, so this loop sees only a review without `Decision` lines or a `retry` run (see "Review routing on open findings").
- A failed re-plan keeps spending a revision, as before, so `limits.maxPlanRevisions` still ends the run. Under the default `halt` a `REVISE` with `Decision` lines never reaches it, only a `RETHINK`, a review without `Decision` lines or a `retry` run. `loops.rethinkToFrame`, `loops.reviseResearchAfter` and `loops.reviseResearchMax` set the counts; a value that is not a positive integer turns that loop off.
- Below `loops.minRigor`, `RETHINK` and `REVISE` re-plan exactly as without these loops.

Budget:

- The steps count against the step budget; skips do not. The budgets are 12 (`lean`), 19 (`standard`) and 24 (`thorough`). The longest failure-free path with every feature in play is 10 steps at `lean`, 17 at `standard` and 22 at `thorough`, so one failed step and its retry still fit and a second failure can end the run with the budget spent. Each path holds a `manual-verify` attempt and its retry, which are outside the extra-step pool.
- A successful `score` step counts like any other step; it is outside the extra-step pool. Failed `score` attempts use no budget. The attempt cap of 3 bounds their cost, so a scorer that fails three times and then skips still leaves the longest path inside the budget. A test lets the router walk saturating plans and checks this; the same test shows that a pool allowance raised by one without a larger delta breaks it. `lean` has an empty pool, so `manual-verify` is its only extra step. The lean walk of the budget test is plan, plan-review, implement, `manual-verify` and its retry, then impl-review, fix, impl-review, fix, impl-review: 10 steps, two below the budget of 12. A lean run whose plan loop re-plans can still spend its budget, as before. Once a failure raises the level, the run has the pool of 2 and the budget of 19 of `standard`. A `lean` run gets no `score` step, also after the rise, because a plan attempt is already logged.
- A failed cheap first attempt (`cheap: true`, see "How routing works") uses no budget either, so it leaves the longest path inside the budget. A drop that the score shift, the clamp or the floor cancelled is no cheap attempt, and its failure counts as usual.
- A neutral rerun after an orchestrator fault adds no log entry and uses no budget: the step keeps its one entry however often it is rerun (see "Neutral rerun after an orchestrator fault").
- Typical worst paths at `standard`: the score step (1), the plan loop (6 steps), a segment, an e2e step and a plain tail (3), `manual-verify` and its retry (2), then impl-review, fix, impl-review, fix, impl-review (5) is 17. At `thorough`: three pre-plan steps, the score step, a `RETHINK` with a frame round and a plan loop (11), segment, e2e, tdd and a plain tail (4), `manual-verify` and its retry (2), then 5 is 22.
- A project that overrides `rigor.budgetDelta` keeps its values. With a pool allowance above 0 and an old delta, the budget can halt a run that uses extra steps. An override that keeps the earlier deltas (-4, +3 and +8) has no room for `manual-verify` and its retry: raise each by 2, or turn the step off with `{ "manualVerify": { "minRigor": null } }`.

Phase executors:

- The step name stays `implement`; the template changes. For the first pending phase of `### Phase N` headings the router returns `implement-e2e` (a valid `/10x-e2e-setup` record in `context/foundation/test-stack.md` and a browser word in the phase), `implement-tdd` (rigor `thorough`, a phase whose files are code and whose rows name a test command) or the plain step. Goal phases in front of a special phase run as `implement-segment`, which stops after its last phase.
- The extra-step pool (`extraSteps.allowance`: `lean` 0, `standard` 2, `thorough` 3) pays for segments, e2e and tdd at 1 each and for the `plan-rejected` re-plan at 2. `manual-verify` is outside the pool: a pool of 0 does not keep it away, and an override of `extraSteps.cost["manual-verify"]` charges nothing. When the pool cannot pay for a segment and the executor after it, plain `implement` runs the whole plan.
- A tdd or e2e step counts as done only with ticked rows and a code commit since it began (read-only `git`; docs, lock files, `assets/**` and `context/**` do not count). The check is per step, not per row: one counted commit covers every row the step ticked. Without git, in a repository with no commit yet or with a head that cannot be resolved, the first check falls back to the count rule, so there is no strict check there. Rows left ticked without a commit get one `implement-retry` step; if they still have none, or the retry cannot check (no git, no commit yet, an unreadable head), the run goes on without a failure and the implementation review prompt carries a warning, with a note when commit evidence was unavailable. The rows are listed as `uncommittedTicks` in the final message, the `archive` summary and `meta.outcome`, and in `report.md` of an `--archive` run.
- A tdd or e2e step that ends `blocked` is a fallback: no failed attempt, no tier bump, no rigor rise, and the executor is not chosen again for that phase. The report shows `fallback`, and `compare` does not count it as a failed attempt. The report shows `implement (<template>)` in the Step cell.
- Code re-plans, at `standard` or above, one per run: `plan-replan` after two implement failures in a row, `plan-rejected` after a first implementation review `REJECTED` before any fix (cost 2 of the pool). A failed `plan-replan` halts the run.
- Word lists and extension lists (`executors`) are uncalibrated. Nothing here has run against a live `/10x-e2e`, `/10x-tdd` or `/10x-goal-implement` session.

Manual verification:

- `manual-verify` runs at every rigor level (`manualVerify.minRigor`, default `lean`) once no Automated row is pending, before the first implementation review, when a Manual row is pending or the last attempt left a tick without valid evidence. It never runs after an implementation review, so a `fix` does not re-run it, and ticked rows stay ticked. It is outside the extra-step pool and each attempt counts one step of the budget (ADR-012).
- Every pending Manual row is in scope, a row with no command and a row that asks a person to read, judge or decide included. A subagent that starts with no memory of earlier steps proves each row by running the row's command, by a green automated test that covers it, by a throw-away script in a `mktemp -d` scratch directory or under `evidence/` (never in the source or test tree), with the Chrome tools, or by a written judgment that quotes what it checked. It saves the proof under `context/changes/<id>/evidence/` and ticks the row with ` — evidence: evidence/<name>`.
- The evidence file name starts with its kind: `command-`, `test-`, `script-`, `browser-` or `judgment-` (`manualVerify.evidenceKinds`). The router records `proved: [{ id, kind, file }]` in the log entry, one item per ticked row; any other prefix, or none, reads `other` and the row still counts. A judgment is weaker proof than a run, and the report says which is which.
- The router checks that the evidence file exists, is regular and non-empty, lies inside the real `evidence` folder and is newer than the step start, and that no Automated row, row title or SHA suffix changed. It never reads the content and never edits `plan.md`. Ticks without valid evidence, a mangled evidence suffix included, are listed as `manualUnproven`.
- Attempts: the first runs on `sonnet/medium` (`steps["manual-verify"]`). A second attempt runs one tier up on `sonnet/high` (`manualVerify.retryBump`, `tierWhy` reads `+1 from manual-verify retry after 1 attempt(s)`) when the first failed its checks or ended `done` with rows still pending. `manualVerify.maxAttempts` (2) caps them. A failed attempt is neutral: no failed attempt counted, no rigor rise, no rollback. After the last attempt the run goes on to the implementation review; an unproved row never halts it.
- Unproved rows: a row the subagent cannot prove stays `[ ]`, and the subagent lists it in `evidence/unproven.md` (`manualVerify.unprovenFile`) as `- <row id> — <reason>`, rewriting the file for every row still pending at the end of each attempt. The router reads it for display only, and only when it is a regular file (not a symlink) inside the real `evidence` folder, at most 65536 bytes and newer than the step start. Each reason is made one line and cut to `manualVerify.reasonMaxChars` (200) code points. A missing, stale or malformed file gives no reasons and never changes the outcome. The log entry gets `reasons` (`{ <row id>: <reason> }`) and `pending` (the row ids still pending).
- Outputs: a `done` run where the step ran lists every row still pending as `manualNotProved`, `<row text> — not proved: <reason>` (`no reason recorded` without one), in the final message, `meta.outcome` and the `archive` summary, next to `manualPending`. `status` shows `proved` (a count per kind) and `pending` (a count) next to `ticked` and `unproven` on the row of each `manual-verify` step. `report.md` gets a `## Manual checks` section (see "Usage report").
- Safety: the prompt (`skills/10x-pipeline/prompts/manual-verify.md`) tells the subagent never to push, deploy, publish or post to an external service, never to write outside the run root and its scratch directory or, in the run root, outside `plan.md` and `evidence/`, to use only read-only git, never to delete a branch, worktree or ref, never to run a command that does not end by itself or waits for input, to start a server only in the background and stop it before the step ends, and to redact credentials, tokens, environment dumps and personal data before saving evidence, because the step commit stores `evidence/` in the run branch. The router enforces none of these: it never reads evidence content and never checks for files written outside the change folder. The step commit and the implementation review see the diff.
- `--chrome` (an `init` flag, kept in `meta.json`): the Chrome tools are on by default. The `manual-verify` template tells the subagent to load the `mcp__claude-in-chrome__*` tools through ToolSearch for rows that need a browser, to open only local pages or pages the row names, never to sign in, submit a form to an external service or enter a credential, and to save the page text, or an image or GIF the tool can export, as `browser-` evidence. When the tools are unavailable it does not wait: it proves the row another way or leaves it pending with that reason. `init --chrome false` stores `false` and selects the `manual-verify-nochrome` template, which uses no browser tool. `--chrome` and `--chrome true` store `true` and change nothing in effect. A resume keeps the stored value, and a run that stored none, or started before Chrome was on by default, reads on. The orchestrator does not probe for the tools.
- Turn the step off per project with `{ "manualVerify": { "minRigor": null } }` in `context/foundation/agent-smith-policy.json`. A `minRigor` that is not a rigor level turns it off too.
- Upgrade note: the policy and the prompts change, so a run in flight records `provenance.drift` for `manualVerify`, `steps`, `extraSteps`, `rigor` and `prompts` at its next `next` call; routing is unaffected. An override that still carries the removed word-list keys of `manualVerify` is harmless, because the router ignores them.
- Release note: `lean` runs gain a step (the attempt, and its retry when rows stay pending), every run now spends tokens on its Manual rows, and Chrome is on by default. Whether it ships as `feat` or `feat!` is the owner's call at commit time. The rules are in ADR-012.
- Nothing here has run against a live Chrome session, and no live run has used the new prompt yet.

Complexity score:

- `score` is a pipeline step (ADR-007). At `score.minRigor` (default `standard`) and above, the router returns it once before the first `plan`, after any `research`, `domain-brief` or `frame` step. `steps.score` pins it to the lowest tier of the ladder; a retry runs one tier up. A `lean` run never pays for it. The step is outside the extra-step pool.
- The subagent follows `skills/10x-pipeline/prompts/score.md`. It reads `change.md`, the goal and the upstream artifacts, never `plan.md`, and writes `context/changes/<id>/complexity.json`:

```json
{
  "schemaVersion": 1,
  "factors": {
    "ambiguity": { "score": 0, "evidence": "..." },
    "novelty": { "score": 0, "evidence": "..." },
    "coupling": { "score": 0, "evidence": "..." },
    "discovery": { "score": 0, "evidence": "..." },
    "volume": { "score": 0, "evidence": "..." },
    "verification": { "score": 0, "evidence": "..." }
  },
  "unknowns": ["..."],
  "confidence": "medium"
}
```

- Each factor scores 0 to 3 with a one-line `evidence`. The cognitive sum (`ambiguity`, `novelty`, `coupling`) and the execution sum (`discovery`, `volume`, `verification`) each run from 0 to 9. Factor names, the scale and the thresholds sit in the `score` block of `policy.json` and are uncalibrated.
- The step counts as done only when `complexity.json` is newer than the step start and is a regular file (not a symlink) of at most `score.maxBytes` (65536) bytes, with `schemaVersion` 1, an integer score from 0 to 3 and non-empty evidence for every factor, `unknowns` as an array and `confidence` `low`, `medium` or `high`. Extra keys are ignored. The router never judges whether the evidence is true.
- The router copies the factor scores, the two sums, the confidence and the number of unknowns into the `score` log entry; the evidence text stays in the file. Every later tier and the report read that copy, so a later edit or deletion of `complexity.json` changes nothing.
- A valid `complexity.json` that exists before the first attempt skips the step with a logged reason and is trusted as-is. An invalid one does not skip the step, and the subagent writes a new file.
- A failed attempt retries one tier up. After 3 failed attempts or 2 invalid files the router logs a skip with the last note and goes on with the deterministic signals; the run never halts for a failed scorer. A failed attempt uses no step budget, raises no rigor and withholds no simple-change discount. A `signals.needsHuman` in a score result halts the run once, as for any step; `signals.rigor` is dropped.
- Shift up: a cognitive sum of 7 or more moves the first plan (template `plan`) up one tier. An execution sum of 7 or more moves an implement step (`implement`, `implement-segment`, `implement-tdd` or `implement-e2e`) up one tier. Up shifts have no guards. A retried first plan or implement step keeps the up shift on top of the failure bump. Re-plans (`plan-revise`, `plan-replan`, `plan-rejected`), `implement-retry`, reviews and fixes get no shift.
- The plan never moves down (`score.shift.plan.down` is `null`): churn risk is not measured before the first plan, and a hard-keyword goal keeps the plan's base tier on purpose.
- Shift down: an execution sum of 2 or less moves an implement step down one tier only when every guard holds: confidence `medium` or `high`, at most 2 unknowns, churn risk measured (the same test as the `lean` plan-review skip) with no hot plan or diff path, no failed step, no simple-change discount and no phase-count bump on the step. The window is narrow on purpose: it opens only for a plan of 2 phases, or of 1 phase with more than 6 rows, whose named paths are all measured and none is hot.
- The shift goes in before the clamp and the effort floor. The floor applies to interactive steps (ADR-003), so `plan`, `implement-tdd` and `implement-e2e` never go below it, while a down shift on plain `implement` or a segment can reach the step's `minTier`, as the simple-change discount can. A shift never changes the rigor level.
- `report.md` gets a `## Complexity score` section with the sums, the factor scores, the confidence, the number of unknowns and one line per shifted step, such as `implement -1 (step 5)`. A shift that the clamp or the floor absorbed reads `not applied (clamp or floor)`. `status` shows `score`, `invalid` and `scoreShift` on the rows that have them. `scoreShift.effective` is the difference of the final tier indexes with and without the shift, so it can read 2 for a shift of 1 when the floor skips a rung.
- A run that starts with a `plan.md` that already has `## Progress` gets no score and no skip entry, and so does a run that already logged a `plan` step.
- Turn the step off per project with `{ "score": { "minRigor": null } }` in `context/foundation/agent-smith-policy.json`. With no score, every tier is what it was without the step.

Override any policy key per project in `context/foundation/agent-smith-policy.json`. Run state lives in `context/changes/<change-id>/agent-smith/`.

Usage report:

- When a run ends (`done` or `halt`, including a spent step budget or repeated failures), the router writes `context/changes/<change-id>/agent-smith/report.md` and adds its path to the output as `report`.
- The report has the goal, the rigor level and the outcome, then one table row per executed step: model, effort, tier, simple-change flag, result and tokens. A totals line sums the tokens and gives the number of skipped steps. A `## Skipped steps` section lists each skip with its reason. A `## Review findings` section (after `## Rolled-back steps` and `## Neutral reruns`, when any review step ended) lists one line per review: `- step <n> <step>[ (confirmation)]: <VERDICT>, <c> critical, <w> warnings measured[; <oc> critical, <ow> warnings open]`. The measured pair is the header count before the review's own fixes; the open part appears only for a review with `Decision` lines and shows what was still open, so tolerated open warnings stay visible. The figures are those stored in `run.jsonl` when the step ended, and the section says that a later edit of a review file (an owner closing a finding after a halt) is not reflected. No review step, no section. A `## Manual checks` section follows it when a `manual-verify` step ran: the rows the last attempt counted as proved, grouped by evidence kind (`- <id> <title> — <kind> (<file>)`), then the rows still pending with their reasons (`- <id> <title> — not proved: <reason>`). The router never reads the evidence content, and the section says so. No `manual-verify` step, no section.
- Token figures are optional. The orchestrator passes along the total tokens, tool uses and duration of a step when the Agent result reports them. A subagent that handed its report back as a message reports them in the `<usage>` block of its task notification instead (`subagent_tokens`, `tool_uses`, `duration_ms`); the orchestrator reads that block too, when it is already there. Before this was documented, the orchestrators of runs whose reports came back as messages passed no figure, so those runs show `-` for every step. A step without a figure shows `-`, and the totals line says how many steps it covers.
- A step the router returned again after an orchestrator fault shows `, <k> neutral rerun(s)` after its result in the Result cell (`-, 1 neutral rerun` while it is still pending), and a `## Neutral reruns` section after `## Rolled-back steps` lists each such step with the orchestrator's notes, each made one line, without backticks and cut to 200 code points. `status` shows `neutralRetries` (a count) on that row. No rerun, no section and no field (see "Neutral rerun after an orchestrator fault").
- `node skills/10x-pipeline/scripts/route.mjs status <change-id> --report` rewrites the report on demand. For a run in progress it prints `Outcome: not ended`. Plain `status` stays read-only.
- A halt for a missing result file writes no report. A run that continues after a halt keeps the old `report.md` until it ends again or you run `status --report`.

Cost estimate:

- Off by default: `policy.json` ships `"prices": null`, so no price is invented. Turn it on in `context/foundation/agent-smith-policy.json` with `{ "prices": { "usdPerMillionTokens": { "opus": 30, "sonnet": 6, "haiku": 2 } } }`, USD per million tokens per model alias (the `model` the log records, never a model id). You supply the numbers; they go stale when the prices change.
- The rate is blended: the host reports one `totalTokens` per step, with no input, output or cache split, so a step costs `totalTokens * price / 1e6`. Only steps with a token figure and a price count. A `0` price is a price.
- `report.md` then gets a `Cost (est.)` column after `Tokens` (`$` and 4 decimals, `-` for a step with no figure or no price) and a line under the totals line: `Cost (estimate): $X.XX at a blended rate (USD per million tokens, no input/output split) · priced N of M steps with a token figure`, plus ` · no price for: <aliases>` when an alias with a figure has no price. With nothing priced the line reads `Cost (estimate): - (no step with a token figure has a price) at a blended rate`. Without prices the report is as before.
- `status` then adds `cost` (USD at 4 decimals, or `null`) to each executed step row and a top-level `cost: { usd, currency: "USD", rate: "blended", priced, withFigures, unpriced }`; `usd` is `null` when nothing is priced. Without prices it has no `cost` key.
- Both chains read the same log entries, so an OpenSpec run gets the same column, line and `status` object.
- A `prices` block of another shape reads as off, and an entry that is not a number of 0 or more is dropped (that alias is unpriced); nothing halts.
- The report computes the estimate with the override as it reads when the report is written. An archived `report.md` keeps the text it was written with; a later price change does not touch it.
- `prices` is display-only: it is in `provenance.ignore`, so it is never hashed and never raises `provenance-differs`.

Lesson candidates:

- The implementation review subagent can end its `RESULT` `signals` with `lessonCandidates`, an array of rule sentences ("Always ...", "Never ...") for findings that would recur in other changes. The prompt asks for them and states both caps and the `RESULT` shape. Other steps' `lessonCandidates` are dropped.
- The router cleans each candidate (one line, no backticks, no format characters), drops case-insensitive repeats and keeps at most `lessons.maxCandidates` (default 3) per review, each cut to `lessons.maxChars` (default 200) code points, back to the last space when the cut falls inside a word. The caps are per review, not per run: a run with three accepted reviews lists at most 9. An invalid value reads as the default.
- `report.md` gets a `## Lesson candidates` section, one line per candidate: `` - `/10x-lesson <seed>` (step <n>) ``. A repeat across reviews shows once, with its first step number. A run with no candidates has no section.
- The pipeline never runs `/10x-lesson` and never writes `context/foundation/lessons.md`: the skill is an interview, so you run a command from the report yourself. The router does not compare candidates with `lessons.md`; the prompt asks the subagent to read that file and skip rules already in it.
- Override the caps in the `lessons` block of `context/foundation/agent-smith-policy.json`. A project that overrides the `impl-review` prompt with a plain string never asks for candidates.

Baseline comparison:

- The baseline is a full run of the same change with every step on the `sonnet` alias at `high` effort, at `standard` rigor, with plan review never skipped and no `score` step (`baseline-policy.json` sets `score.minRigor` to `null`). It needs its own checkout: run state is per checkout, and a second `init` on the same change id resumes the first run.
- Make the baseline: read `meta.baseSha` of the routed run; `git worktree add -b agent-smith/<change-id>-baseline <path> <baseSha>` (a branch under `agent-smith/`, so the isolation gate of `init` passes there); copy into it every input file the routed change folder held when its `init` ran (`change.md`, `research.md`, `frame.md` and similar) and none of the files the run produced (`plan.md`, `plan-brief.md`, `complexity.json`, `reviews/`, `agent-smith/`). For an isolated routed run these are the files of its start commit, `git show --name-only <meta.startCommit>`, without `agent-smith/`; copy `<plugin dir>/skills/10x-pipeline/baseline-policy.json` to `context/foundation/agent-smith-policy.json` there (`<plugin dir>` is the installed plugin directory, not a project path; if the project already has an override, merge by hand: arrays are replaced whole and `rigor` merges key by key); run `/agent-smith:10x-pipeline <change-id> <same goal text>` with no extra flag, because the file fixes `standard` rigor, keeps plan review on and turns the score step off. The baseline arm is isolated too, so it runs the cheaper first attempt: on its all-`sonnet`/`high` ladder the drop changes no model or effort, and a failed first attempt is treated as in the routed arm.
- Compare: `node skills/10x-pipeline/scripts/route.mjs compare <change-id> --baseline <worktree> [--routed <dir>] [--format md] [--unpinned]`. It is read-only and writes nothing; redirect stdout to keep the output. `--routed` defaults to the current project. For an isolated routed run pass `--routed <routed run root>`, the run root in its worktree, because the change folder of the main checkout holds no run log. Each `<dir>` is a project root, or the `agent-smith` folder itself, and is read from `context/changes/<id>/agent-smith/` or, when the change is archived, from `context/archive/<date>-<id>/agent-smith/` (a live folder wins over an archived one and adds a warning; two archive folders for one id halt).
- The output has per-side totals and coverage (`stepsWithFigures` of `steps` for tokens, tool uses and duration), tokens per model alias (`tokens.byModel`) and per tier (`tokens.byTier`, keyed `<model>/<effort>`, with `unknown` for a missing model or effort), `pinned`, `comparable`, `reasons`, `warnings`, `dropPercent`, `targetDropPercent` and `verdict` (`target not set`, `met`, `not met`, `unpinned` or `not comparable`). `--format md` prints both token splits as `Tokens by model, ...` and `Tokens by tier, ...` lines. A pair is comparable only when both runs ended `done`, every executed step of both has a token figure and the baseline has at least one executed step, all on `sonnet` at `high`. A baseline whose token total is 0 is not comparable either (`baseline-total-zero`). A failed step that has no token figure makes its whole side not comparable (`usage-incomplete`), so a pair with a crashed or timed-out step usually is not comparable. A `meta.json` that is missing or unreadable shows only as `outcome-not-done` on that side, plus goal and `baseSha` mismatch warnings; nothing names the file. Skipped steps on the baseline, a different goal or `baseSha`, and differing input file names are warnings. `complexity.json` (the file named by `score.file`) is a produced file, like `plan.md`, so it never counts as an input file.
- `--unpinned` is for the scorer A/B check, where the baseline is a routed run too. It waives only the `baseline-not-pinned` reason, adds the warning `baseline-unpinned` and gives a comparable pair the verdict `unpinned` instead of the target verdict. `dropPercent` is then the share of tokens the scorer saved, negative when it cost more. A bare `--unpinned` or `--unpinned true` turns it on, `--unpinned false` turns it off, and any other value halts before anything is read. A word after the bare flag is read as its value, so `--unpinned md` halts: put the flag last or before another `--` flag.
- Cost: with `prices` set in the policy of the project that runs `compare`, each side carries `cost: { usd, priced, withFigures, unpriced, byModel }` (`byModel`: USD per alias over priced steps; `usd` and each `byModel` value at 4 decimals, summed before rounding; `usd` is `null` when nothing is priced, as in `status`), and `--format md` prints a `Cost (estimate)` row (`$X.XX (P of S priced)`, or `- (0 of S priced)`), `Cost by model, baseline: ...` and `Cost by model, routed: ...` lines and `Cost is an estimate at a blended rate and does not enter the verdict.` after the unit line. Both sides are priced from that one table. Without prices each side has `cost: null` and the Markdown is as before. A side with a token figure on an unpriced alias adds the warning `cost-incomplete:<side>`. `comparable`, `reasons`, `dropPercent` and `verdict` never read `cost`.
- `dropPercent` is the exact drop rounded down to 2 decimals; the verdict uses exact tokens. Run `compare` from the project whose override file holds the target: `compare.targetDropPercent` is read from that project's policy, not from `--routed`'s. It ships as `null`, so the verdict is `target not set` until the owner fills it.
- The unit is raw tokens, a proxy for the weekly limit. It understates savings from `haiku` steps and overstates a drop bought by moving work to `opus`. Orchestrator-session tokens are not counted; retries are counted.
- One pair is an anecdote. Compare per-pair drops across several changes, run the two sides close in time and alternate which runs first. A halted or incomplete side makes the pair not comparable instead of being dropped. Read the warnings before trusting the number.
- The baseline file keeps its keys, so the baseline arm runs the same phase executors, segments, `manual-verify` and re-plans as the routed arm. For a routing-only comparison add this to the baseline override by hand: `{"extraSteps": {"allowance": {"lean": 0, "standard": 0, "thorough": 0}}, "codeReplan": {"afterFailures": 0}, "manualVerify": {"minRigor": null}}`. A pool allowance of 0 turns off segments, executors and the `REJECTED` re-plan, all of which draw from the pool; `afterFailures` 0 turns off the failure re-plan, which does not; `manualVerify.minRigor: null` turns off `manual-verify`, which is outside the pool, so a pool of 0 no longer turns it off. The commit check, the retry and the fallback act only after an executor step ran, so with the allowance at 0 they never fire. When both runs carry a provenance record, `compare` warns `provenance-differs:codeReplan,extraSteps,manualVerify` for these additions (see "Run provenance").
- Keep the baseline worktree until `compare` has run, because its `run.jsonl` exists nowhere else; remove it with `git worktree remove <path>` afterwards.

Scorer A/B check:

- ADR-007 keeps the score step only if it saves more than it costs. One pair is one change run twice from the same `baseSha`: the scorer off as the baseline, the scorer on as the routed side. Both arms use the shipped routing, not `baseline-policy.json`.
- Make the scorer-off arm like the baseline above (a worktree at `meta.baseSha`, the same input files, the same goal text), but with only this override in `context/foundation/agent-smith-policy.json`: `{ "score": { "minRigor": null } }`. The scorer-on arm runs with the shipped default. Run both arms at `standard` or above, for example with the same `--rigor` on both: a `lean` run never scores.
- Compare: `node skills/10x-pipeline/scripts/route.mjs compare <change-id> --baseline <scorer-off dir> --routed <scorer-on dir> --unpinned`. Keep `dropPercent`, `tokens.byModel` and `tokens.byTier` of both arms, and the reasons of a pair that is not comparable.
- Make one A/A pair too: the same change with the scorer off on both arms, compared the same way. Its absolute `dropPercent` is the run-to-run spread.
- Alternate which arm runs first and run the two arms close in time.
- Decision rule, fixed before any run. The scorer stays on only when all three hold over at least 5 comparable pairs: the median `dropPercent` is above 0; the median per-pair difference of `opus` tokens (on minus off, from `byModel`) is 0 or less; the median `dropPercent` is above the absolute A/A `dropPercent`. Any other outcome turns it off: fewer than 5 comparable pairs, no A/A pair, or a result inside the A/A spread. To turn it off, set `score.minRigor` to `null` in `policy.json`; the router does not change. A pair that is not comparable is recorded with its reasons and does not count.
- Five pairs is a screen, not a significance test. The rule reads raw tokens and does not credit an effort move beyond the tokens it saves. The result goes into ADR-007 under "A/B result"; no pair has run yet.

Run provenance:

- `init` records what a run runs with in `meta.provenance`, once, while the run has no executed step: `schemaVersion` 1, `plugin` (the `version` of `.claude-plugin/plugin.json`), `sections` and `flags`.
- `sections` holds one hash per section of the merged policy: the first 16 hex characters of a SHA-256 over JSON with sorted keys. `prompts` hashes the resolved text of every template, so an edit of a `prompts/*.md` file changes it. `agentFiles` hashes the `agents/*.md` files of the plugin.
- The sections in `provenance.ignore` (default `compare`, `provenance` and `prices`) are not hashed. Setting `compare.targetDropPercent` changes no hash.
- `flags` holds `archive` and `chrome` from `meta.json`, `score.minRigor` from the merged policy (`null` when unset), `agents.restricted` and `advisor.enabled`. `chrome` is the effective setting: `true` unless the run stored `--chrome false`, so a run that never set the flag records `true`. Any other flag that is missing or malformed reads `false`.
- Computing the record never halts a run. An unreadable `plugin.json` gives `plugin: null`, a missing `agents/` folder gives `agentFiles: null`, and a prompt reference that does not resolve gives `prompts: null`; the run then halts at `next` as before.
- The record is never rewritten, also on a resume. Each `next` hashes the sections again and adds every section that differs from the record to `provenance.drift`, sorted, each name once. `drift` is absent while empty. `plugin` and `flags` are not tracked for drift. `next` writes `meta.json` for drift only when the list changes.
- A run whose log already holds executed steps and has no record, because it started before provenance existed, gets none. Nothing halts for a missing record.
- `compare` prints the record of each side as `provenance` (`null` when absent) and appends these warnings after the others. They never change `comparable`, `reasons`, `dropPercent` or `verdict`.
- `provenance-unknown:<side>`: exactly one side has no record. Two sides without a record stay silent.
- `provenance-differs:<names>`: the sections, or `plugin`, that differ between the two records, sorted and comma-joined.
- `flags-differ:<keys>`: the flags that differ.
- `provenance-drift:<side>:<names>`: the `drift` list of that side.
- Names the pair is expected to differ in raise no warning. Without `--unpinned` the set is `provenance.expected.pinned` (default `ladder`, `rigor` and `score`, the sections `baseline-policy.json` changes). With `--unpinned` it is `provenance.expected.unpinned` (default `score`, the scorer A/B arms). The mode follows the flag only, never the `pinned` value `compare` measures.
- A flag is exempt when its first dot segment is an expected section, so `score.minRigor` raises no warning in either mode.
- The expected sets come from the policy of the project that runs `compare`. A list that is not an array of strings reads as the default.

Restricted step agents (opt-in):

- `agents.restricted` in the policy turns it on. It ships as `false`. Only the boolean `true` turns it on; a block of another shape reads as off and never halts.
- When it is on, a step that `agents.steps` maps to an agent type gets `agent: <type>` in its `run` output and its log entry, and `status` shows `agent` on that row. The orchestrator passes it as `subagent_type`; a step without the field runs as `general-purpose`, as before. A value that is not a non-blank string gives that step no agent. The `archive` action never carries `agent`.
- The shipped map names only `score`: `agent-smith:score`, defined in `agents/score.md` at the plugin root. Its `tools` list is `Read`, `Grep`, `Glob` and `Write`, so the scorer can read and search the repository and write files, and cannot use `Bash`, `Edit`, `Skill`, `Agent` or web tools. The definition sets no `model` and no `effort`, so the router's model and effort for each call stay in control.
- `Write` cannot be scoped to one path. The scorer can still write any file; only the prompt rule "change no other file" and the router's check of `complexity.json` hold it to that file. Plugin agents ignore `hooks`, so no hook can guard the path either.
- No fallback. When the type does not resolve (the plugin is loaded under another name, or Claude Code is too old), the Agent call fails, the orchestrator records the step as `unknown` and does not retry it as `general-purpose`, and the router counts a failed `score` attempt. That is neutral, as for any failed scorer: a retry one tier up with the same agent, no step budget, no rigor rise, and a logged skip after 3 failed attempts. The run goes on.
- The name `agent-smith:score` is inferred from the Claude Code docs and has not been checked in a live run. If it does not resolve, correct `agents.steps.score` in the project override; the router does not change.
- A/B reading: both arms run the same model and effort, and the restricted arm has fewer tools, so no token drop is expected and none is the criterion. The restriction earns the default `true` only when the restricted arm has no more failed `score` attempts than the unrestricted arm and no halts.
- Provenance records the flag as `agents.restricted` in `flags`, the block as the `agents` section and the definition files as `agentFiles`, so `compare` warns when two arms differ in any of them.

Advisor (opt-in):

- `advisor.enabled` in the policy turns it on. It ships as `false`. Only the boolean `true` turns it on; a block of another shape, or an `advisor.templates` value that is not an array of strings, reads as off and never halts.
- When it is on, the prompt of a step whose template `advisor.templates` names (shipped: `plan`, `implement`, `implement-segment`) gets the rules of `skills/10x-pipeline/prompts/advisor.md` after the step's own text and before the generic suffix, and its log entry gets `advisor: true`. The rules ask the subagent to consult the advisor once, after the plan draft or the implementation is complete and before the `RESULT` line, only when an advisor tool is available, to act on the advice or say why not, to leave the workers of `/10x-goal-implement` out of it, and to add one `assumptions` entry that says a consult happened. Re-plans, `implement-retry`, the tdd and e2e executors, reviews, `fix`, `score` and the pre-plan steps get no advisor text.
- `advisor.enabled` cannot configure or cap the advisor. It only adds prompt text. The advisor is the native Claude Code tool, and your own `advisorModel` setting (or `--advisor`, `/advisor`) decides whether one exists and which model it is. The pairing rule applies: the advisor must rank at or above the step's model, so a Sonnet 5.5 step needs an advisor at or above Sonnet 5.5 (Fable, Opus 5 or later, or Sonnet 5.5), and Claude Code attaches no weaker one, without an error. With no advisor the rules tell the subagent to go on without it.
- The router never reads a settings file, never checks that a consult happened and never caps the consults; Claude Code has no setting that caps or forces them. With `advisorModel` set, other steps of the session may consult the advisor on their own too.
- Provenance records the flag as `advisor.enabled` in `flags` and the block as the `advisor` section. It cannot see `advisorModel`, so for an A/B pair record the advisor setting and the Claude Code version of both arms by hand; both arms need the same ones.
- Whether the step's reported `totalTokens` includes the advisor's tokens is not known yet. The flag stays off until a live run settles it. The precondition and the A/B decision rule are in `docs/ADR/ADR-009-managed-agent-patterns.md`.

Limits:

- Subagents cannot use `AskUserQuestion`. Where a skill would ask, the subagent decides from researched best practice, cites the evidence and lists the decision as an assumption. With no evidence-backed answer it reports `blocked` with `signals.needsHuman`, and the router halts.
- `10x-goal-implement` spawns its own subagents. This needs `CLAUDE_CODE_MAX_SUBAGENT_SPAWN_DEPTH` of 3 or more (the default since Claude Code v2.1.219).
- The Chrome browser tools are on by default for `manual-verify` (`--chrome false` turns them off), and the subagent loads them through ToolSearch. Whether a subagent can load and call them was not tested; when they are missing the `manual-verify` subagent proves the row another way or leaves it pending with that reason, and the run goes on. `/10x-e2e` and `/10x-tdd` also run in a subagent and answer their own questions from the decision guides in `skills/10x-pipeline/prompts/`; no live run has been done.

Orchestrator anti-stall:

- Five rules in `skills/10x-pipeline/SKILL.md` (section "Anti-stall rules") keep the orchestrator from stalling between steps. The first three hold for every `run` step, the last two for the whole run.
- If the Agent tool returns a launch notice because the subagent runs in the background, the orchestrator ends its turn and continues the Loop when the subagent's final report arrives. It starts no other step and does not poll. The same holds for the archive subagent.
- If the final report holds its `RESULT:` line and no usage figure has arrived, the orchestrator writes the result file without `usage` and runs `next` in the same turn.
- A usage figure that arrives after `next` ran is dropped: the result file is not rewritten and `next` is not called again. That step shows `-` for tokens in `report.md`, and `compare` counts the side as `usage-incomplete`.
- While the run has not ended in `done`, `archive` or `halt`, the orchestrator does not end its turn into an idle state, unless a launched subagent is still running.
- When you ask what the run is doing, the orchestrator states only what tool output in this session shows, and says so when nothing is running.
- Headless limit of the first rule. It relies on the host giving the orchestrator a new turn when a background subagent ends, as an interactive Claude Code session does. In a headless `claude -p` run the process is expected to end when the orchestrator ends its turn, and the background subagent most likely ends with it: the run exits early instead of stalling. This has not been verified in a live headless run. The interrupted step writes no result file, and the router logged the step when it returned it, so re-running `/agent-smith:10x-pipeline <change-id>` halts with `Step <n> (<step>) has no result. Write <resultFile> first.` When no subagent of that step can still be running, write `{"status":"orchestrator-error","note":"interrupted"}` there and re-run: the router returns the same step with the same prompt and counts no failed attempt (see "Neutral rerun after an orchestrator fault"). Any other status than `done` there (for example `{"status":"failed","note":"interrupted"}`) counts the step as a failed attempt, which the router handles like any other failed step. A killed subagent may leave partial edits in the working tree, and a neutral rerun continues over them; check `git status` before the re-run.

Neutral rerun after an orchestrator fault:

- The orchestrator writes `{"status":"orchestrator-error","note":"<what happened>"}` as the result file when the fault is its own and no subagent of the step is running: the Agent call was refused or errored before any subagent started, for a cause other than the router's `agent`; the prompt could not be passed whole, for example because it was cut; or the call returned neither a reply nor an error. A launch notice is none of them. Both skills carry the rule in step 2 of the `run` branch.
- When the last executed log entry has no result and `last-result.json` parses with that status, `next` consumes the file, appends `{ at, note }` to `neutralRetries` of that entry (the note made one line and cut to 200 code points, empty when absent) and prints `run` with the entry's `n`, `step`, `agent`, `model`, `effort`, `reason` and `resultFile`, the stored prompt and `neutralRetry: { count, cap }`. The orchestrator ends its `Step <n>` line with `Neutral rerun <count> of <cap>.`
- The rerun is the same step: no new log entry, no result, no failed attempt, no tier bump, no rigor rise and no budget use, and in an isolated run no rollback, step commit or reset. The entry keeps `startedAt`, `startSha`, `before`, `tier`, `tierWhy` and `rigor`. A `meta.outcome` of an earlier end is removed, as before any new step.
- The prompt: `next` stores the rendered prompt of each new step as `pendingPrompt` on its log entry, and the intake of a real result of any status deletes it, so `run.jsonl` holds only the prompt of the pending step. The step commit rewrites `run.jsonl` from the log in memory first, so the prompt never lands in a step commit. A rollback snapshot is taken before that rewrite, so the side ref of a failed step under `refs/agent-smith/` holds the on-disk entry with `pendingPrompt`; that ref is local.
- A rerun after a lost report continues over the lost run's edits. `startedAt` stays, so a file the lost run wrote still counts as fresh for the step check, and a later failed result rolls back to the original `startSha`.
- Declare the status only when no subagent of the step can still be running. A background subagent that outlives the declaration would edit the same files as the rerun. That is also why the router never returns the step again by itself when the result file is missing: a missing file can mean that the subagent still runs (see "Orchestrator anti-stall"). The missing-result halt now ends with `When the fault is the orchestrator's own and no subagent of the step is running, write {"status":"orchestrator-error","note":"..."} to rerun the step unchanged.`
- Cap: `limits.maxNeutralRetries` (default 2) per step. An `orchestrator-error` result on a step that already had that many reruns consumes the file and ends the run with a halt, a report and `meta.outcome`: `Step <n> (<step>) hit its limit of <cap> neutral reruns after orchestrator faults (limits.maxNeutralRetries). Needs a human.` The text names the two ways forward: write a result file with the real status (the router verifies the step by its files), or raise `limits.maxNeutralRetries` in `context/foundation/agent-smith-policy.json` and write the `orchestrator-error` result file again, then run `next`.
- `{ "limits": { "maxNeutralRetries": 0 } }` turns it off: the status then reads as any status other than `done`, a failed attempt. A value that is not a non-negative integer reads as 2.
- Faults that stay failures: an agent type that does not resolve (the router's `agent`) and a reply without a parsable `RESULT:` line, a cut-off one included, are `unknown`, a failed attempt. The `archive` action has no log entry and no result file, so it has no neutral rerun.
- `compare` counts no reruns, and a lost run has no token figure. Both chains share the rule, because both skills go through `next`.
- Upgrade note: an entry logged before this change has no `pendingPrompt`. For it an `orchestrator-error` result halts without a report (`Step <n> (<step>) was logged without a stored prompt, so it cannot be rerun unchanged after an orchestrator fault.`) and leaves the file in place; replace it with `{"status":"failed","note":"..."}` to count the attempt. `limits` gains a key, so a run in flight when the plugin is upgraded records `provenance.drift` for `limits` at its next `next` call, and `compare` warns `provenance-drift:<side>:limits`. That is expected and changes no routing.
- The rules are in ADR-015. No live run has declared the status yet, and the cap of 2 is uncalibrated.

PR comment (opt-in):

- Needs the GitHub CLI `gh`, authenticated, and only with `--pr-comment`. Without the flag nothing is posted and `gh` is not needed. The permission a fine-grained token needs is not verified yet (pull requests or issues write is the expected one).
- Opt-in because the comment is visible to collaborators and carries the goal text. The comment goes to the repository named in the pull request url, which for a pull request from a fork is the base repository and can be public. Besides `@mentions`, the report text is posted as it is (links, images and HTML included); a halt can quote subagent text, and the lesson candidates are subagent text too. The PRD wording "is posted" is therefore met only when the flag is given.
- When the run ends (`done`, `archive` or `halt` with a `report`), the orchestrator runs `skills/10x-pipeline/scripts/pr-comment.mjs <change-id>`. It posts `report.md` as one comment on the open pull request of the current branch. In an `archive` run it posts before the move. An isolated run posts from the main checkout with `--report "<run root>/context/changes/<change-id>/agent-smith/report.md"`, so the comment goes to the pull request of the main checkout's branch, not to the local run branch, which has none. The flag is kept as an orchestrator task named `PR comment: <change-id>` and read at each end of the run; `route.mjs` and `policy.json` are not involved.
- One comment per change per pull request. The first line is a hidden marker, `<!-- agent-smith:pr-report change=<change-id> -->`. A later run edits the comment of the same author that holds the marker, even after you edited it in the GitHub web UI. It never edits another comment. The author is the login from `gh api user`. When that call fails (a timeout, a 5xx or a token without access to `/user`, such as some integration tokens), the script posts nothing and skips with `viewer lookup failed`, because it cannot tell its own comment from one planted by another user. The edit replaces the earlier text; GitHub keeps the edit history.
- Skip reasons, each with exit code 0 and no effect on the run: `gh is not installed`, `gh is not authenticated`, `no pull request for this branch`, `not a git work tree`, `pull request is MERGED` or `CLOSED`, `unsupported host <host>` (no GitHub Enterprise), `viewer lookup failed`, `gh timed out` (each call has 20 seconds; a pull request with hundreds of comments can exceed that while the comment list is read, and the skip posts nothing and cannot duplicate), `comment lookup failed` (also when `gh` prints a list the script cannot read, so an unexpected format cannot create a duplicate), `comment request failed`, a missing, empty or foreign report, and `task list unavailable` (the task tools are missing, so the flag cannot be stored and nothing is posted). A draft pull request gets the comment.
- The orchestrator prints a `PR comment:` line when the flag was given. A missing line means the step was dropped.
- Mentions such as `@name` in the report get a zero-width space after the `@`, so nobody is notified. A body over 60000 UTF-16 code units is cut and says how many characters were omitted.
- Nothing is written to the change folder, so `report.md` cannot say whether it was posted. The result is in the final message only.
- A report with a `Cost (estimate)` line (see "Cost estimate") posts the dollar estimate to the pull request like any other report text.
- A change id is at most 100 characters for the script (the marker must fit in the comment head). The router has no such limit, so a longer id ends in `PR comment: skipped, script error`.
- A run that ended before the pull request existed: open the pull request, check out its branch and run `node <plugin>/skills/10x-pipeline/scripts/pr-comment.mjs <change-id> [--report context/archive/<date>-<change-id>/agent-smith/report.md]` from the project root. The comment goes to the pull request of the branch checked out now, so run it from the branch of that pull request. The result prints the pull request url. `--report` accepts only a file named `report.md` inside a directory named `agent-smith`, whose first line is `# Run report: <change-id>`.

## `/agent-smith:openspec-pipeline <change-name> [goal] [--archive] [--pr-comment]`

Runs an existing OpenSpec change (`openspec/changes/<change-name>/`) through the steps `os-propose`, `os-apply` and `os-verify`, a fix loop on a failed verify, and, with `--archive`, the OpenSpec CLI archive. The skill is `skills/openspec-pipeline/SKILL.md`; it calls the same router (`skills/10x-pipeline/scripts/route.mjs`) with `--chain openspec` on every call and reads the same policy and override file. The decisions are in ADR-013. Everything this section does not name works as described above for the 10x chain: the ladder and the effort floor, the step budget, rigor raised by failed steps and `signals.rigor`, `signals.needsHuman`, provenance, run isolation with its start commit, step commits and rollback, `report.md` and `--pr-comment`.

Requirements in the target project:

- An OpenSpec project: `openspec/config.yaml`, committed. In a git work tree the skill stops when `openspec/config.yaml` is not tracked, because the run worktree sees only committed files (ADR-013 D11).
- The change folder, made with `openspec new change <change-name>` (or `/opsx:propose`). The router never creates it: `init` and `next` halt, and write nothing, when it is missing, and say that a change hosted in a store (`--store`) is not supported.
- The OpenSpec skills `openspec-propose`, `openspec-apply-change` and `openspec-verify-change`. They resolve from the session's project, not from the worktree files (check 1 of ADR-013); the skill prints one line naming untracked `.claude/skills/openspec-*` folders, because a session started inside the run worktree sees them only once they are committed.
- With `--archive`, the `openspec` CLI on `PATH` (the archive subagent runs it) and a git work tree, as for the 10x archive.
- Node.js 24 or later and `git`, as for the 10x chain.

Chain switch (`--chain`):

- Every router command takes `--chain 10x|openspec`. Any other value halts before anything is read.
- `init --chain openspec` stores `chain: "openspec"` in `openspec/changes/<change-name>/agent-smith/meta.json`. A 10x `meta.json` never gets a `chain` key, and the provenance `flags` gain `chain` only when `meta.chain` is set, so a 10x run's record keeps its keys.
- `init` without `--chain` is a 10x init. It halts when the live `openspec/changes/<change-name>/agent-smith/meta.json` holds `chain: "openspec"`, and names `--chain openspec`.
- Every other command without the flag uses the stored chain: `chain: "openspec"` in the live `meta.json`, or, when the live folder is gone, in the `meta.json` of an archive folder of the name, unless a 10x change uses the name, live under `context/changes/` or archived under `context/archive/`. Otherwise it is a 10x command. A `--chain` that contradicts the stored chain halts. A live 10x run counts as a stored chain too: `--chain openspec` on a name whose `context/changes/<change-name>/agent-smith/meta.json` exists halts, writes nothing and says the change is a 10x run.
- `archive` is not a change name for the OpenSpec chain, because `openspec/changes/archive/` is OpenSpec's archive folder: every command that resolves to the OpenSpec chain halts on it and writes nothing.

Run state and collisions:

- Run state (`run.jsonl`, `meta.json`, `last-result.json`, `report.md`) and the verdict file `verify.md` live in `openspec/changes/<change-name>/agent-smith/`, so `openspec archive` moves them with the change. OpenSpec's `validate`, `status` and `archive` accept the extra folder (`evidence/check-3-cli.md`).
- `init --chain openspec` halts, and writes nothing, when `context/changes/<change-name>/` exists: a 10x change already uses the name (D8). A branch `agent-smith/<change-name>` that belongs to a 10x run holds that folder, so a run of the other chain on it halts the same way. The branch, the worktree and the side refs keep their 10x names; no prefix is added.
- Run isolation works as in "Run isolation" above, on the branch `agent-smith/<change-name>`. The skill copies `openspec/changes/<change-name>/` into the new worktree with `cp -Rp`, only when it creates the run branch. The start commit commits `openspec/changes/<change-name>/`. The isolation gate and `init --archive` check that git does not ignore `agent-smith/run.jsonl`, `agent-smith/meta.json`, `agent-smith/report.md` and `tasks.md` of the change. A rollback sets back the file times of `tasks.md` and `verify.md`.
- With isolation off, nothing commits the code `os-apply` writes: the `os-apply` guide forbids commits, the router makes step commits only in an isolated run, and the pre-archive commit and the `os-archive` commit hold only `openspec/` paths. The skill's final message says so; commit the code yourself.
- `guardArchived` halts `init`, `next` and `status` for a name whose live folder is gone and whose archive folder exists under `openspec/changes/archive/`. OpenSpec stamps no status, so a live folder is never treated as half-archived.

Routing order (D4):

- The router reads the change from files and never runs the `openspec` CLI (D2). An artifact exists when its file does. Planning is complete when `proposal.md`, at least one `specs/**/*.md` and `tasks.md` exist (predicate A); `design.md` is optional. OpenSpec's own `isPlanningComplete` stays `false` without `design.md` while `openspec instructions apply` already reports `state: "ready"`; the router follows apply readiness, because `os-apply` is the step that needs it.
- A task row is a line the CLI's own pattern matches (OpenSpec 1.16.1, `TASK_LINE_PATTERN`): a list item under `-`, `*`, `+` or `1.`/`1)`, nested rows included, with a checkbox that holds at most one non-space marker. A row is complete only for `x` or `X`; every other marker (`[ ]`, `[]`, `[~]`) is open work. A link bullet such as `- [doc](x.md)` and a bracket with a word in it such as `- [WIP]` are no rows, as in the CLI.
- The order: no change folder halts; planning incomplete returns `os-propose` (the reason names the missing files); a `tasks.md` with no task row halts for a human; an open row returns `os-apply`; every row ticked and no verified `os-verify`, or a verified step after the last one, returns `os-verify`. Otherwise the verdict of `verify.md` decides (see "Verify verdict and fix loop").
- `os-propose` writes the planning artifacts only. `os-apply` implements every open task and ticks it. `os-verify` runs the verify skill read-only and writes `verify.md`. Each prompt carries a decision guide (`prompts/os-propose.md`, `os-apply.md`, `os-verify.md`, `os-archive.md`, see `prompts/README.md`): the subagent decides from evidence and lists the decision as an assumption, and with no evidence-backed answer ends `blocked` with `signals.needsHuman`, which halts the run.

Step verification:

- `os-propose`: the status is `done`, planning is complete and at least one artifact file (`proposal.md`, `design.md`, `tasks.md` or a `specs/**/*.md`) is newer than the step start.
- `os-apply` (template `os-apply`): the status is `done` and `tasks.md` has more ticked rows than when the step started (`before.ticks` in the log entry).
- `os-apply` in fix mode (template `os-apply-fix`): the reported status decides, as for the 10x `fix` step; the next `os-verify` checks the code.
- `os-verify`: the status is `done`, `verify.md` is a regular file newer than the step start and its header parses. The log entry gets `review: { verdict, critical, warnings }`, so `status` and the `## Review findings` section of `report.md` show it. It never has an open part: ADR-011 does not apply.
- A step that fails its check counts as a failed attempt: its retry runs one tier up, the run halts after `limits.maxAttemptsPerStep` (3) failed attempts of the same step, and the rigor level rises as for any failed step.
- An `orchestrator-error` result is no step result: the router returns the same `os-` step with the same prompt (in fix mode its `{findings}` included) and the same `before.ticks`, as in the 10x chain (see "Neutral rerun after an orchestrator fault").

Verify verdict and fix loop:

- `verify.md` starts with three lines: `Verdict: PASS`, `Verdict: PASS WITH WARNINGS` or `Verdict: FAIL`, then `Critical: <n>` and `Warnings: <n>`. Then `## Critical` and `## Warnings` with one `- ` line per issue, then the skill's report. A `Critical` count above 0 reads as `FAIL` whatever line 1 says, and so does a `- ` line under `## Critical` under a lower count: the critical count is the larger of the header count and the number of lines, so the file is never read as cleaner than it says.
- The router reads the verdict from the file each time it decides, not from the log copy, so a human who fixes the code or edits `verify.md` after a halt is routed on the file. A `verify.md` that a fresh `os-verify` leaves malformed fails that step; one that becomes unreadable or malformed after a verified `os-verify` halts the run and names the file and the line that does not parse.
- `PASS` or `PASS WITH WARNINGS` ends the run `done`, or, for a run started with `--archive`, goes to the archive branch below.
- `FAIL` returns `os-apply` with template `os-apply-fix` while fewer verified fix steps than `limits.maxFixLoops` (2) ran. The prompt carries the `- ` lines under `## Critical` (at most 20, each made one line and cut to 300 code points) as `{findings}`, or `see verify.md` when there are none. A verified fix step returns `os-verify`. Only verified fix steps count toward the cap, unlike the 10x fix loop, which counts every `fix` attempt; failed fix attempts are bounded by `limits.maxAttemptsPerStep` and the step budget.
- `FAIL` at the cap halts: `OpenSpec verify FAIL after <n> fix loops. Needs a human. Fix the issues, set the first lines of <verify.md path> to "Verdict: PASS" and "Critical: 0", then run /agent-smith:openspec-pipeline <change-name> again.` In an isolated run it ends with `Commit the edit in the run worktree first: a failed step rolls back uncommitted edits.`

Tiers, rigor and budget:

- `policy.json` `steps` holds the four steps with the pins of the 10x step each one mirrors (D9, uncalibrated): `os-propose` as `plan` (base 5, min 2, max 7, interactive), `os-apply` as `implement` (base 3, min 2, max 7), `os-verify` as `impl-review` (base 3, min 2, max 6, interactive), `os-archive` as `archive` (pinned at 3, interactive).
- The tier is the base tier, plus one rung per trailing failed attempt of the same step (`escalation.perFailure`), clamped to the step's bounds, with the effort floor of `rigor.minEffort` for the interactive steps. The fix step is an `os-apply` step and gets no bump of its own: a verified `os-apply` before it leaves no trailing failure, so it runs at the `os-apply` base unless an earlier fix attempt failed. No phase-count bump, simple-change discount, score shift, cheaper first attempt (`escalation.firstAttempt.templates` names only 10x templates) or `rigor.tierOffset` (it names `impl-review`) applies, because an OpenSpec change has no plan.
- Rigor starts from the goal class or `--rigor` and rises with failed steps and `signals.rigor`. There is no plan, so neither the phase count nor churn risk raises it, and `risk --chain openspec` reports no plan hits.
- The step budget is that of the 10x chain (12, 19 and 24). The longest failure-free path is 7 steps (propose, apply, verify, then two rounds of fix and verify); a third `FAIL` halts on the fix-loop cap before the `lean` budget.

Archive (`--archive`, D5):

- The Manual gate of the 10x archive (ADR-014) is mirrored in the skill's `archive` branch and is dormant here: `summary.manualPending`, `manualUnproven` and `uncommittedTicks` are always `[]`, because there is no plan and an open `tasks.md` row halts first. A no would point at `openspec archive <change-name> --yes --json`.
- `init --archive` stores the flag as for the 10x chain and checks that the project is a git work tree and git ignores none of the router files named above.
- At a passing verdict the router runs the git safety checks of the 10x archive (nothing staged, a symbolic HEAD, no merge, rebase, cherry-pick or revert in progress), except the `created:` line, which an OpenSpec change does not have. It halts when `tasks.md` has an open row, and when the target folder exists, naming `archive_target_exists`, the CLI error it would hit. A halt carries `archive: "skipped: ..."` and `committed`, as in the 10x chain.
- Then it writes `report.md`, whose `Archive: requested` line names the CLI command `openspec archive <change-name> --yes --json`, commits `openspec/changes/<change-name>/` with `archive.commitMessage`, and returns an `archive` action with the `os-archive` prompt at the pinned tier, `archivePath`, `commit` and `ignored`.
- `archivePath` is `openspec/changes/archive/<local YYYY-MM-DD>-<change-name>`, or `openspec/changes/archive/<change-name>` when the name already starts with a date, as the CLI names it.
- The orchestrator runs the `os-archive` prompt in one subagent. It runs `openspec archive <change-name> --yes --json` once from the run root, never the archive skill or `/opsx:archive`, and on success commits only the paths the CLI changed (`openspec/changes/<change-name>/`, the archive folder and `openspec/specs/`) as `chore(archive): close <change-name>`; when anything else is staged it ends `blocked` without committing. A CLI error (for example `archive_target_exists` or a validation error) ends it `blocked` with the error quoted, without a retry. The step has no log entry, no usage figure and no report row, as the 10x `archive` step.
- `verify-archive <change-name> --chain openspec [--path <p>]` then reads files only: `archived: true` when the archive folder exists and `openspec/changes/<change-name>/` is gone. It prints `{ archived, path, report }`; OpenSpec stamps no status, so there is no `archivedAt`. Without `--path`, several matching folders give `archived: false` with an `ambiguous` list. With a `--path` that is not an archive folder of the name, the reason lists the `<date>-<change-name>` folders that exist.

Read-only commands:

- `status <change-name> --chain openspec` adds `openspec: { planningComplete, tasks: { total, complete } }`, the reading the contract test compares with the CLI.
- `compare <change-name> --chain openspec` reads each side from `openspec/changes/<change-name>/agent-smith/` or `openspec/changes/archive/<date>-<change-name>/agent-smith/` (a live folder wins, with the same warning as for 10x). The baseline procedure of "Baseline comparison" is written for the 10x chain; `baseline-policy.json` pins no `os-` step. The input files of a side exclude `proposal.md`, `design.md`, `tasks.md`, `verify.md` and `complexity.json`, which a run produces, so a `proposal.md` that existed before the run is not listed as an input either. Pass `--chain openspec`: without it `compare` takes the chain from the project it runs in, not from `--routed` or `--baseline`.
- `risk <change-name> --chain openspec` prints the churn numbers with no plan paths.

Dropped in this chain (D10): `score`, the pre-plan steps, the phase executors, `manual-verify` (so no `--chrome`), the code re-plans, plan review, the confirmation round, lesson candidates, the advisor text (`advisor.templates` names no `os-` template) and restricted step agents (`agents.steps` names only `score`). An OpenSpec run is therefore cheaper and less checked than a 10x run.

Limits:

- The router reads OpenSpec state from files, so it can drift from the OpenSpec parser. `skills/10x-pipeline/test/openspec-contract.test.mjs` compares `status --chain openspec` with `openspec instructions apply --change <name> --json` on fixture changes (`OPENSPEC_BIN`, default `openspec`; every test skips when the binary does not start). It bounds the drift; it does not remove it.
- The task row pattern is a copy of the CLI's `TASK_LINE_PATTERN` of version 1.16.1. A later CLI version can change it, and the router then drifts until the pattern is updated. The contract test covers standard rows and rows in every list form and marker.
- `tasks.md` and `verify.md` are read only as regular files whose real path lies inside the change folder, at most 256 KiB and 64 KiB. A larger or symlinked file reads as unreadable: `tasks.md` counts no row, and `verify.md` fails the `os-verify` step or halts the run with the reason. Control and format characters in the critical lines that reach the fix prompt become a space or are dropped. The caps are constants in `openspec.mjs`, not policy keys.
- A router call without `--chain` on a name that only an OpenSpec change holds, such as `next demo` run by hand before `init`, resolves to the 10x chain and creates an empty `context/changes/demo/agent-smith/` folder. A later `init demo --chain openspec` then halts on the name collision (D8). Delete that empty folder and run the command again. The orchestrator skill always passes `--chain openspec`, so only a hand-run command causes it.
- A change whose schema skips specs (`skip_specs`) never satisfies predicate A. The `os-propose` guide ends such a step `blocked` with `signals.needsHuman`, so the run halts at once; a subagent that ignores the rule makes the run return `os-propose` until the attempt cap halts it.
- Archive date at midnight: the router computes `archivePath` with the local date when it returns the `archive` action, and the CLI takes the local date when it runs. A run that crosses midnight between the two gets another folder name, and `verify-archive --path` reports `archived: false`; its reason lists the folder that exists.
- Changes hosted in a store (`--store`) are not supported (D3): such a change sits outside the worktree and outside the rollback.
- `verify.md` has no `### F<n>` blocks or `Decision` lines, so ADR-011's open-findings routing does not apply and a passing verdict with warnings never halts.
- The guides passed five live probes (`context/changes/openspec-pipeline/evidence/check-3-live.md`); no live run of the whole skill has been done yet.
- Upgrade note: the policy gains `steps` and `prompts` keys, so a 10x run in flight when the plugin is upgraded records `provenance.drift` for `prompts` and `steps` at its next `next` call, and `compare` warns `provenance-drift:<side>:prompts,steps`. That is expected and changes no routing. A 10x run never gets a `chain` key.
