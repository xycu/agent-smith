Unattended rules for /openspec-propose. No human answers, so every ask point of the skill has a fixed answer here. The change is `{id}` at `openspec/changes/{id}/`, and the goal is the text after "Goal:" in the first lines of this prompt.

## Rules

- **GIVEN** `openspec/changes/{id}/` already exists **WHEN** Step 4 would create the change or the guardrails would ask whether to continue it or create a new one **THEN** you **MUST** continue `{id}` and never run `openspec new change` or create a change under any other name.
- **GIVEN** Step 3 picks a schema **WHEN** you run a command **THEN** you **MUST NOT** pass `--schema`, so the schema recorded in `openspec/changes/{id}/.openspec.yaml` stays in force.
- **GIVEN** the project check or `openspec context --json` reports no root, a store declaration error or any other failure **WHEN** the skill would stop and ask how to proceed **THEN** you **MUST** finish with status `blocked` and `signals.needsHuman` quoting the CLI `message`, and never run `openspec init`.
- **GIVEN** Step 1 would ask what to build **WHEN** the goal, `proposal.md` or another file already in `openspec/changes/{id}/` describes the change **THEN** you **MUST** take the missing input from them and cite the source.
- **GIVEN** the goal is empty and `openspec/changes/{id}/` holds no file beyond `.openspec.yaml` that describes the change **WHEN** you cannot tell what to build **THEN** you **MUST** finish with status `blocked` and `signals.needsHuman` naming what is missing, and write no artifact.
- **GIVEN** the request holds an ambiguity that would materially change scope, externally observable behavior, compatibility or acceptance criteria **WHEN** the code, tests, docs, `openspec/specs/` or the `context` of `openspec/config.yaml` settle it **THEN** you **MUST** decide from that evidence, record the decision in the artifact it shapes and list it as an assumption with its `file:line`.
- **GIVEN** such a material ambiguity **WHEN** no repository evidence settles it **THEN** you **MUST** finish with status `blocked` and `signals.needsHuman` naming the open question, and leave the artifacts you already wrote in place.
- **GIVEN** a minor detail is open **WHEN** you write an artifact **THEN** you **SHOULD** make a reasonable assumption and record it in the planning artifacts, as the skill says.
- **GIVEN** Step 6 would ask because the target project is unclear, the source is unavailable, an artifact needs user input or an open question in `design.md` would change the tasks **WHEN** repository evidence answers it **THEN** you **MUST** answer from that evidence, cite `file:line` and list it as an assumption.
- **GIVEN** Step 6 would ask a question **WHEN** no repository evidence answers it **THEN** you **MUST** finish with status `blocked` and `signals.needsHuman` naming the question.
- **GIVEN** a resolved output path falls outside `openspec/changes/{id}/`, or an instruction delegates an artifact to a skill or command that cannot write there **WHEN** the skill says to stop and tell the user **THEN** you **MUST** finish with status `blocked` and `signals.needsHuman` naming the path.
- **GIVEN** you write any file **WHEN** you pick its path **THEN** you **MUST NOT** write outside `openspec/changes/{id}/`, and never into `openspec/specs/`.
- **GIVEN** the planning boundary of the skill **WHEN** the goal also asks to build or fix something **THEN** you **MUST NOT** edit project code, run the apply workflow or tick a row of `tasks.md`.
- **GIVEN** an artifact already exists in `openspec/changes/{id}/` **WHEN** you continue the change **THEN** you **SHOULD** re-read it from disk, keep it and create only the missing artifacts, editing an existing one only where it contradicts the goal and listing each such edit as an assumption.
- **GIVEN** `openspec status --change "{id}" --json` gives the required set **WHEN** you decide which files to write **THEN** you **MUST** write `proposal.md`, at least one delta spec under `specs/<capability-path>/spec.md` and `tasks.md`.
- **GIVEN** `openspec status --change "{id}" --json` reports `specs` as `skipped` **WHEN** you would write no delta spec **THEN** you **MUST** finish with status `blocked` and `signals.needsHuman` saying the schema skips specs, because the pipeline needs at least one delta spec to go on.
- **GIVEN** the schema lists `design` in the `requires` of `tasks` **WHEN** the design instruction marks `design.md` as conditional **THEN** you **SHOULD** still write a short `design.md`, because without it `isPlanningComplete` stays false and the verify step reports Design Adherence as not verified.
- **GIVEN** you skip `design.md` anyway **WHEN** `tasks` reads `blocked` only because of that skip **THEN** you **MUST** write `tasks.md` anyway, as the skill says for a skipped conditional dependency, and list the skip with its reason as an assumption.
- **GIVEN** you write a delta spec **WHEN** you add a requirement **THEN** you **MUST** put it under `## ADDED Requirements`, `## MODIFIED Requirements`, `## REMOVED Requirements` or `## RENAMED Requirements` as `### Requirement: <name>` with at least one `#### Scenario:` that has WHEN and THEN bullets.
- **GIVEN** you write `tasks.md` **WHEN** you add a task **THEN** you **MUST** write it as an unticked row `- [ ] X.Y <task>` that states how to verify it, so the apply step finds at least one open row.
- **GIVEN** every file of the required set exists **WHEN** you are about to finish **THEN** you **MUST** run `openspec validate "{id}" --json` and fix every `ERROR` issue in the artifacts before you end.
- **GIVEN** `proposal.md`, at least one `specs/**/*.md` and `tasks.md` with at least one `- [ ]` row exist and validate reports no `ERROR` **WHEN** the skill would present the artifacts and wait for a new request **THEN** you **MUST** finish with status `done` and name the artifacts you wrote in `note`.
- **GIVEN** the skill would ask a question **WHEN** you run unattended **THEN** you **MUST NOT** print a plain-text question or wait for input, and you answer by the rules above.
- **GIVEN** you record an assumption in the RESULT line **WHEN** you write it **THEN** you **MUST** cite the evidence for it.
