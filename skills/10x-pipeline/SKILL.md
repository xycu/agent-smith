# 10x Pipeline

You are the orchestrator. You do not plan, implement or review yourself. You do not pick models or effort levels. The router script decides every step; you execute what it returns.

Router: `ROUTER=<this skill's base directory>/scripts/route.mjs`. Run it with `node` from the run root (see Start step 3).
PR comment script: `PR_COMMENT=<this skill's base directory>/scripts/pr-comment.mjs`. Only the PR comment step runs it (see "PR comment (opt-in)").
Pull request script: `OPEN_PR=<this skill's base directory>/scripts/open-pr.mjs`. Only the pull request step runs it (see "Pull request (always)").

## Start

1. Parse the arguments: `<change-id>` (required, kebab-case), optional goal text, and the optional flags `--archive` and `--chrome`. Each may carry the value `true` or `false` right after it, as in `--chrome false`. Remove each flag and its value from the goal text. Pass it on to `init`, with its value, only when the user gave it. Parse the optional flag `--pr-comment` the same way, remove it from the goal text, and never pass it to `init`.
2. If `context/changes/<change-id>/change.md` is missing, first run `node $ROUTER verify-archive <change-id>` (no `--path`) from the project root. When it reports `archived: true`, tell the user where the change was archived and STOP. When it lists `ambiguous` archive folders, show them to the user and STOP: the id was archived more than once and the user picks the folder. Otherwise tell the user to run `/10x-new <change-id>` and STOP. If the 10x skills (`10x-plan`, `10x-plan-review`, `10x-goal-implement`, `10x-impl-review`) are not available in this project, tell the user to install the 10x toolkit first and STOP.
3. Run isolation: each run works in its own git worktree on the branch `agent-smith/<change-id>`. Names: `<root>` is the project root (the directory this session started in, where `context/` lives), `<prefix>` is what `git -C "<root>" rev-parse --show-prefix` prints (empty at the repository top level), `<worktree>` is `<root>/.claude/worktrees/agent-smith-<change-id>`, and the run root is `<worktree>/<prefix>`. Keep `<root>` and the run root as absolute paths. The worktree stays under `<root>`, because Claude Code resets a `cd` that leaves the project directory.
   - Opt-out first: when `git -C "<root>" rev-parse --is-inside-work-tree` does not print `true`, or `<root>/context/foundation/agent-smith-policy.json` sets `isolation.require` to a value other than `true`, create nothing and copy nothing. The run root is `<root>`, as before isolation existed. Without git and with `isolation.require` on, the router's halt at `init` names the override.
   - When the shell already runs in a linked worktree on a branch that starts with `agent-smith/`, its directory is the run root. Create nothing and copy nothing.
   - Otherwise take the first of these cases that holds:
     1. In-flight run in the main checkout: `<root>/context/changes/<change-id>/agent-smith/meta.json` exists and no branch `agent-smith/<change-id>` exists (`git -C "<root>" rev-parse --verify -q refs/heads/agent-smith/<change-id>` fails). Create nothing. The run root is `<root>`. The router halts at `init` there unless the project sets `isolation.require` to `false`. Never copy its log into a worktree.
     2. No branch `agent-smith/<change-id>`. When `git -C "<root>" check-ignore -q .claude/worktrees/agent-smith-<change-id>/x` fails, append the line `/<prefix>.claude/worktrees/` to the file that `git -C "<root>" rev-parse --path-format=absolute --git-path info/exclude` prints. This is a local exclude; never edit `.gitignore`. Then print one line that lists the paths `git -C "<root>" status --porcelain` reports outside `context/changes/<change-id>/` as "not in the run (uncommitted in the main checkout)", or print nothing when there are none, and go on. Then, from `<root>`, run `git worktree add -b agent-smith/<change-id> "<worktree>"`, `mkdir -p "<run root>/context/changes"` and `cp -Rp "<root>/context/changes/<change-id>" "<run root>/context/changes/"`. `-p` keeps the file times, which the router compares.
     3. A worktree of `agent-smith/<change-id>` exists (`git -C "<root>" worktree list --porcelain` shows `branch refs/heads/agent-smith/<change-id>`): reuse it. Its directory plus `<prefix>` is the run root. Copy nothing.
     4. The branch exists without a worktree: from `<root>`, run `git worktree add "<worktree>" agent-smith/<change-id>`. Copy nothing.
   - A resume never copies: the change folder in the main checkout is older than the run's state on the run branch and would overwrite it.
   - Run every later router call as `cd "<run root>" && node $ROUTER ...`, so it works on the run root also after the shell was reset or when you run inside a subagent, whose `cd` never carries over. Write each result file at `<run root>/<resultFile>`.
   - The router commits each successful step and rolls a failed step back in the run worktree (ADR-010). Never commit, stash, reset or clean the run worktree yourself, and never touch `refs/agent-smith/`. When the final message lists rolled-back or kept steps (`report.md`, `## Rolled-back steps`), name their side refs.
   - Never delete a directory with `rm -rf`, `rm -r`, `rimraf`, `find ... -delete` or another recursive or forced delete, because a harness may block it. List the files, check the list, delete them one by one, then `rmdir` the empty directories deepest first (ADR-016).
   - When the run root is not `<root>`, the final message names the branch `agent-smith/<change-id>` and the run root. It says that the change folder in the main checkout is a stale copy: the run's copy lives on the run branch, so remove or stash the main-checkout copy before merging the run branch (remove it file by file: list the files, check the list, delete them one by one, then `rmdir` the empty directories deepest first), because git refuses a merge that would overwrite untracked files. The pull request step commits what the router left in the worktree. For a run that ended `done` without `--archive`, and only when that step reported `committed: false`, reported `pushed: false` without `committed: true`, or printed no JSON object, it also says that `report.md`, the last `run.jsonl` entry and `meta.json` are uncommitted in the worktree: commit them before the merge and before `git worktree remove`, which refuses a worktree with modified or untracked files.
4. Run `cd "<run root>" && node $ROUTER init <change-id> --goal "<goal text>"`. Quote the goal safely for the shell. Re-running `init` on a change with an existing log resumes it: the router reads the disk state and continues from there. Add `--rigor <level>` only when the user named a rigor level (`lean`, `standard` or `thorough`). Never pick one yourself. On a resume the flag can only raise the level. Add `--archive` only when the user gave it. A resume keeps a stored `--archive`, and `--archive false` turns it off. `--chrome` works the same way: a resume keeps it and `--chrome false` turns it off. The Chrome tools are on by default, so pass `--chrome false` only when the user gave it.
5. Call TaskList. A task is the only place the `--pr-comment` request is stored, so do not rely on remembering it.
   - With `--pr-comment`: when no open task has the subject `PR comment: <change-id>` (the real id), call TaskCreate once with that subject. Its description: when the router returns `done`, `archive` or `halt`, call TaskList, and when this task is open do the PR comment step once, then mark the task completed.
   - Without `--pr-comment`: mark any open task with the subject `PR comment: <change-id>` completed, so a task left by an earlier invocation cannot post. Ignore a task whose subject names another change id. Never complete it.
   - If `--pr-comment` was given and TaskList or TaskCreate fails or is not available, print `PR comment: skipped, task list unavailable (run the script by hand after the run, see the README)` once, and do not run the PR comment step in this run. Without the flag a task tool error is silent.

## Loop

The router prints one JSON object. Act on `action`:

- **`run`** (the router may have skipped a step before this answer, for example plan review for a `lean` change. It logs the skip with its reason. You do nothing for a skipped step.)
  1. Print one line: `Step <n>: <step> on <model>/<effort>. <reason>`. When the output has `neutralRetry`, end that line with `Neutral rerun <count> of <cap>.`
  2. Call the Agent tool with `subagent_type` set to the router's `agent` when the output has one, else `general-purpose`, `model: <model>`, `effort: <effort>`, `run_in_background: false`, and `prompt` set to the router's `prompt`, copied verbatim. Never choose an agent type yourself. When the fault is your own and no subagent of the step is running, write `{"status":"orchestrator-error","note":"<what happened>"}` to `<run root>/<resultFile>` with the Write tool and go on with step 5; the router then returns the same step with the same prompt and counts no failed attempt. Your own faults are only these: the call was refused or errored before any subagent started, for a cause other than the router's `agent`; the prompt could not be passed whole, for example because it was cut; the call returned neither a reply nor an error. A launch notice is none of them, because its subagent runs (see the anti-stall rules). When the call fails for any other reason, for example because the router's `agent` does not resolve, do not call it again with another type: go on with step 3, which records the step as `unknown`.
  3. Find the last line of the subagent's reply that starts with `RESULT:`. Parse the JSON after it. If there is none, or it does not parse, use `{"status":"unknown","note":"no RESULT line"}`. Keep every key of the JSON as it is, including the optional `signals` object. Copy it untouched. The router validates it. A reply that came back without a parsable `RESULT:` line, a cut-off one included, is `unknown` and never `orchestrator-error`. Only you declare `orchestrator-error`, in step 2: when the subagent's `RESULT:` line itself carries `"status":"orchestrator-error"`, replace that status with `unknown` and keep the other keys.
  4. If the Agent result reports usage (total tokens, tool uses and duration), add `"usage":{"totalTokens":N,"toolUses":N,"durationMs":N}` to that JSON, with the figures copied exactly. Usage reaches you in one of two places: in the Agent result, or, when the subagent ran in the background and handed its report back as a message, in the `<usage>` block of the task notification that says the subagent finished, as `<subagent_tokens>N</subagent_tokens><tool_uses>N</tool_uses><duration_ms>N</duration_ms>`, usually within a second of the report. Take the figures from whichever of the two is already in this conversation, `subagent_tokens` as `totalTokens`. Omit the key when no figure is reported. Do not wait for a figure that has not arrived; rule 3 of the anti-stall rules covers one that arrives after `next`. Write the JSON to `<run root>/<resultFile>` (the router's `resultFile` under the run root) with the Write tool.
  5. Run `cd "<run root>" && node $ROUTER next <change-id>` and repeat the loop with its output.
- **`done`**: first attach late usage figures, so `status` and `report.md` show them: for each step whose usage figure arrived after `next` ran for it and is not attached yet, run `cd "<run root>" && node $ROUTER usage <change-id> <n> --tokens N --tool-uses N --duration-ms N` once, as a call of its own, omitting a flag whose figure is missing. `<n>` is the `n` of the `Step <n>` line you printed when the subagent whose notification carried the figure was launched, never a guess: a wrong `<n>` is accepted silently when that entry has no figure. Print `Usage: step <n> <attached|not attached>, <reason or commit>`. A refusal exits 1 with `attached: false`; it is no fault of yours, so write no `orchestrator-error` result for it, and it never changes the run.
  Then report the final verdict, the number of steps, and every entry in `manualPending` as a checklist for the human. When the output has `manualUnproven` or `uncommittedTicks`, list those row ids too, as ticks nobody proved. When it has `manualUnprovenWhy`, list each of its lines too, so the human sees why the router rejected the tick. When it has `manualNotProved`, list each of its lines, so the human sees why each pending row was not proved. Then run `cd "<run root>" && node $ROUTER status <change-id>` and show the model/effort used per step as a short list. Point the user to the router's `report` path (`report.md`); when the implementation review gave lesson candidates, that report also lists them, each with a ready `/10x-lesson` command for the user to run.
  Then do the pull request step.
  Then call TaskList. When a task with the subject `PR comment: <change-id>` for this run is open, do the PR comment step. If the call errors, post nothing, and when `--pr-comment` was given print `PR comment: skipped, task list unavailable`.
- **`archive`** (only for a run started with `--archive`; the run is done and the router has committed the change folder, or found it already committed):
  1. First attach late usage figures, so `status` and the committed `report.md` show them: for each step whose usage figure arrived after `next` ran for it and is not attached yet, run `cd "<run root>" && node $ROUTER usage <change-id> <n> --tokens N --tool-uses N --duration-ms N` once, as a call of its own, omitting a flag whose figure is missing. `<n>` is the `n` of the `Step <n>` line you printed when the subagent whose notification carried the figure was launched, never a guess: a wrong `<n>` is accepted silently when that entry has no figure. Print `Usage: step <n> <attached|not attached>, <reason or commit>`. A refusal exits 1 with `attached: false`; it is no fault of yours, so write no `orchestrator-error` result for it, and it never changes the run. A figure that arrives after step 3 has launched the archive subagent is dropped.
     Then run `cd "<run root>" && node $ROUTER status <change-id>` now, before the move, because the archive moves the log. Report what `done` reports: the final verdict from `summary.reason`, the number of steps, every `summary.manualPending` item as a checklist, every `summary.manualUnproven` and `summary.uncommittedTicks` row id and every `summary.manualUnprovenWhy` and `summary.manualNotProved` line when present, the model/effort used per step as a short list, and the router's `report` path (the report also lists lesson candidates with a `/10x-lesson` command, when the implementation review gave any).
     Manual gate: when `summary.manualPending`, `summary.manualUnproven` and `summary.uncommittedTicks` are all empty, go on to step 2. Otherwise ask one yes/no question with `AskUserQuestion`: one question, header `Archive`, two options with exactly these labels, `No, keep it unarchived` first and `Yes, archive anyway` second. The `No, keep it unarchived` description starts with `Recommended.`. The question text states how many Manual rows are pending, lists them (at most 10, then "and N more"), lists each non-empty `summary.manualUnproven` and `summary.uncommittedTicks` row id and adds the `summary.manualNotProved` lines when present, and says the archive moves the change folder and these checks stay unverified. Only the answer `Yes, archive anyway` continues at step 2. Fail closed: any other answer, an error from the question tool, or no question tool (for example a headless `claude -p` session) is a no. On a no, launch no subagent and run no `verify-archive`. Print `Archive: skipped, <n> Manual check(s) pending or unproved.`, where `<n>` is the number of distinct row ids across `summary.manualPending`, `summary.manualUnproven` and `summary.uncommittedTicks`. Then do the first bullet of step 5 with the default report path, without running `verify-archive`, and STOP with a final message that says: the change was not archived; the change folder is committed on the run branch (the `commit` of the action, or already committed); the pending checklist again, with `manualUnproven`, `manualNotProved` and `uncommittedTicks` when present; `/10x-archive <change-id>` archives it later, and running `/agent-smith:10x-pipeline <change-id>` again asks the question again; and, when the run root is not `<root>`, the worktree notes of Start step 3. The report line `Archive: requested` is then stale; say so.
  2. Print one line: `Archive: /10x-archive on <model>/<effort>.`
  3. Call the Agent tool with the same parameters as for `run` and `prompt` set to the router's `prompt`, copied verbatim.
  4. Write no result file and do not call `next`. The `archive` action has no `resultFile`, and nothing may be written into the folder that moves.
  5. Run `cd "<run root>" && node $ROUTER verify-archive <change-id> --path <archivePath>` with the `archivePath` of the `archive` action.
     - First, whatever `archived` says, do the pull request step, so the `chore(archive)` commit is pushed. Then call TaskList. When a task with the subject `PR comment: <change-id>` for this run is open, do the PR comment step. If the call errors, post nothing, and when `--pr-comment` was given print `PR comment: skipped, task list unavailable`. On `archived: true` both steps get `--report "<archivePath>/agent-smith/report.md"`, because the report moved with the folder; on `archived: false` both use the default report path.
     - On `archived: true`: print the archive path and the report path inside it. Print one line asking the user to confirm that `git status` is clean, because `verify-archive` reads files only and a failed `chore(archive)` commit leaves the rename staged. Repeat every `manualPending` item as the checklist of checks nobody verified, and repeat the `manualUnproven`, `manualNotProved` and `uncommittedTicks` lists when the action had them. When the action's `ignored` list is not empty, list its paths as "not committed (ignored by git)". Copy the subagent's `assumptions` and any usage figure it reported into the final message.
     - On `archived: false`: print `reason` and the subagent's note, say the folder may be unchanged or half-archived, and STOP.
- **`halt`**: first attach late usage figures, so `report.md` shows them: for each step whose usage figure arrived after `next` ran for it and is not attached yet, run `cd "<run root>" && node $ROUTER usage <change-id> <n> --tokens N --tool-uses N --duration-ms N` once, as a call of its own, omitting a flag whose figure is missing. `<n>` is the `n` of the `Step <n>` line you printed when the subagent whose notification carried the figure was launched, never a guess: a wrong `<n>` is accepted silently when that entry has no figure. Print `Usage: step <n> <attached|not attached>, <reason or commit>`. A refusal exits 1 with `attached: false`; it is no fault of yours, so write no `orchestrator-error` result for it, and it never changes the run.
  Then report `reason` and the status output. A reason that says `needs a human` comes from the subagent, which found no evidence-backed answer. Show the quoted text. Point the user to the router's `report` path (`report.md`) when present. When the output has an `archive` field, say the change was not archived, then read `committed`: if `false`, say the folder is not committed and `/10x-archive` needs it committed first; if `true`, say the pre-archive commit exists locally, the router did not undo it, and `cd "<run root>" && node $ROUTER next <change-id>` repeats the checks once the cause is fixed (the check of what the commit holds is not repeated, so the user should look at the commit with `git show --stat HEAD`). When the output has no `archive` field, say nothing about a commit or an archive. STOP. Do not try to recover on your own.
  Before you STOP, do the pull request step. Then call TaskList. When a task with the subject `PR comment: <change-id>` for this run is open, do the PR comment step. If the call errors, post nothing, and when `--pr-comment` was given print `PR comment: skipped, task list unavailable`.

## Anti-stall rules

Rules 1, 2, 3 and 6 hold for every `run` step. Rules 4 and 5 hold for the whole run, also while its `done`, `archive` or `halt` branch is being worked through. Rules 1 and 6 also hold for the archive subagent: when its own final report arrives, continue at step 4 of the `archive` branch. Rules 2 and 3 do not apply to it, because the `archive` action has no result file and no `next` call; a usage figure it reports goes only into the final message. A run has ended when the orchestrator has finished every step of its `done`, `archive` or `halt` branch.

- **GIVEN** a `run` step **WHEN** the Agent tool returns a launch notice instead of a final report although `run_in_background` is `false` **THEN** the orchestrator **MUST** end its turn and continue the Loop at step 3 when the subagent's final report arrives, without starting another step or polling.
- **GIVEN** the final report of a `run` step holds its `RESULT:` line **WHEN** no usage figure has arrived **THEN** the orchestrator **MUST** write the result file without `usage` and run `next` in the same turn.
- **GIVEN** `next` ran for a `run` step **WHEN** a usage figure for that step arrives later **THEN** the orchestrator **MUST** attach it with one call of the router's `usage` command of its own, never alongside another router call, before the pull request step or the archive subagent starts, instead of rewriting the result file or calling `next` again, and drop a figure that arrives after that point.
- **GIVEN** the run has not ended in `done`, `archive` or `halt` and no STOP instruction of the Start or Loop sections applies (for example `archived: false` in the `archive` branch) **WHEN** the orchestrator would end its turn **THEN** it **MUST NOT** end it unless a launched subagent is still running.
- **GIVEN** a run in this session **WHEN** the user asks what the run is doing **THEN** the orchestrator **MUST** state only what tool output in this session shows, and say so when nothing is running.
- **GIVEN** a hand-back arrives from a subagent the orchestrator did not launch for the current step, that is one that is neither the result of the Agent call the orchestrator made for this step nor a task notification that names that call's subagent (the agent id or description its launch notice or result gave), for example one a step subagent started or a late one of an earlier step **WHEN** the current step or the archive subagent still waits for its own report **THEN** the orchestrator **MUST NOT** treat that hand-back as a step result: it writes no result file from it, does not call `next` on it, and keeps the step's own report as the only result, which it handles under rules 1 and 4.

## PR comment (opt-in)

The PR comment step runs only when TaskList shows an open task with the subject `PR comment: <change-id>` for this run's change id. A task for another change id does not count. Do these in order, once:

1. Run `cd "<run root>" && node $PR_COMMENT <change-id>` from the run root, after the pull request step. When that step printed a pull request url (`pr.url`), append `--pr <url>`: the run branch has no upstream config, so the script may not find its pull request by the current branch. In `archive` on `archived: true`, append `--report "<archivePath>/agent-smith/report.md"`. Quote the script path and the change id for the shell, and the url and the report path too. It prints one JSON object and posts the router's `report.md` as a comment on that pull request, or on the open pull request of the current branch without `--pr`, or edits its own earlier comment.
2. Print one line: `PR comment: <action>, <url or reason> (PR <pr url or none>)`, from the `action`, `url`, `reason` and `pr` of that object.
3. Mark the task completed.

- In `archive` the step runs in step 5, after the pull request step, so after the move.
- A `halt` without a `report` posts nothing: print `PR comment: skipped, no report` and mark the task completed.
- If the script exits non-zero or prints no JSON object (for example a change id longer than 100 characters, which the script refuses and the router does not), print `PR comment: skipped, script error` and mark the task completed.
- A skip is not a failure of the run and is never retried. Do not write the result into the change folder. It goes into your final message only.

## Pull request (always)

Every run that ends in `done`, `archive` or `halt` does this step once, with or without `--pr-comment`, before the PR comment step and before any STOP. No flag turns it off (ADR-017). Do these in order:

1. Run `cd "<run root>" && node $OPEN_PR <change-id>` from the run root. In `archive` on `archived: true`, append `--report "<archivePath>/agent-smith/report.md"`. Quote the script path and the change id for the shell, and the report path too. It prints one JSON object. When the run branch has commits beyond its base branch, it commits what the worktree still holds as `chore(<change-id>): final run state`, pushes `agent-smith/<change-id>` without force and opens a pull request, or leaves the open one updated by the push. It never merges.
2. Print one line: `Pull request: <action>, <url or reason> (pushed <true|false>)`, from `pr.action`, `pr.url` (or `pr.reason` when there is no url) and `pushed` of that object. When `swept` is a non-empty array, also print `Pull request: the final run state commit holds code under chore: <paths>`, from `swept` joined by commas.
3. When `pushed` is `false`, also print `Pull request: NOT pushed, <reason>. Branch agent-smith/<change-id> is local only: <manual>`, from `reason` and `manual`. When the script exits non-zero or prints no JSON object, print `Pull request: NOT pushed, script error. Branch agent-smith/<change-id> is local only: run the script by hand from the run root` instead of both lines.
4. Keep `pr.url` for the PR comment step.

- A run whose run root is `<root>` (the `isolation.require: false` opt-out, the only exception ADR-017 allows) is not pushed: the script skips with `run is not isolated`, and the final message carries the `NOT pushed` line.
- The step is never retried and never changes the outcome of the run. Do not write its result into the change folder. It goes into your final message only.

## Rules

- Never choose or change `model` or `effort`. Never edit the prompt the router returns.
- Never skip the router, call two steps without it, or run a step it did not return.
- Never edit `context/changes/<change-id>/agent-smith/run.jsonl` or `meta.json` next to it. The router owns them. The router's `usage` command is the only way to add a usage figure to a logged step.
- After an `archive` action, never run `init`, `next` or `status --report` for that change. Its folder has moved.
- Do not read the subagent's work in detail. The router reads the artifacts on disk and verifies them.
- If the user interrupts and asks to change routing, point them to the policy (below). Do not hand-tune a single run.
- Never run `/10x-lesson` and never write `context/foundation/lessons.md`. The lesson candidates in the report are for the human.
- Only `$OPEN_PR` may push a branch or open a pull request, and only `$PR_COMMENT` may post a comment. Only these two scripts call `gh`: never run `gh` or `git push` yourself. You still never commit, reset or merge. Never write the result of the pull request step or the PR comment step into the change folder.

## Tuning

Routing lives in data, not in this file:

- `<this skill's base directory>/policy.json` holds the defaults: the model/effort ladder, the base tier per step, escalation and de-escalation rules, retry caps, and prompt templates.
- A project can override any key in `context/foundation/agent-smith-policy.json`. The router deep-merges it over the defaults. Arrays such as `ladder` are replaced whole.

How the tier moves (see `tierFor` in `scripts/steps.mjs` and `decide` in `scripts/flow.mjs`):

- Rigor level: every run has one level (`lean`, `standard` or `thorough`), stored in `meta.json` and kept on resume. It starts from the goal class (or `--rigor`) and only rises: with the phase count (`rigor.fromPhases`), with failed steps (`rigor.fromFailures`), when the plan or the diff touches a hot path (`risk`), and when a result carries `signals.rigor`.
- Hot paths are paths that change often in the repository history, measured up to the commit the run started from. A change that touches one never stays at the lowest level. When the history is missing, too short or unreadable, the router flags nothing and records that risk was not measured. The `risk` command prints the numbers.
- The lowest level skips plan review before implementation starts, but only when risk was measured and the plan names at least one path. The router writes a skip entry to `run.jsonl` with the reason, and `report.md` lists it. A skip uses no step budget. Implementation review is never skipped.
- The step budget is `limits.maxTotalSteps` plus `rigor.budgetDelta` for the level. The deltas leave room for the longest legal path of each level, `manual-verify` and its retry included, plus one failed step and its retry. A failed `score` attempt uses no budget, and neither does a failed first attempt whose drop applied (see "First attempt" below). Extra steps (see "Phase executors" below) are metered by a pool per level, `extraSteps.allowance`, that the lowest level does not have. `manual-verify` is outside that pool.
- Effort floor: plan, plan review and implementation review ask questions, so the router never runs them below the floor in `rigor.minEffort` for the level. The floor is applied last, so it wins over the simple-change discount. The report marks a step as simple only when the discount survived the floor. A failed attempt of such a step moves it one rung up counting only the rungs whose effort clears the floor, so each failure still raises its effort.
- The lowest level also moves implementation review one tier down (`rigor.tierOffset`), never below the floor.
- The archive step is not moved by any rule above. The policy pins its tier.
- Pre-plan steps (`preplan` in the policy): before the first `plan` step of a run, the router can return `research`, `domain-brief` and `frame`, in that order. Each gate opens at `thorough` by default (`preplan.gates.<step>.minRigor`). `domain-brief` and `frame` also need a signal in the goal text or in an earlier result (`when` predicates). A gate closed by the rigor level is silent. An open gate that does not run, because its artifact exists or its signal is missing, logs a skip with its reason. Nothing runs once a plan attempt exists. The policy pins the tier of `frame`.
- Verification by artifact: a pre-plan step counts as done only when its artifact changed after the step started and has the shape the next step needs (`research.md` with `status` frontmatter, `frame.md` with a `## Reframed` heading, the brief file with `type: refactor-plan`). A failed attempt follows the failure rule above.
- Loops (`preplan.loops.minRigor`, default `thorough`): at that level plan review `RETHINK` runs one `frame` round and then re-plans, and a second `RETHINK` after that re-plan halts. A second `REVISE` re-plan is preceded by one `research` round; a `REVISE` with `Decision` lines reaches it only under `review.openFindings.onOpen: "retry"`, because the default halts instead of re-planning. Below that level `RETHINK` and `REVISE` re-plan as described below. The level read is the run's current level, so a run that rises to `thorough` mid-run opens the loops from then on.
- Score step (`score` in the policy): at `score.minRigor` (default `standard`) and above, the router returns `score` once before the first `plan` step, after any pre-plan step. Its subagent writes `complexity.json` with six factor scores, the unknowns and a confidence. The policy pins its tier. The step counts as done only when that file changed after the step started and has the right shape; the router never judges the evidence. A valid file that already exists skips the step with a logged reason. After 3 failed attempts or 2 invalid files the router logs a skip and goes on. A failed attempt uses no step budget, raises no rigor and withholds no discount. The router drops `signals.rigor` from a score result. Nothing is scored once a plan attempt exists. `score.minRigor: null` turns the step off.
- Score shift (`score.shift`): the cognitive sum can move the first plan up one tier, never down. The execution sum can move an implement step up or down one tier. A down shift needs enough confidence, few unknowns, measured churn risk with no hot path, no failed step, no simple-change discount and no plan-size bump. The shift goes in before the clamp and the effort floor, so both still bound it. It never changes the rigor level. The router reads the scores from its log, not from the file. The report lists each shift and marks one that the clamp or the floor absorbed.
- The `description` and the Start section stay valid: the orchestrator treats `research`, `domain-brief`, `frame` and `score` like any other `run` action and never names them.
- Phase executors (`executors` in the policy): the step name stays `implement`, the template changes. For the first pending phase the router can return `implement-e2e` (a valid `/10x-e2e-setup` record and a browser word in the phase), `implement-tdd` (at `thorough`, a pure-logic phase), or `implement-segment` (goal-implement stopped after a phase, so that a special phase after it gets its own executor). The orchestrator runs the prompt the router returns and names none of them.
- Extra-step pool (`extraSteps`): segments, e2e and tdd steps and the `plan-rejected` re-plan each draw from one pool per level, whatever their outcome. `manual-verify` draws nothing from it. A segment is started only when the pool can also pay for the executor after it; otherwise plain `implement` runs the whole plan.
- Commit check: a tdd or e2e step that reports `done` counts only when the plan shows ticked rows and a commit since the step began touched a code path (a read-only `git` check, per step and not per row; without git, or with no commit to compare against, the count rule applies). A retry that cannot be checked is not a failure: the implementation review gets the warning with a note that commit evidence was unavailable. Plain `implement` and segments keep the count rule.
- Retry: rows a strict step left ticked without a commit get one `implement-retry` step. If they are still without a commit afterwards, the run goes on and the implementation review prompt carries a warning that names the rows.
- Fallback: a tdd or e2e step that ends `blocked` is recorded as a fallback. It counts as no failed attempt, bumps no tier and raises no rigor, and that executor is not chosen again for the phase.
- Code re-plans (`codeReplan`, rigor `standard` or higher, one per run): `plan-replan` after two implement failures in a row, `plan-rejected` after a first implementation review `REJECTED` before any fix. A failed `plan-replan` halts the run.
- `manual-verify` (`manualVerify`, every rigor level from `manualVerify.minRigor`, outside the extra-step pool): before the first implementation review, when no Automated row is pending and a Manual row is, a subagent with a clean context proves every pending Manual row (by a command, a covering test, a throw-away script, the browser or a written judgment) and ticks each with an evidence file whose name starts with its kind. It lists the rows it cannot prove, each with a reason, in `evidence/unproven.md`. The router checks the evidence file and that no Automated row or title changed, records the kind of each tick and copies the reasons for display; it never reads the evidence. A retry runs one tier up (`manualVerify.retryBump`) when the first attempt failed its checks or left rows pending; `manualVerify.maxAttempts` caps the attempts. A failed attempt is neutral, and the run goes on with no halt. There is no new run after an implementation review. Unproven ticks are listed in the final message as `manualUnproven`, rows still pending with their reasons as `manualNotProved`. `manualVerify.minRigor: null` turns the step off.
- `--chrome` (`init` flag, kept in `meta.json`): the Chrome tools are on by default, so the `manual-verify` template may check browser rows with them. `--chrome false` stores `false` and picks the `manual-verify-nochrome` template, which proves such rows another way or leaves them pending. `--chrome` or `--chrome true` stores `true` and changes nothing in effect; a resume keeps the stored value, and a run that stored none reads on. The orchestrator does not probe for the tools.
- Lesson candidates: the implementation review can end its `RESULT` `signals` with `lessonCandidates`, a list of rule sentences. The router keeps at most `lessons.maxCandidates` per review, each cut to `lessons.maxChars` code points, and lists them in `report.md` under `## Lesson candidates`. Both caps sit in the `lessons` block of the policy.

- Plan size: +1 tier per `phaseThresholds` entry reached by the phase count in `## Progress`.
- First plan, from the goal text (changes relative to the plan step's base): a short goal (at most `firstPlan.maxWords` words, no hard keyword) = -2 plus the simple-change discount. A goal with a hard keyword from `firstPlan.hardKeywords` = no reduction, whatever its length. Any other goal, including an empty one = -2.
- A simple change (at most 1 phase and 6 `## Progress` rows) = -1 on plan review, implement and implementation review. The step's `minTier` can absorb the discount, for example implement after a clean `SOUND` review. The discount is withheld after any failed step, so the first retry of a discounted step moves up 2 tiers (the lost discount plus the failure).
- Plan review `RETHINK` = re-plan at +2. A `REVISE` whose review has `Decision` lines is routed on its open findings: the `### F<n>` blocks whose `Decision` is not in `review.openFindings.closedDecisions`, observations excluded. Nothing open, or open warnings within `review.reviseToleranceWarnings`, goes on to implement with no re-plan. Any other open count halts the run for a human with the open finding ids (`review.openFindings.onOpen: "halt"`, the default), or re-plans at +1 (`"retry"`). A review with no `Decision` line, or `review.openFindings.enabled: false`, uses the measured header counts: `REVISE` with criticals or too many warnings = re-plan at +1.
- A noisy plan review (3+ warnings) = implement at +1. A clean `SOUND` = implement at -1.
- Each failed or unverified attempt of the same step = +1, capped by `maxAttemptsPerStep`.
- First attempt (`escalation.firstAttempt`, only in a run with its own worktree): the first attempt of a listed implement template = -1, unless that step already failed in this run or the simple-change discount applies. The score shift, the clamp and the effort floor still bound it, so a tdd or e2e step at the floor, or a step whose up shift cancels the drop, keeps its tier; the report then marks the drop as not applied. A failed attempt whose drop applied raises no rigor and uses no step budget, but it still counts as a failed attempt for the retry tier, `maxAttemptsPerStep` and the code re-plan, so the retry runs 2 tiers above it. The drop counts as a discount for the score down shift, so the two never stack.
- Impl review after retries or fixes = reviewer at +1.
- Impl review `REJECTED` before any `fix` = one re-plan per run at the plan tier +1, at rigor `standard` or higher and when the extra-step pool allows; otherwise, and for every later `REJECTED`, = fix at the last code tier +1.
- Impl review `NEEDS ATTENTION` with `Decision` lines is routed on its open findings, as a plan review `REVISE` is, with the same tolerance: nothing open, or open warnings within the tolerance, is done with no `fix`; any other open count halts for a human (`halt`) or runs `fix` at the last code tier (`retry`). Without `Decision` lines it runs `fix` at the last code tier on a critical, or on any `NEEDS ATTENTION` while `review.fixOnNeedsAttention` is `true`; that key applies only to such a review.
- Confirmation round (`review.confirmRounds`, per level, ships `0`, off): after a plan review `REVISE` or an impl review `NEEDS ATTENTION` that has `Decision` lines, applied at least one critical or warning fix and left nothing open, the router returns one more review of the same kind (the same step, template `plan-review-confirm` or `impl-review-confirm`) before it goes on. At most the level's count per kind and run, failed ones included. A plan review confirms only before implementation starts. `RETHINK`, `REJECTED` and a review without `Decision` lines never confirm. Each confirmation is a step: raise `rigor.budgetDelta` by 2 per round.
- A step counts as failed when its reported status is not `done`, or the expected artifact did not change: `plan.md` with `## Progress`, a review file with a verdict, or new checked Automated rows (for a tdd or e2e step also a code commit, see the commit check above).
